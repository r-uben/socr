# 2026-08-01 — TICKET-B5: reconstruct a row label wrapped across two lines

## What changed

`src/socr/tables/native_rows.py`:

- **`_merge_continuation_bands(bands, spans)`** — new. Runs after step (1)'s band
  construction and before step (2)'s label/value split. Folds a text-only band (no
  values of its own) into the value-bearing band immediately below it — single-hop
  only — when all of: the gap between them is no wider than the text-only band's own
  line height, both share a left edge (nearest-point `round(x0)`), it is not an
  `_MARKER_RE` hierarchy marker ("of which:"), **and** both bands are set in the same
  font.
- **`_span_fonts(page, bbox)` / `_font_of(word, spans)`** — new. A second, narrower
  read of the region (`page.get_text("dict", clip=bbox)`) purely to recover font
  identity per word, since `page.get_text("words")` (used everywhere else in this
  module) does not carry it. Nothing downstream of the band merge depends on this data.
- **`_reading_order(band)`** — new, replaces the plain `sorted(band, key=lambda w:
  w[0])` used to order each band's words before the label/value split. Bisects the
  band by its largest y0 gap; applies top-half-then-bottom-half order only if both
  halves independently share one left edge; falls back to plain x0 order otherwise.

## Why two mechanisms, not one

The ticket's three reproduction cases split into two distinct defects at the band
level:

- **9pt / 12pt gap** — the wrapped continuation line is its OWN band (step (1)'s
  half-height overlap test correctly keeps two lines apart at this gap). The fix here
  is band-level: fold the orphan band into the row below it. This is
  `_merge_continuation_bands`.
- **6pt gap** — tight leading pushes the continuation line's box far enough into the
  value line's box that step (1) already merges them into ONE band (by design —
  `270cdab`'s half-height rule is deliberately permissive here). The defect is then
  purely about **word order within that one band**: plain x0-sort interleaves the two
  original lines ("Central government net" / "debt" → "Central debt government net").
  This is `_reading_order`.

Both are required; neither alone covers all three gaps.

## Two failed intermediate designs, both caught by the corpus gate, not the unit suite

1. **First `_merge_continuation_bands`: unrestricted right-to-left chaining.** Passed
   all unit tests, but on OBR page 48 chained THREE unrelated text-only bands (a
   "£ billion" axis-title fragment, a chart-legend fragment, and the table's real first
   data row) into one fabricated phantom row, because nothing bounded how far the merge
   could reach once it found any numeric band. Fixed by restricting to single-hop: the
   target band must already carry values before any merge happens, never accumulated
   through one.

2. **`_reading_order`'s first form: a blanket `(y1, x0)` sort over every band.**
   Fixed the 6pt case in isolation, but regressed 10 real pages (39, 48, 59–63,
   65–67) on the corpus gate:
   - **Root cause A (page 61):** word bbox top edges (`y0`) are not level across
     glyphs of different heights on one physical printed line — the digit in "GDP1"
     sits higher (smaller `y0`) than the capital letters in "Nominal" beside it, even
     though both share one baseline (`y1`). Sorting on `y0` read that as two lines and
     reversed the words to "GDP1 Nominal". Switching the sort key to `y1`-primary
     fixed this case but not the rest.
   - **Root cause B (page 48):** a *pre-existing* bug in step (1)'s band clustering —
     unrelated to B5, present at `899dd80` too — where a transitively-chained
     y-overlap test can absorb x-unrelated content into one band regardless of
     horizontal distance, when `locate_tables` scopes a bbox generously enough to
     include chart axis labels or legend fragments alongside the real table. The OLD
     x0-only sort happened to push the resulting garbage band's label past all its
     words, so the row silently dropped (a "lucky" pre-existing defect, not a real
     fix). The new y1-sort instead fabricated a phantom row (`"£ Other spending
     policy"` with value `"25"`) by reordering the same garbage band differently.
   - This is why the final design bisects each band and only reorders it when a
     genuine two-line split with matching left edges is found, otherwise falling back
     to the original x0 order — it deliberately preserves the pre-existing wide-band
     bug's old (silent-drop) behaviour rather than trying to fix it, since that bug is
     out of B5's scope (reconstructing a wrapped label, not fixing step (1)'s
     clustering).
   - **Root cause C (pages 59, 60, 62, 63, 66, 67), found only after switching to the
     bisection design:** `_merge_continuation_bands`'s geometric rule alone (no
     values, adjacent, matching left edge) is not sufficient — the reference corpus
     carries bold section headers ("Key fiscal determinants", "Financial and property
     sectors") set flush against the data row directly beneath them, geometrically
     identical to a genuine wrapped continuation. These got folded into the row's
     label, corrupting it (e.g. `"Key fiscal determinants Employment (million)"`).
     Added the font-identity check described above — a continuation is the same label
     carrying on, so it shares the row's own font; a section header is conventionally
     set apart (bold/medium weight in this corpus, though the check itself does not
     hardcode a font name, only equality).

## No magic thresholds

Both mechanisms derive their geometry from the page itself: adjacency from the
text-only band's own line height (`bottom - top`), the split point in `_reading_order`
from the band's own largest y0 gap, left-edge matching from the existing
`round(x0)` precedent (`_superscript_tokens`), and font matching from equality against
whatever font the target band already uses — no constant is introduced.

## Findings on the ticket text / assignment framing

- The ticket's "Do" instruction ("Derive adjacency from the page's own line metrics
  (font size, band spacing), not a constant") turned out to be more literally correct
  than the ticket author likely intended — **font identity, not just font size, was
  necessary**, and was not mentioned in the ticket. Without it, the geometric rule
  (no values + adjacent + matching left edge) is genuinely indistinguishable from a
  section header sitting flush against its first data row, which is exactly the shape
  that regressed 6 real corpus pages during development. The ticket's own "known scope
  limits" framing anticipated something adjacent to this ("a genuine text-only header
  line directly above a data row... is indistinguishable from a wrapped continuation")
  but treated it as an accepted, unexercised limitation rather than something the
  reference corpus would actually hit. It does hit it — worth flagging so a future
  ticket doesn't reintroduce the geometric-only version believing it to be safe.
- The ticket did not anticipate that fixing the 6pt case would require touching
  **word order within an already-merged band**, only "reconstruct... row labels" and
  "join in reading order — never x-sort across bands." That framing reads as being
  about the band-merge step, but the actual 6pt defect is downstream, in step (2)'s
  existing sort. Both were in scope by any fair reading of "never x-sort across
  bands," but it's worth noting for anyone tracing the diff against the ticket text
  that the change touches two separate functions for that reason, not scope creep.
- No other issues found with the ticket or the assigning message's framing; the
  "single shared working tree" constraints, corpus-gate-as-primary-check framing, and
  the B2-derived landmine list were all accurate and load-bearing during this work
  (the corpus gate caught two design-level regressions the unit suite missed
  entirely, exactly as B2's own history predicted it would).
