## Defect confirmed (team lead's measurement, reproduced)

`bind()`'s per-cell value comparison read the RAW candidate cell before both the `is_numeric_token`
gate and the `_normalize_numeric_token` equality check. An entity-encoded value that agrees with its
native counterpart (`&minus;1.5` vs native `-1.5`) failed `is_numeric_token` on its undecoded form and
fell straight into the "not a numeric token at all" branch, producing a false `ContradictedCell` for a
row that actually matches. This is the exact gap GH-690's own decision log flagged as unfixed
(`docs/log/2026-09-16_690.md`, "Related finding NOT fixed").

Reproduced with the issue's own fixture before any change:

```
markdown = "| Item | A |\n| --- | --- |\n| Yield | 1.5 |\n|  | &minus;1.5 |\n| Forward | 3.5 |\n"
words    = [(100,60,140,70,"1.5",0,0,0), (100,100,140,110,"-1.5",0,0,0), (100,140,140,150,"3.5",0,0,0)]
bind(words, markdown)
  -> candidate_spacer_rows_dropped = 0      (GH-690's fix, working)
  -> contradicted_cells = 1  native='-1.5'  model='&minus;1.5'
```

## The fix — three sites, same root cause

All three route the candidate cell through `_normalize_cell` (decode HTML entities, strip trailing
dash-rule decoration; `native_verifier.py`, already imported by `binding.py`) before the numeric-token
gate and/or the value comparison, mirroring the #690 fix to `_candidate_row_multiset`.

1. **`bind()`'s equal-lane-count walk** (`binding.py`, the two `ContradictedCell` construction sites):
   `model_value_normalized = _normalize_cell(model_value)` computed once, used for
   `is_numeric_token(...)` and `_normalize_numeric_token(...)` — the two checks that decide
   match/contradiction. `ContradictedCell.model_token` still records the RAW `model_value` (see
   decision below).
2. **`_best_lane_column_map`** (the salvage-DP scoring loop, ~1587): `cand_normalized =
   _normalize_cell(cand_text)` before `is_numeric_token` and before the `_normalize_numeric_token`
   equality test used to award DP score. Without this, an entity-encoded value that genuinely agrees
   with a native lane scores 0 for that (lane, column) pair, so the DP either leaves the lane unmapped
   or — worse, and the case that actually mattered in testing — maps the lane to the WRONG column if a
   decoy plain-text column coincidentally agrees somewhere else.
3. **`_record_inventions_on_parent_row`** (~1653): same normalize-before-`is_numeric_token` gate. A
   parent (heading) row has no native lane tokens, so any numeric candidate cell under it is an
   invented digit that must surface as `model_unbound`. Before the fix, an entity-encoded invented
   value failed the raw gate and was silently dropped — not misclassified, just never reported at all.
   `cand_text` (raw) is still what gets recorded in the `UnboundCell`; only the numeric *test* is
   decoded.

## `ContradictedCell.model_token`: kept RAW

Decision, independently reasoned (matches the team lead's stated view, reasoning is mine):

Keep `model_token` as the raw candidate cell the model actually emitted, not the normalized form used
internally by the comparison.

- **Consistency with the rest of the module.** `UnboundCell.token` already stores the raw cell
  everywhere else in `binding.py` (`model_unbound`/`native_unbound` append `model_value`/`native_value`
  directly, never a normalized derivative). Making `ContradictedCell` the one diagnostic type that
  reports a synthetic, decoded string would be an unexplained asymmetry in a module whose own comments
  repeatedly stress "evidence stays verbatim" (see `test_decorated_native_numerics_yield_a_non_zero_lane_count_and_bind`).
- **Honesty of the record.** The normalized form never appeared in the candidate markdown; it is an
  implementation detail of the numeric-agreement check, not part of the document. A downstream
  consumer (adjudication call, human review, a log) that re-reads the candidate context alongside
  `model_token` should see the same string, or the two will look inconsistent for no reason.
- **No loss of information.** `native_token` is also raw (native words are never entity-encoded — they
  come straight off the PDF), so keeping `model_token` raw preserves symmetry: both sides of a
  `ContradictedCell` show exactly what their source said, and a reader can see for themselves why the
  binder judged them different, rather than being shown one side's post-processed form.

   existing `test_parent_row_inventions_use_native_lane_headers_in_salvage_walk` fixture shape but with
   the invented value entity-encoded (`&minus;9.9`); without the fix it silently vanishes rather than
   surfacing as `model_unbound`.

## Related finding NOT fixed (out of ticket scope, reported)

While designing the salvage-DP test, found that `_candidate_data_column_indices`
(`binding.py` ~536 — decides which markdown columns even count as "data columns", upstream of
everything in this ticket's scope) has the SAME raw-`is_numeric_token` bug: a column's cells are only
counted toward its per-row width if they pass the raw (undecoded) numeric-token check, so an
entity-encoded column never contributes to that count. The consequence depends on table shape, and an
initial draft of this section overstated it — corrected here after the team lead traced the call site's
fail-safe (`binding.py:1905-1911`) and I re-verified against the actual multi-column shape rather than
accepting the correction as fully general:

- **Single numeric column, entirely entity-encoded** (nothing else in the table scores any width):
  `_candidate_data_column_indices` returns `()`. The call site's own guard —
  `if not candidate_data_columns: candidate_data_columns = tuple(range(1, physical_n_cand_cols + 1));
  grid = candidate_grid` (`binding.py:1908-1910`) — is fail-safe here: it falls back to treating every
  physical column as data and keeps the UNPROJECTED grid. Verified: projected `grid.rows` for this
  shape is unchanged, `[('A', '&nbsp;1.5'), ('B', '&nbsp;2.5')]`. **No content is lost** in this case.
  The "dropped from the candidate grid entirely" reading in an earlier draft of this section was
  checked against exactly this shape and is WRONG for it.
- **Mixed columns — at least one OTHER column has plain-text numeric content** (this ticket's own
  salvage-DP test fixture: `Val` all entity-encoded, `Extra` all plain): `Extra` alone establishes a
  nonzero per-row width, so `_candidate_data_column_indices` returns a NON-EMPTY tuple (verified:
  `(2,)`, just the `Extra` column). The `if not candidate_data_columns:` fail-safe at 1908 does **not**
  fire — nothing is empty. `_project_candidate_data_columns` then runs and the projected grid genuinely
  drops `Val`: verified `grid.rows` becomes `[('A', '9.9'), ('B', '9.9')]`, `Val`'s entity-encoded cells
  gone before `bind()`'s comparison logic (this ticket's fix) ever sees them. **This is real content
  loss, not merely a skipped narrowing**, and it is exactly what forced the salvage-DP test's design:
  a `Val` column entity-encoded on every row vanished upstream regardless of this ticket's fix, so the
  test was redesigned so `Val` keeps one plain-text row to survive this upstream filter, isolating the
  actual site-2 (`_best_lane_column_map`) behavior under test rather than accidentally exercising this
  unrelated site.

So the severity is shape-dependent: the fail-safe genuinely covers the case where the WHOLE table's
candidate side scores no numeric content anywhere, but does not cover — and was never traced to cover —
the case where one specific column is entity-encoded while a sibling column is plain. Same root cause as
GH-679/GH-690/GH-766 ("labels are decoded, values are not"), one layer further upstream. Not fixed
here — outside the ticket's named scope (2194/2222, 1626/1653, 1587) — flagged per the issue's own note
to check for further sites. Candidate for its own ticket, and that ticket should scope to the
mixed-column case specifically, since the single-column case is already fail-safe.
