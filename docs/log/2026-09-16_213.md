## Single-locator fixtures: all NULL — and that is a fixture-shape failure, not a detector finding

Every fixture below models an index row as **one term + one trailing page number** — the
shape the issue's own disproof argues about (`_MIN_LANES_PER_ROW = 3`,
`reconstruct.py:90`; `_MIN_TABLE_ROWS = 3`, `reconstruct.py:91`; gated at
`reconstruct.py:613`, `len(numeric_words) < min_lanes_per_row * _MIN_TABLE_ROWS`). One
numeric token per row cannot reach 3 lanes; none of these should be expected to fire, and
none did:

| Fixture | rows | `find_tables()` | `has_numeric_columns()` | `has_tables` |
|---|---|---|---|---|
| right-aligned page numbers | 25 | 0 | False | False |
| left-aligned page numbers | 25 | 0 | False | False |
| right-aligned, fewer rows | 10 | 0 | False | False |
| right-aligned, more rows | 40 | 0 | False | False |
| two numeric cols/row (term, "see also" ref, page no.) | 25 | 0 | False | False |
| genuine two-column PAGE LAYOUT (independent left/right index lists) | 25 | 0 | False | False |
| GH-64's own `test_book_index_page_also_flags` fixture, reproduced verbatim | 25 | 0 | False | False |

**These are not evidence that the detector rejects book indexes in general.** They are
evidence that a single-locator fixture is the wrong model of a book index, confirming (via
independent construction) what the earlier session found by reading real pages: see next
section. A null from the wrong fixture says nothing about the detector.

This includes the fixture at
`/Users/rubenffuertes/repos/.worktrees/socr-64/tests/test_gh64_table_structure_flag.py:285-331`
(`test_book_index_page_also_flags`, GH-64 branch, mid-merge, not touched by this session).
That test's own assertion (`not result_page.has_tables`, line 329) is correct about what it
asserts — on that fixture, routing does reject it. But the fixture itself is not a faithful
book-index model: a real index entry is not one term + one page number, it is a term
followed by a *list* of locators (see below). GH-64's test is right about its own fixture
and should not be changed for this; it simply cannot be read as settling the #213 question,
because it never modeled the shape that actually reaches the corpus.

## The earlier, real-page measurement (cited, not re-verified)

Source: `docs/log/2026-08-15_213-branch-identification.md`, commit `7a72cbe` (branch
`docs/213-index-routing-plan`, unmerged). Measured directly on
`2003__woodford.pdf` pp. 798–799 and `039_2021__nagel__ml_ap.pdf` p. 157 (real corpus
pages; not reproduced here, not opened by this session):

| Page | `find_tables()` | `has_numeric_columns()` |
|---|---|---|
| woodford p798 | 0 | **True** |
| woodford p799 | 0 | **True** |
| nagel p157 | 0 | **True** |

Intermediate numbers (from that log): woodford p799 — 82 numeric tokens, 15 lanes, 33 rows,
10 qualifying rows (gate needs `>= 3`). woodford p798 — 52 tokens, 19 lanes, 27 rows, 7
qualifying. nagel p157 — 124 tokens, 14 lanes, 44 rows, 13 qualifying.

The mechanism that log identified: a real index entry carries a *list* of locators on one
running line — e.g. `under, 410–11; asymmetric, 418; choice of index, 13–14, 440–41, 442f,`
— several numeric tokens at several x-positions on a single line, which alone populates
`>= 3` lanes without any column alignment across the page. That is not the shape any
single-locator fixture (including GH-64's) can produce.

That session's follow-on (`docs/log/2026-08-16_213-lane-sharing-rejected.md`, commit
`e8e0a2a`) already tried and killed a Task-2 candidate: a lane-sharing / Jaccard-overlap
discriminator (mean pairwise Jaccard of lane-sets over qualifying rows). Measured against 3
index pages (0.111–0.323), 8 real tables (0.600–1.000), and 403 native pages: no valley
below 0.95 in the full distribution, and ~5.4% of real captioned tables sit at or below the
index pages' ceiling. **Do not attempt this discriminator again** — it is measured and
dead, not merely untried.

## This session's independent confirmation (synthetic, multi-locator)

Built a fixture from a different direction than the earlier session — not reading corpus
pages, but modeling "several locators per running line" directly: 25 rows, each one term
followed by 4 numeric tokens spread across increasing x-positions on the same line (no
ruled lines, no header row):

| Fixture | `find_tables()` | `has_numeric_columns()` | `has_tables` |
|---|---|---|---|
| multi-locator index entries (4 numeric tokens/row, irregular x) | 0 | **True** | **True** |

This reproduces the earlier session's conclusion from an independent construction: it is
**Branch B — `has_numeric_columns`, the lane-cooccupancy gate** — that admits a book index,
not `page.find_tables()`. `find_tables()` returned 0 tables on every fixture tried in this
log, single- or multi-locator, real or synthetic.

## Answer to Task 1

**Branch B (`has_numeric_columns`) fires; Branch A (`find_tables()`) does not.** Confirmed
twice independently: on real corpus pages (2026-08-15, `7a72cbe`) and, in this session, on
a from-scratch synthetic multi-locator fixture. The mechanism is not the single trailing
page number the issue originally (and still, in its current text) frames the disproof
around — it is that a dense index entry's own list of cross-reference locators, several
numeric tokens on one running line, is by itself enough to clear the 3-lanes-per-row,
3-row gate that `_MIN_LANES_PER_ROW` / `_MIN_TABLE_ROWS` set
(`reconstruct.py:86-91,613`).

## Open question (added after review; not settled, not this session's finding)

`has_numeric_columns`'s docstring (`reconstruct.py:541-569`, GH-248/GH-348) states that
co-occupancy alone is NOT the discriminator between a table and scatter — the filter this
function is supposed to add is lane **reuse**, the same x-lanes recurring across rows, not
merely each row populating several lanes once. The orchestrator tested this while verifying
this log's multi-locator result and reports:

- A fixture with 4 numeric tokens per row at **random x per row** (25 rows, i.e. scatter
  with no cross-row lane alignment) fires `has_numeric_columns() == True` just as readily
  as the fixed-lane version. That is the exact case the docstring says should be filtered
  out by the reuse requirement.
- An attempt to make this decisive by giving each row a disjoint x-band (so no lane could
  possibly "reuse" another row's) produced a degenerate fixture — only 12 numeric tokens
  were detected, below the `min_lanes_per_row * _MIN_TABLE_ROWS` = 9-token-per-qualifying-set
  floor at `reconstruct.py:613` for reasons unrelated to lane reuse (tokens merged) — so it
  settled nothing.

Status: **UNRESOLVED.** The random-x observation is the orchestrator's, not measured
independently in this session. No defect is claimed on this evidence — a positive
(fires-when-it-shouldn't) result from one ad-hoc fixture is not proof the reuse filter is
inert, only a failure so far to demonstrate that it works. If the filter turns out to be
inert, that has consequences for GH-248/GH-348 and belongs in its own ticket, opened on a
proper fixture harness rather than on two people's throwaway PDFs.
