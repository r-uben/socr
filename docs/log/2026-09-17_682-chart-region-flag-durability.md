# GH-682: three GH-189 chart-region flags did not survive resume

## What changed

`chart_region_render_failed`, `chart_region_placement_unresolved`, and
`chart_region_inventory_failed` drove the document-status demotion in
`_apply_chart_region_guard`-equivalent aggregation (the `chart_region_lost_pages` /
`chart_region_unresolved_pages` blocks in `_phase_assemble`, `orchestrator.py:13215-13234`)
but were never persisted to the page sidecar and never restored on resume. Their siblings
`chart_asset_render_failed` / `chart_asset_detection_failed` were, four lines away, in both
the sidecar-meta write block (`orchestrator.py` around 11151) and the
`_restore_terminal_page_state` restore block (around 12065). On resume the three defaulted
`False`, the guard became a no-op, and a page that had lost a chart region reported a clean
`SUCCESS`.

Fix, mirroring the sibling code exactly:

1. Persist the three flags in the sidecar meta build block
   (`src/socr/pipeline/orchestrator.py`, next to `chart_asset_detection_failed`).
2. OR-restore them in `_restore_terminal_page_state`, same pattern as
   `chart_asset_detection_failed` (never a plain assignment — a flag this run already set
   must survive a sidecar written before the flag existed, or from a run that never set it).

## Files changed

- `src/socr/pipeline/orchestrator.py` — the write + OR-restore blocks (29 lines).
- `tests/test_chart_lane.py` — 7 new tests: write persistence (3, parametrized), OR-restore +
  demotion-survives (3, parametrized), and the clean-resume-stays-clean direction (1).
- `tests/fixtures/p6/prechange_assemble.json` — purely additive: the three new keys, `false`,
  added to all 12 corpus sidecar entries (the p6 golden-byte-identity fixture; regenerated by
  hand-patching rather than the `socr-regenerate-p6-prechange` devtool, since that tool
  requires a committed revision and running it uncommitted would have meant amending the
  ticket's one commit — see "P6 golden fixture" below).
- `tests/test_p6_disposition_persistence.py` — the frozen pre-disposition sidecar key-set
  test (`test_sidecar_only_additive_key_is_disposition`) updated to include the three new
  keys; this enumerates the FULL sidecar key set minus `disposition` and must be updated
  whenever a field is legitimately added to the sidecar, same as any other addition would
  require.

## Tests

The resume test is the point (per the ticket): it drives the real
`_restore_terminal_page_state`, writes a stale clean sidecar, sets the flag as "this run", and
asserts BOTH the flag survives (OR) AND `_phase_assemble` on the restored state still returns
`AUDIT_FAILED` — not just that the field round-trips. A separate, isolated write-side test
exercises the real `_flush_page_sidecar` and reads the key back off disk (a hand-written-JSON
resume test alone cannot catch a missing write). A negative-direction test resumes a page with
no chart-region problem and asserts it stays clean at the document level too.

(`/tmp/gh682-mut-write`, `/tmp/gh682-mut-restore`); canary
`os.path.realpath(socr.__file__)` confirmed each mutant resolved to its OWN copy, not the
shared venv's editable install or `/tmp/wt-682`. Confirmed uncapped anchor `count == 1` in
`orchestrator.py` before each edit.

- **Write mutation** (reverted the three-key write block in the sidecar meta build):
  `test_gh682_chart_region_flag_persisted_in_sidecar_write[chart_region_render_failed]`,
  `[chart_region_placement_unresolved]`, `[chart_region_inventory_failed]` all reddened

- **OR-restore mutation** (reverted the OR to a plain `bool(meta.get(...))` assignment,

  3 parametrized cases (`chart_region_render_failed`, `chart_region_placement_unresolved`,

## P6 golden fixture — the non-obvious part

Adding the three keys to every sidecar broke `tests/test_p6_stage_ab_difference.py`'s
`TestPreChangeByteIdentity` (byte-identity against `tests/fixtures/p6/prechange_assemble.json`)
and `tests/test_p6_stage_c_difference.py`, plus the frozen key-set test in
`test_p6_disposition_persistence.py` — 7 failures, all correctly caused by this ticket's
change (verified: running the SAME comparison against the unmodified baseline tree produces
zero failures in those files). This is the sanctioned mechanism, not scope creep — the module
even ships a regen devtool (`socr-regenerate-p6-prechange`) precisely for "a field legitimately
added to the sidecar". Patched `prechange_assemble.json` by hand instead of via that tool
(which needs a committed revision, `git archive <rev> src`) because regenerating an
uncommitted change would have forced amending the ticket's one commit; the patch is verified
purely additive (`git diff --stat`: 36 insertions, 0 deletions — exactly the 3 keys × 12
corpus sidecars) and all 83 p6-family tests pass afterward.

One initial false alarm on this path, corrected before touching the golden fixture: a
standalone (non-pytest) capture script showed large NON-additive drift (page 9/12 events
differing) even against the unmodified baseline — that was this machine's real ollama
answering differently, because the standalone script bypassed `tests/conftest.py`'s autouse
fixture that blocks the ollama daemon for hermetic tests. Re-run inside a real pytest test
(so the autouse fixture applied) reproduced the SAME non-additive drift on baseline too,
proving it long-predates this ticket (the p6 test suite absorbs it via
`apply_stage_c_patch`, a documented prior migration's expected delta) — GH-682's actual,
isolated effect on that fixture is exactly the 36 additive lines committed here.

## Where the ticket's framing was imprecise

`_apply_chart_region_guard` as a function name does not exist; the demotion is the inline
`pages_ok = pages_ok and not chart_region_lost_pages` / `... chart_region_unresolved_pages`
block in `_phase_assemble` (`orchestrator.py:13215-13234`), which sends the DOCUMENT to
`AUDIT_FAILED`, not the individual page to `WARNING` (the page's own `best_output.status` is
untouched by this guard — `audit_passed` stays `True` deliberately, per the #252 precedent
noted in the surrounding comments). This doesn't change the fix or its scope; the demotion
test asserts the document-level `AUDIT_FAILED` outcome, which is what the ticket's "the guard
still demotes" requirement actually needs.
