# TICKET-E1 — mechanical binding evidence at the gate (GH-353)

## What changed

`_run_table_judge_gate` (`src/socr/pipeline/orchestrator.py`) now runs
`tables/binding.py:bind()` against every LOCATED table witness before it hits
the real judge ladder. When `bind()` finds a genuine conflict — a value
anchored to the wrong row label, or a value token that contradicts the
candidate's own cell at the same anchored position — a synthetic rung
(`mechanical:binding`) carrying those findings as a `TableJudgeVerdict(verdict="FAIL",
confidence="high", findings=[...])` is **prepended** to the real rung
sequence and passed to A4's `run_table_ladder()` unmodified. Absence of
coverage (no native words on the page, cells the geometry couldn't check)
never triggers this — only `contradicted_cells` / `row_label_contradictions`
being non-empty does.

New helpers on `UnifiedPipeline`:
- `_binding_contradiction_findings(binding_result)` — maps
  `RowLabelContradiction` / `ContradictedCell` to `Finding(code=WRONG_BINDING, ...)`.
- `_binding_contradiction_rung(findings)` — builds the fixed-FAIL synthetic `RungCallable`.
- `_binding_contradiction_for_witness(state, page_num, witness)` — reads native
  words for the page via `open_pdf`, calls `bind(words, witness.markdown,
  region=witness.box.bbox)`, returns `None` (no-op) unless a genuine
  contradiction is found. Errors (unreadable PDF, `bind()` raising) are caught
  and logged, never escalated — the mechanical check degrades to absent, not
  a crash.

`_run_table_judge_gate` tracks which table_ids were forced
(`forced_by_binding: dict[str, bool]`) and uses that to correct the
`rung_trail` audit payload's positional `rung1_model`/`rung2_binary` label
offset — without the fix, prepending a synthetic rung would silently
mislabel every real rung's `executing` field by one slot once a
contradiction fires.

## Design decision: CONTRADICTION-ONLY, not `no_known_contradiction`

The ticket text says "`no_known_contradiction == False` forces the FAIL
path." I did not use that property literally. `BindingResult.no_known_contradiction`
is `not (contradicted_cells or row_label_contradictions or native_unbound or
model_unbound)` — it goes `False` on mere *coverage gaps* (unmatched native
or candidate cells), not only on genuine conflicts. Using it literally would:

1. Violate the ticket's own second acceptance criterion — an empty-`words`
   fixture (no native text at all) drives `no_known_contradiction=False`
   purely via `model_unbound`, with zero actual contradictions, which is
   exactly the "must not be demoted" case.
2. Spuriously flip ~15 pre-existing, already-accepted tests in
   `tests/test_table_judge_gate.py` (a file I don't own): its `_ruled_pdf` +
   `_TABLE_MD` fixture has native text ("00,01,...,33") that doesn't
   literally match the candidate markdown ("10,11,...,33"), producing
   `native_unbound`/`model_unbound` entries with zero `contradicted_cells`/
   `row_label_contradictions` — i.e. a coverage gap, not a defect.

I used the narrower signal already named and ratified in
`src/socr/tables/witness.py`'s own module docstring (from the same
2026-08-30 consilium round, citing E1 by ticket ID): only
`contradicted_cells or row_label_contradictions` forces demotion.
`native_unbound` / `model_unbound` / `row_binding_unverifiable` /
`column_binding_unverifiable` / `ambiguous_count` stay excluded — they are
absence-of-evidence signals, not conflict signals, and the design's own
"mass-demotion trap" guard is precisely to keep absence from demoting.
Verified: `~/venvs/socr/bin/pytest tests/test_table_judge_gate.py -q` — 19
passed, zero regression.

## Design decision: injection-as-rung, not post-hoc override

The team-lead brief also said the mechanical check "must be able to overrule
a judge PASS" (citing GH-273, where two frontier judges both blessed the
wrong-binding table). Composing the mechanical FAIL as rung 0 in the sequence
passed to `run_table_ladder()` does **not**, by itself, guarantee that: A4's
already-ratified semantics let *any* high-confidence PASS at *any* position
accept immediately ("never held hostage by an earlier B"), so a real rung
that still claims high-confidence PASS after seeing the mechanical findings
in `prior_findings` can still win. I kept the injection-as-rung design
anyway, because:

- It is the literal mechanism the ticket specifies ("tiebreak... with the
  contradictions attached as findings evidence for the next rung's
  `prior_findings`") and it composes with A4's public API without touching
  A4's file (out of my write ownership).
- It still gives the mechanical check real teeth in the two cases that
  matter operationally: (a) when no real rung is available at all (e.g.
  `strict_local`, or every profile otherwise unavailable) — the synthetic
  rung is then both first and last, so its FAIL exhausts the ladder to
  REJECTED unconditionally, with no judge able to override it; (b) when a
  real rung, having now seen the binding evidence, does not answer with
  high confidence — a low-confidence PASS after a FAIL tiebreak resolves to
  UNVERIFIED (A4: "a lone weak witness is not consensus"), not a silent
  ACCEPTED.
- What it deliberately does *not* guarantee: a real rung that insists on a
  high-confidence PASS despite the injected evidence still wins. This
  matches A4's own documented contract and is not something E1 can change
  without reopening A4's ratified design. I flagged this as the one place
  where the literal "must overrule a judge PASS" language and A4's existing
  semantics are in tension, and resolved it in favor of A4 (already-accepted,
  out of my write ownership) rather than post-hoc overwriting the ladder's
  own outcome after the fact.
