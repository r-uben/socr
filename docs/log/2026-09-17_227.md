# 2026-09-17 — GH-227: cascade-halt must not fire on a page that succeeded

**Branch:** `fix/227-halt-only-on-failed-pages` (off `main@f80f44e`)
**Status:** DONE

## The defect

`UnifiedPipeline._attempts_show_timeout` answers "did anything on this page time
out" (its own docstring), not "did this page fail". The call site in
`_phase_agentic` (`orchestrator.py`) used that `any(...)` result on its own to
arm the cascade-halt: `if _had_timeout and not self._probe_backend_idle():`.
A page whose first rung timed out and whose later rung was accepted armed the
halt identically to a page that timed out and stayed failed.

This was latent until #221 (functional generation canary) and #222
(host-aware probe) shipped: before those, `probe_..._idle()` could not
actually report "not idle" for a live backend (an `/api/tags` ping answers
200 OK regardless of what the model is doing), so `not self._probe_backend_idle()`
never fired for a healthy-but-busy backend and the bug had no observable
effect. With a working probe the branch is live: a document with every page
succeeding can now be marked `PARTIAL_SAVE_VLM_TIMEOUT` and truncated —
pages never processed — on the strength of an early timeout the page
recovered from on its own.

## What changed

`src/socr/pipeline/orchestrator.py` (`_phase_agentic`, around the cascade-halt
check): gated the halt on the page's own outcome, not just on whether any
attempt on it timed out:

```python
_had_timeout = self._attempts_show_timeout(decision.attempts)
if _had_timeout and not decision.accepted and not self._probe_backend_idle():
```

`decision.accepted` (`PageDecision.accepted`, `agentic.py`) is the ladder's
own verdict for this exact page — `PageDecision(..., accepted=True)` is
returned only once some rung's `decision.accept` fires
(`agentic.py:439`); the fallback path used when nothing was accepted
returns `accepted=False` (`agentic.py:442`). This is the same field the
surrounding code already reads to decide `SUCCESS` vs `AUDIT_FAILED` for the
page (a few lines above the halt check), so gating on it reuses the outcome
the ladder already computed rather than re-deriving it from the attempt
list.

`_attempts_show_timeout` itself is unchanged — its docstring's question ("did
anything time out") is still the right question for it to answer; the bug
was that the CALLER treated that answer as sufficient on its own. Left the
`"timeout"` substring scan alone (out of scope per the ticket) and did not
touch the probe or its host resolution (#221/#222, already done).

## Deliberately out of scope

- The full degraded-backend policy (canary the specific backend, mark
  degraded, drop ladder rungs using it) that the issue attributed to a
  `docs/plans/2026-08-17_backlog-reconciliation/TICKET-D1` which does not
  exist in this tree. Not implemented — a citation neither the dispatcher
  nor I could read is not a spec.
- Attributing the timeout to the SPECIFIC attempt that determined the
  outcome (via `backend`/`provider_id`, now available per #159). Not
  needed: `decision.accepted` already IS the outcome for this page as a
  whole, and the ticket's acceptance criteria only require distinguishing
  "this page succeeded" from "this page did not" — which `decision.accepted`
  does exactly, without needing to single out which attempt's backend timed
  out.
