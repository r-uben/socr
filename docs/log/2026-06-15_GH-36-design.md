# GH-36 — General clean-equation to LaTeX path (design)

Date: 2026-06-15
Plan folder: `docs/plans/` (ticket: GH-36 section of `docs/plans/TICKETS.md`)
Status: design note for the consilium gate (no production code written)
Author agent: socr-designer (read-only on source)

## Scope recap

The **corrupt-font** math subcase already ships end to end: a born-digital page whose math
glyphs are font-map mojibake gets its corrupt-math *lines* cropped, OCR'd to LaTeX by a local
VLM, and spliced back into otherwise-trusted native prose. GH-36 is the **clean-equation**
sibling: a born-digital page whose prose AND math both decode fine as text, but where native
extraction *linearizes* the math (flattens super/subscripts, drops/garbles symbols, breaks
reading order). For those pages we want a real LaTeX rendering of display equations, gated so
bad LaTeX never silently replaces a faithful crop or the native linearized text.

This note follows the **same two-tier shape as GH-49A** (`docs/log/2026-06-15_GH-49A-design.md`):
a deterministic gate validates a model output *before* it is allowed to replace good content;
on failure, keep the faithful fallback and record provenance — never silently overwrite.

## 1. What exists today

### The corrupt-font math recovery path (reuse, do NOT duplicate)

`src/socr/math/recover.py` is the whole engine and it is already structured exactly the way
GH-36 needs:

- `corrupt_math_line_rects(page)` (`recover.py:49`) — pulls `get_text("dict")` lines, keeps
  those that trip `line_has_corrupt_math`, merges vertically-adjacent ones into equation
  `fitz.Rect` regions. Merge gap `_REGION_MERGE_GAP_PT = 6.0` and pad `_REGION_PAD_PT = 4.0`
  are named module constants (not magic literals) — `recover.py:36,39`.
- `latex_for_image(png, ...)` (`recover.py:111`) — base64 PNG → local Ollama `/api/generate`,
  `temperature=0`, `num_ctx=8192`, `keep_alive=30m`, returns `""` on any failure (caller keeps
  the crop). `urllib` only; no new deps.
- `recover_math_regions(page, ocr=…)` (`recover.py:153`) — renders each region at
  `DEFAULT_DPI=300`, OCRs (retry once), returns `(rect, latex)` pairs. `ocr` is injectable for
  tests.
- `splice_math(page, native_text, regions)` (`recover.py:192`) — walks dict lines in reading
  order; a line covered by a region is emitted once as `$$…$$`; empty-LaTeX regions emit a
  crop-reference note `*(equation — see page image; OCR unavailable)*` so corrupt glyphs never
  reach the corpus. **This is already the "never replace good with bad" guarantee — but only
  for the corrupt case, where the native line is known-garbage so any non-empty LaTeX is an
  improvement.**

Orchestrator wiring (`src/socr/pipeline/orchestrator.py`):
- `corrupt_math_pages` built from `pa.has_corrupt_math` (`orchestrator.py:652`); gated on
  `config.recover_corrupt_math` + born-digital + has native text (`:659`); such pages go to
  `prose_pages` AND `math_recovery_pages` (`:667`), deliberately avoiding whole-page VLM OCR.
- Tier-1 splice loop `:788` calls `recover_math_regions(page, model=self.config.math_model)`
  then `splice_math`, tags engine `native+math`, prints `recovered/total equations`.

Config knobs already exist: `recover_corrupt_math: bool = False` and `math_model`
(`src/socr/core/config.py:131,135`), surfaced on the CLI (`cli.py:238,240`). Both are part of
the manifest's replay fingerprint inputs (`config.py:274`).

**Two real defects in the existing code GH-36 must reckon with (cite, do not silently inherit):**
1. `recover.py:29` hardcodes `DEFAULT_MODEL = "qwen3-vl:8b"` — **violates the repo rule** (the
   only sanctioned local OCR model is `qwen3-vl:30b-a3b-instruct`; never `:8b`/`:30b`). The
   orchestrator path overrides via `config.math_model` (default `"qwen3.5:cloud"`), so the bad
   default is only hit by direct callers/tests, but GH-36 touches this file and should fix the
   default to `qwen3-vl:30b-a3b-instruct` as part of the work.
2. **There is no LaTeX validation anywhere.** `splice_math` accepts *any* non-empty model
   string as LaTeX. For the corrupt case that is tolerable (native is garbage). For GH-36's
   clean case it is **not**: the native linearized text is faithful-but-flattened, so an
   unvalidated, malformed, or hallucinated LaTeX block could replace genuinely-correct content
   — the exact silent-data-loss the hard AC forbids. **The validation gate is the new core of
   GH-36.**

### Equation detection signals (confirmed in `src/socr/core/born_digital.py`)

`PageAssessment` carries both `has_equations` and `has_corrupt_math` (`born_digital.py:72,74`).
`has_equations` is set true if any of (`:289`):
- `_detect_math_fonts(page)` (`:632`) — scans `page.get_fonts()` basefonts against
  `_MATH_FONT_RE` (CMMI/CMSY/STIX/etc.). O(font_count), source-side, runs before extraction.
  **This is the primary, deterministic clean-equation signal and it already exists.**
- `_detect_equations(text)` (`:681`) — literal LaTeX markup / `$$…$$` (rare in typeset PDFs).
- `has_corrupt_math` (the mojibake path).

So a clean-equation page is exactly: `has_equations and not has_corrupt_math and
is_born_digital`. **The page-level trigger already exists; what does NOT exist is a
*clean-equation region detector*** — `corrupt_math_line_rects` keys off `line_has_corrupt_math`,
which is false on clean pages, so it returns no regions. GH-36 needs a sibling region detector.

What PyMuPDF actually exposes for deterministic display-equation region location WITHOUT
whole-page OCR (all already used in-repo):
- `get_text("dict")` lines with `bbox` + per-span `font` names → a line whose spans are
  predominantly a math font (`_MATH_FONT_RE`) is an equation line; merge vertically-adjacent
  ones exactly like `corrupt_math_line_rects` does. Reuse `_REGION_MERGE_GAP_PT`/`_REGION_PAD_PT`.
- Display equations are typically **isolated, horizontally-centered blocks** with extra
  leading/trailing vertical gap — detectable from line `bbox` x-centering vs. page text width
  and inter-line gaps. Any centering/gap tolerance must be **named/derived/config**, not a bare
  literal (GH-36 hard rule), mirroring the existing named constants.
- Equation *numbering* (`(3.4)` flush-right on the math line) is a strong, cheap confirmer.

### Provenance plumbing to mirror (do not invent new)

- `ManifestEntry.journal: list[dict]` (`src/socr/core/manifest.py:119`) — per-page provenance of
  attempts tried. An accepted equation replacement should append a journal entry (engine
  `native+math`, region bbox, crop path, validation verdict).
- `AuditEvent(kind, page_num, …)` + `RunAudit` (`src/socr/core/audit_log.py:43,63`) — stable
  machine-token events. GH-36 adds kinds like `equation_latex_accepted` /
  `equation_latex_rejected_kept_crop`, mirroring GH-49A's `native_table_structure_failed`.

### Crop-PNG storage precedent (mirror exactly)

`FigureExtractor._save` (`src/socr/figures/extractor.py:448`) writes
`self.save_dir / f"figure_{fig_num}_page{page_num}.png"`, `save_dir.mkdir(parents=True)` at
`:150`, gated on `config.save_figures`. Equation crops should follow the identical pattern, e.g.
`equation_{n}_page{N}.png` under the same per-document output dir, so retained crops sit beside
figures and are referenced from the `$$…$$` fallback note.

**Reusable as-is:** region merge geometry, render path, Ollama call, splice walk, manifest
journal, audit-log, figure-PNG save pattern. **New:** clean-equation region detector (math-font
lines + centered-block geometry), **the LaTeX validation gate**, and the splice **policy**
(replace only on validation pass; else keep crop + native linearized text).

## 2. Options

Two genuinely independent forks. **Fork 1 (validation/fallback policy) is the decision-critical
one** — it is what makes GH-36 safe and is mandated by the hard AC. **Fork 2 (engine) is
secondary** and largely answers itself given the repo's local-first stance and the fact a
working VLM path already exists.

### FORK 1 (primary) — LaTeX validation gate before splicing

Common to all: on a clean page the native linearized text is *faithful but flattened*, so the
gate must be strict enough that a bad LaTeX never replaces it, yet permissive enough that valid
LaTeX with retained crop is the win. All options keep the crop PNG regardless and append a
manifest/audit entry. Any tolerance is named/derived/config.

- **Option 1A — Lightweight parser check (`pylatexenc` / structural validation, no TeX run).**
  Validate that the model output parses as well-formed LaTeX math: balanced `{}`/`\left\right`/
  environments, known macros, no stray prose, non-empty. `pylatexenc` is a pure-Python dep
  (lightweight, offline, permissive license) already idiomatic for this. *Pro:* fast (ms),
  deterministic, offline, no toolchain, runs per region at scale. *Con:* validates *syntax*,
  not *visual fidelity* — a syntactically-valid but wrong transcription (e.g. swapped sub/sup)
  passes the gate. Mitigate by keeping the crop PNG always (the human/audit can compare), which
  the AC already requires.
- **Option 1B — Full TeX render-to-image + compare.** Compile each LaTeX block (e.g.
  `matplotlib mathtext`, KaTeX/Node, or a real `pdflatex`) and confirm it renders without error;
  optionally image-compare against the crop. *Pro:* strongest "renderable" guarantee, directly
  matches AC wording "produce renderable LaTeX." *Con:* heavy dependency (full TeX or a JS/Node
  KaTeX or matplotlib-mathtext, which supports only a math subset), slow, a determinism/replay
  liability (toolchain version affects output), throughput risk flagged by AC3. matplotlib
  mathtext is the lightest renderer but rejects many valid LaTeX constructs → high false-reject.
- **Option 1C — Render-validate but NEVER splice; always keep crop, attach LaTeX as sidecar.**
  Treat LaTeX as advisory: emit the crop PNG inline (faithful) plus the validated LaTeX in a
  comment/sidecar, never replacing the native/crop in the body. *Pro:* zero false-replacement
  risk by construction (satisfies the hard AC trivially); decouples engine quality from corpus
  safety. *Con:* doesn't deliver the ticket's headline value (renderable LaTeX *in* the
  document); defers the splice decision rather than solving it.

Trade-off summary: 1A is the local-first/deterministic-throughput pick and the only one that
scales per-region cheaply; 1B best matches the literal "renderable" AC but is a dependency/
throughput/replay hazard; 1C is the safest but lowest-value.

### FORK 2 (secondary) — equation→LaTeX engine

- **Option 2A — Reuse the existing local `qwen3-vl:30b-a3b-instruct` VLM path.** `recover.py`'s
  `latex_for_image` already works and is benchmarked faithful on the corrupt class. *Pro:* zero
  new dependency, fully offline, identical code path/provenance/keep_alive tuning, consistent
  with repo local-first philosophy. *Con:* general VLM, not math-specialized; per-region latency
  is the throughput variable AC3 wants measured.
- **Option 2B — Texify (math-specialized image→LaTeX).** *Pro:* purpose-built, often higher
  symbol fidelity on display equations. *Con:* new heavyweight dep (PyTorch + model weights),
  GPU-hungry, another model to vendor/version; license/offline fit must be checked; duplicates
  the VLM call shape for marginal gain over 2A.
- **Option 2C — marker-pdf.** *Pro:* end-to-end PDF→markdown with equation handling. *Con:*
  whole-*document* converter — directly fights this repo's region-only, avoid-whole-page-OCR
  architecture and its deterministic born-digital routing; wrong layer, heavy dep. Reject.

Cloud (e.g. current `math_model` default `qwen3.5:cloud`) is allowed as an opt-in but must not
be the default for an offline-first corpus pass.

## 3. Recommendation

- **Fork 1: Option 1A (pylatexenc structural validation), with the crop PNG ALWAYS retained and
  the native linearized text kept on validation failure.** It is deterministic, offline, fast
  enough for per-region throughput (AC3), adds one light pure-Python dep, and — combined with
  always-keep-crop — fully satisfies the hard AC that bad LaTeX never silently replaces a
  faithful crop. 1B's full render is a dependency/replay/throughput hazard disproportionate to
  the gain, since 1A + retained crop already prevents silent loss. **But this is the
  decision-critical fork: a reasonable reviewer could argue the AC's word "renderable" demands an
  actual render (1B) — panel it.**
- **Fork 2: Option 2A (reuse local qwen3-vl:30b-a3b-instruct)** — clear enough to NOT panel.
  Reuse the proven local path, fix the `:8b` default in `recover.py:29`, keep cloud as opt-in.
  Texify/marker are dependency weight the repo's local-first stance doesn't justify when a
  working local VLM exists. Revisit only if 2A's measured symbol fidelity on clean display
  equations proves inadequate.

Primary fork for the panel: **the validation/fallback policy (Fork 1).** Secondary, only if the
panel wants it: engine choice (Fork 2), but I recommend skipping it.

## 5. Acceptance-criteria readiness & ticket-split recommendation

ACs as written:
- *"Display equations on a sample chapter produce renderable LaTeX with retained crop PNGs"* —
  implementable, but **"renderable" needs tightening**: it is exactly Fork 1. If the panel picks
  1A, restate as "produce **structurally-valid** LaTeX (parses as well-formed math) with retained
  crop PNGs"; if 1B, keep "renderable (compiles)". Resolve before implementation.
- *"Bad LaTeX never silently replaces a faithful image/crop"* — implementable and is the hard
  gate; satisfied by always-keep-crop + validation-on-failure-keeps-native. No change needed,
  but make "faithful" explicit: the native linearized text is the clean-case fallback, not
  garbage.
- *"Region-only throughput is measured before any default-on decision"* — implementable;
  requires a measured per-region latency report (reuse the corrupt-math timing path) and keeping
  the feature **default-off** (`recover_corrupt_math` is already `False`; add a parallel
  `recover_clean_equations` flag default-off). Tighten: name the throughput metric (regions/min
  or s/region) and the sample chapter.

Detection thresholds: the new centered-block / math-font-line region detector must express any
centering, vertical-gap, or math-font-span-fraction tolerance as **named/derived/config**
constants (mirror `_REGION_MERGE_GAP_PT`), not bare literals — call this out in the
implementation ticket.

**Split recommendation — YES, split into two phases:**
- **GH-36a — detection + crop + provenance (no engine quality dependency):** clean-equation
  region detector (math-font lines + centered-block geometry), crop-PNG storage mirroring
  `FigureExtractor._save`, manifest journal + audit-event kinds, the `recover_clean_equations`
  flag (default-off), and the throughput harness. Deterministic, fully unit-testable without a
  model (inject `ocr`, like `test_math_recover.py`).
- **GH-36b — engine integration + validation gate + splice policy:** wire the chosen engine
  (recommended 2A: local qwen3-vl, fixing the `:8b` default), the Fork-1 validation gate (panel
  outcome), and the splice-vs-keep-crop policy; the default-on decision waits on GH-36a's
  measured throughput.

This split lets the deterministic, safe-by-construction half land and be reviewed independently
of the engine/validation fork the panel is deciding.

## Consilium decision (2026-06-15, run 20260615T210537Z-6621) — ACCEPTED

**Panel:** Codex (gpt-5.5) + Gemini (antigravity). **Verdict: Hybrid 1A + 1C, unanimous.**

Validation-before-splice policy for GH-36b:
- **1A structural gate (pylatexenc, pure-Python, offline, deterministic, replay-safe):** accept VLM
  LaTeX only if structurally well-formed (balanced delimiters/environments, known macros, non-empty).
  On failure, keep the native linearized text and record the failure reason. NO heavy render
  toolchain in the deterministic path.
- **1C non-destructive presentation:** NEVER silently replace the crop or native text in the document
  body. Always inline the crop PNG as visual ground truth; attach the 1A-validated LaTeX ADJACENTLY
  (sidecar / comment / `<details>` / image alt / `<socr-equation>` block), marked as a
  structurally-validated candidate. Rationale: 1A validates SYNTAX, not FIDELITY — syntactically
  perfect LaTeX can still be a semantic hallucination (x_i↔x_j, dropped summation limit), and in a
  citation corpus a confident-but-wrong equation is toxic.
- **1B (full render / image-compare) REJECTED** as the deterministic gate (toolchain weight +
  replay-determinism liability + brittle false-rejects). At most a later opt-in `--qa-render-check`,
  manifest-recorded.

### Phase split (designer's recommendation, reinforced by the decision)
- **GH-36a** — model-free foundation: deterministic display-equation region detection + crop-PNG
  storage + manifest/audit provenance + default-OFF flag + throughput harness. Fully unit-testable
  without a model. **Also fix the two flagged defects:** `math/recover.py:29` hardcodes the
  forbidden `qwen3-vl:8b` default (repo rule violation), and document that `splice_math`
  (`recover.py:192`) does zero LaTeX validation (acceptable for the corrupt-font case where native
  is garbage, but the exact silent-data-loss risk this ticket must NOT replicate for clean math).
- **GH-36b** — engine integration (reuse local `qwen3-vl:30b-a3b-instruct`, NOT marker-pdf/Texify)
  + the 1A validation gate + the 1C splice/keep-crop policy. The default-on decision waits on
  GH-36a's measured region-only throughput (a hard AC).

Engine fork was NOT paneled: reuse the proven local VLM (settled by local-first philosophy).
