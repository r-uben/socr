# 2026-09-16 — GH-690: spacer filter drops unlabeled rows with entity-encoded values

Worked in `/Users/rubenffuertes/repos/.worktrees/socr-690` (branch
`fix/690-spacer-entity-numbers`, based on `origin/main@7d4b5ef`). All commands run with
`PYTHONPATH=/Users/rubenffuertes/repos/.worktrees/socr-690/src`; `socr.__file__` confirmed
pointing inside the worktree before any test run.

## Defect confirmed (team lead's measurement, reproduced)

`_candidate_row_multiset` (`src/socr/tables/binding.py`) ran `is_numeric_token(tok)` on the
RAW cell. `_normalize_candidate_rows` only HTML-unescapes the LABEL cell
(`_normalize_label_cell`, col 0). An unlabeled row whose only value is entity-encoded
(`&minus;1.5`) or `&nbsp;`-prefixed (`&nbsp;62.5`) was therefore misclassified as a #601
layout spacer by `_is_spacer_row`, and `bind()` silently dropped it.

`_candidate_row_multiset` is the SAME function `_bind_rows` calls for the row-anchoring
numeric multiset compare, so the hole was not confined to spacer classification: an
entity-encoded value row that survived classification for some other reason would still fail
to anchor.

## (a)/(b) choice: promoted `_normalize_cell` to `native_verifier.py`

GH-679 (`6226e92`, merged an hour before this ticket started) added `_normalize_cell`
(`html.unescape` + trailing-dash-rule strip over a named `_TRAILING_DASH_CHARS` constant) to
`src/socr/tables/source_evidence.py`. It is the exact normaliser both tickets want shared, not
copied a third time.

Chose **(b): promote to `src/socr/tables/native_verifier.py`**, not (a) import it across
modules as private to `source_evidence.py`. Reasoning:

- `binding.py` already imports from `native_verifier` (`is_numeric_token`,
  `_normalize_numeric_token`, `label_key`, etc.) — no new cross-module dependency edge.
- `source_evidence.py` already imports from `native_verifier`
  (`_numeric_multiset_from_tokens`, `is_numeric_token`) — same story.
- `binding.py` and `source_evidence.py` do not otherwise import each other; importing (a)
  `_normalize_cell` from `source_evidence` into `binding.py` would have created a NEW,
  otherwise-unjustified dependency edge between two independent table-verification modules for
  the sake of one shared helper. `native_verifier.py` is already the shared low-level
  normalisation module both depend on (`is_numeric_token`, `strip_presentation`,
  `_normalize_numeric_token` all live there) — `_normalize_cell` belongs next to them.
- There is existing precedent for private (`_`-prefixed) helpers in `native_verifier.py` being
  imported across `tables/` submodules (`_normalize_numeric_token`, `_numeric_multiset_from_tokens`),
  so keeping the name `_normalize_cell` (not renaming to a public name) matches the module's
  existing convention rather than introducing a new one.

This is the right layer, not merely a convenient one: `native_verifier.py`'s own imports are
`socr.core.table_grid` and `socr.tables.reconstruct` only — neither imports `source_evidence`
or `binding`, so the dependency direction is (and stays) `native_verifier` <- {`binding`,
`source_evidence`}, one more symbol flowing the SAME pre-existing edge, not a new one.

`source_evidence.py`'s own behaviour must not change: its import was rewritten to
`from socr.tables.native_verifier import (_normalize_cell, _numeric_multiset_from_tokens,
is_numeric_token)`, the local definition (and now-orphaned `_TRAILING_DASH_CHARS`) deleted, no
other line touched (`html` stays imported there — it is used elsewhere in the module, not only
by `_normalize_cell`). GH-679's own test file
(`tests/test_gh679_decorated_numeric_tokens.py`) exercises only the module's PUBLIC functions
(`collect_table_tokens`, `verify_table_tokens`), never `_normalize_cell` directly, so it needed
no changes and is included in the 748-test targeted run below, all passing.

## The fix

`_candidate_row_multiset` now runs `_normalize_cell(cell).strip()` (decode entities, strip
trailing dash-rule decoration) before splitting on whitespace and checking `is_numeric_token`,
instead of the raw `cell.strip()`. One-line change to the function both `_is_spacer_row` (#601
classification) and `_bind_rows` (row-anchoring multiset compare) call — closes both call
sites in one place, matching the ticket's "before spacer classification (and ideally before
multiset compare)" ask.

## Wider `&nbsp;` finding

Confirmed the ticket's own scope note: the hole is not `&minus;`-specific. `&nbsp;62.5` fails
`is_numeric_token` on the raw cell by the identical mechanism (no entity decode before the
numeric-token check) and was dropped the same way. Fixed by the same one-line change (the
normaliser decodes ALL HTML entities via `html.unescape`, not a `&minus;`-specific string
replace) and pinned explicitly in `test_gh690_nbsp_prefixed_value_row_is_kept_not_dropped`.

## Related finding NOT fixed (reported, out of ticket scope) — UNFIXED, needs its own ticket

**This is the most load-bearing finding in this log and it is deliberately left unfixed.** A
false `ContradictedCell` on an entity-encoded value actively asserts that correct data is wrong,
where a drop merely loses it.

**Severity, corrected against the code.** An earlier draft of this paragraph (the team lead's
wording, written before anyone traced it) said a false contradiction "can demote a page that was
actually right." That is NOT supported. Traced before this PR merged: a contradiction sets
`forced_by_binding` (`orchestrator.py:7057`), which escalates the table to adjudication, and the
code states explicitly that **a mechanical contradiction does not upgrade this to REJECTED**
(GH-359 ruling 5, in a comment at that site). With no rungs available (`strict_local`, or CI with
no provider) it fails open to UNVERIFIED.

So the real cost is an unnecessary adjudication call on data that is already correct, plus a
recorded contradiction that is not real. That is bounded, and it is why this ticket ships without
waiting for the fix. Had a contradiction demoted the page, this PR would have been held until both
were fixed together — the severity is what decided the scope, so it is recorded here rather than
asserted.

While reproducing the fixture with a matched native word, found a THIRD instance of the same
underlying gap (raw, un-decoded candidate cell reaching a numeric check) in a DIFFERENT gate:
`bind()`'s own per-cell value comparison, inline in `bind()` itself (not `_bind_rows` /
`_candidate_row_multiset`, which this ticket fixed).

**Exact anchors** (this repo, post-fix, `src/socr/tables/binding.py`):
- `binding.py:2194` — `model_value = model_raw.strip() or None` (raw cell, no `_normalize_cell`).
- `binding.py:2222` — `if not is_numeric_token(model_value):` — checks the RAW, un-decoded
  value, so an entity-encoded number always fails this and falls into the mismatch branch below.
- `binding.py:2224-2231` and `binding.py:2233-2242` — both `ContradictedCell(...)`
  constructions in this walk use the raw `model_value` as `model_token`.
- Same shape in the salvage-DP counterpart: `_record_inventions_on_parent_row`
  (`binding.py:1626`), `cand_text = cand_row[col].strip()...` at `binding.py:1653` and
  `binding.py:1587`, neither routed through `_normalize_cell`.

**Minimal reproduction** (run with `PYTHONPATH=<worktree>/src`):

```python
from socr.tables.binding import bind

markdown = "| Item | A |\n| --- | --- |\n| Yield | 1.5 |\n|  | &minus;1.5 |\n| Forward | 3.5 |\n"
words = [
    (100, 60, 140, 70, "1.5", 0, 0, 0),
    (100, 100, 140, 110, "-1.5", 0, 0, 0),  # native word: real minus, matches &minus;1.5
    (100, 140, 140, 150, "3.5", 0, 0, 0),
]
result = bind(words, markdown)
print(result.candidate_spacer_rows_dropped)  # 0 -- this ticket's fix: row survives
print(result.contradicted_cells)
# [ContradictedCell(row_path=('',), col_path=(), native_token='-1.5',
#                    model_token='&minus;1.5', native_bbox=(100, 100, 140, 110))]
```

The row is no longer dropped (this ticket's fix works), but its value is then marked
CONTRADICTED against a native token that is the SAME number, because `is_numeric_token` at
line 2222 sees the raw `&minus;1.5`, not a decoded `-1.5`.

This is a DIFFERENT gate than either #679 (evidence-gate numeric multiset) or this ticket's
#601 spacer classifier. Explicitly out of this ticket's stated scope ("before spacer
classification (and ideally before multiset compare)" — the multiset compare it names is
`_candidate_row_multiset` via `_bind_rows`, not this inline per-cell match/contradict walk in
`bind()`). Not fixed here; needs its own ticket — it has a materially wider blast radius
(every table's cell-level match/contradict path, not
just spacer classification) and deserves its own scoped ticket and review, not a
scope-creeping addition to this one.
