# 2026-08-30 — TICKET-A1: verdict schema, rung contract, event kinds (GH-353)

## What
New `src/socr/judge/table_verdict.py` — the ladder's owned contract, importable
by every other ladder module without re-deriving the schema:

- `FindingCode` — closed 6-value `str` enum (MISSING_VALUE, FABRICATED_VALUE,
  WRONG_BINDING, HEADER_MANGLED, STRUCTURE_MERGED, NOT_A_TABLE).
- `Finding` (code, where, detail) and `TableJudgeVerdict` (verdict, confidence,
  findings, raw) dataclasses.
- `parse_table_verdict(text) -> TableJudgeVerdict` — strict JSON parse via the
  same `_extract_json` balanced-brace/fence extraction `socr/judge/judge.py`
  already uses for the page-level judge (imported, not duplicated). Fenced
  ```json``` output parses cleanly (NOT an S1 failure — the gemini CLI fences
  routinely). Any of: empty output, non-JSON, non-object JSON, missing/invalid
  `verdict`, missing/invalid `confidence`, malformed `findings` entry, unknown
  `code`, or a findings list that violates "empty iff PASS" raises
  `TableVerdictParseError` — the S1-failure signal. `TableVerdictParseError` is
  never turned into a synthesized FAIL; callers see ¬S1 and must escalate as a
  substitute (fresh eyes), not a tiebreak.
- `RungResult` (rung id, `ok` S1 bit, verdict, latency_sec, error) and the
  `RungCallable` protocol `(crop_path, markdown, prior_findings) -> RungResult`
  that A2 (ollama) and A3 (gemini) implement.
- `rung_result_from_output(rung, text, latency_sec)` — the shared S1
  classification helper so A2/A3 don't each reimplement the
  try/parse/except-into-RungResult dance.
- Three audit-event kind constants (`TABLE_LADDER_ACCEPTED_KIND`,
  `TABLE_LADDER_REJECTED_KIND`, `TABLE_LADDER_UNVERIFIED_KIND`) plus a
  frozenset of all three, for B1 (gate) to emit and B2 (trust) to register in
  `TABLE_DISTRUST_KINDS`/`RESOLVING_KINDS`. Intermediate per-rung steps
  (tiebreak/substitute) are not separate event kinds — they're `RungResult`
  values a caller may log, not terminal dispositions a consumer reads.

## Design choice not spelled out in the ticket
The design doc says findings are "empty iff PASS" (`docs/log/2026-08-30_table-
judge-ladder.md`), a biconditional. I enforce both directions: PASS with
non-empty findings, and FAIL with empty findings, both raise
`TableVerdictParseError` (¬S1) rather than being silently accepted. A FAIL with
zero evidence is exactly as untrustworthy as the inverse case.
