# TICKET-C2 — surface content loss on local-only runs (socr #123)

Branch `feat/123-metric-blind-spots`, on top of C1's `8a6efee`.

## The gap C1 left

C1 routed B1's not-scorable gate and B2's unexplained-lane count through
`tables_trust`, but the only call site was `_table_page_needs_escalation`,
only reached from `_escalate_table_page`, only reached when
`_pick_escalation_provider` returns a non-`None` profile. socr is local-first
by design, so a local-only run — no cloud provider configured,
`--strict-local`, or a cost cap suppressing the lane — never called either
method, and every not-scorable page and unexplained-lane page shipped with no
trace, same as before C1. On the reference document that is 17 of 68 pages.

## What changed

**One new call site, zero new emitters.** `_table_page_needs_escalation`
already is the single emitter (grid gate → `table_not_scorable`,
`ceiling_note` → `table_not_scorable`, `unexplained_lanes` →
`table_unexplained_lanes`); this ticket does not touch its body.

`src/socr/pipeline/orchestrator.py`:

- New method `_surface_table_scoring(state, page_num, ps, bo)`: opens the PDF,
  gets the page, and calls `_table_page_needs_escalation` for its side effect
  (the audit events), discarding the boolean return. Wrapped in the same
  broad `except Exception` + `logger.warning` pattern `_escalate_table_page`
  already uses, so a scoring failure never loses a page.
- The per-page loop's escalation branch (around what was line 2469) gained an
  `elif bo.text:` arm that calls `_surface_table_scoring` whenever the `if`
  (escalation profile present, lane not degraded) does not fire — i.e. no
  provider, `--strict-local`, the lane turned off, or the lane degraded after
  a wedged provider. The `if` branch itself is byte-for-byte unchanged.

No change to `_table_page_needs_escalation`, `_escalate_table_page`,
`escalation_decision.decide_escalation`, or any accept/reject logic. When a
provider IS available, the code path taken is identical to before this
ticket — the `elif` is only reachable when the `if` is false.

## The cost measurement — the decision this ticket turns on

Measured `native_rows_from_page` + `score_page` (the two calls
`_table_page_needs_escalation` makes) run over every page of the reference
document (`~/data/fiscal-ballast/regulation/uk/obr_efo/2022-11-17_efo-november-2022.pdf`,
68 pages), using the preserved emitted markdown in
`~/data/fiscal-ballast/_experiments/2026-08-01_gh96-corpus-rerun/out/2022-11-17_efo-november-2022/pages/`.
Pure CPU, no model call, no PDF re-render:

```
pages=68 grid_pages=18 (pages clearing the B1/B2 grid predicate)
native_rows_from_page: total=6834.60ms  mean=100.509ms  max=537.544ms
score_page (grid pages only): total=1550.89ms  mean=22.807ms  max=154.743ms
combined total: ~9270ms for the whole 68-page document (~136ms/page mean)
fitz.open() overhead for 68 fresh opens: 155.68ms total (~2.3ms/page) — negligible
```

`native_rows_from_page` dominates and must run on every page regardless of
whether it turns out to be a grid — there is no way to know without running
it. Three pages carry most of the cost (537ms, 427ms, 334ms; everything else
is under 165ms), consistent with those being the document's largest native
tables.

**Decision: always-on, no opt-out.** ~9.3s total CPU across a 68-page
document (~137ms mean, ~692ms worst case per page) is negligible against the
per-page VLM inference this loop already pays for on every page in agentic
mode — local qwen3-vl inference alone runs multiple seconds per page, before
any table re-read, equation, or repetition pass. The measured cost is roughly
1-2 orders of magnitude below the work this loop already does per page, so an
opt-out would add configuration surface to save time nobody would notice.
This matches the ticket's own framing: "if the measured cost is negligible
relative to a page's existing native-text work, always-on is the simpler and
better answer."

## No third not-scorable contract, no duplicated predicate

`_surface_table_scoring` calls `_table_page_needs_escalation` — the existing
method — rather than reimplementing any part of its grid check or event
emission. There is still exactly one emitter for `table_not_scorable` /
`table_unexplained_lanes`, called from two sites (`_escalate_table_page` and
the new `_surface_table_scoring`) instead of one.

## Escalation behaviour — unchanged, verified

`tests/test_gh96_escalation_lane.py` covers `_table_page_needs_escalation`
and `_escalate_table_page` directly and is entirely unmodified by this
ticket (41 tests, all pass). The `if` branch's body in the per-page loop
(`_escalate_table_page(...)`) is untouched; the new `elif` is only reachable
when that `if` is false, so a run with a provider configured takes the
identical code path it took before this ticket.

## CI hermeticity

`_surface_table_scoring` calls no engine, no provider, no ollama — it is a
pure PDF-text-layer read plus the pre-existing `score_page` metric. The new
test drives it directly with a hand-built fixture PDF and asserts on
`state.events`; nothing here touches `_phase_agentic` or `process()`, so
there is no provider ladder to patch and no `_available_engines_for_agentic`
dependency.

## Collision risk / follow-up for the reviewer

- The per-page loop's escalation block now has an `if`/`elif` instead of a
  single `if`; anyone re-reading that block should not assume "no
  escalation" means "no table scoring happens" any more — it now always
  scores a table page against its native layer when there is output text.
- `_surface_table_scoring` opens a fresh `fitz.open(state.handle.path)` per
  call, matching `_escalate_table_page`'s existing pattern rather than
  threading a shared document handle through the per-page loop. Measured
  overhead is ~2.3ms/open on the reference document — not worth the
  refactor to share a handle, but noted in case a future change already
  has one open and can avoid the reopen.
- STATUS.md and TICKETS.md updated in the same commit (ticket board, active
  agents table, findings/next-action sections).
