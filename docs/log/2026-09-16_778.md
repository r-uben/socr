# GH-778 fix: `_native_label_lane` decodes an entity-encoded model label

Branch `fix/778-decode-label-lane`, off `origin/main@7992215`, worktree
`/Users/rubenffuertes/repos/.worktrees/socr-778`.

## The defect

`_native_label_lane(grid, label, words)` (`src/socr/tables/header_repair.py`)
tokenised `label` with `re.findall(r"[\w&]+", label.casefold())` directly on
the raw text, then compared token-for-token against native PyMuPDF words
(`w[4]`, never entity-encoded). An entity glued to a word corrupted that
word's own token and the match silently abstained:

```
'Net income'        raw -> ['net', 'income']            matches native
'Net&nbsp;income'    raw -> ['net&nbsp', 'income']        'net' corrupted, no match
```

## Fix: decode through the existing `decode_label_cell` boundary

`label_tokens = re.findall(r"[\w&]+", decode_label_cell(label).casefold())`.

`decode_label_cell` (`socr/tables/label_canonical.py`) is already the shared
"binder's view of a row label" (`html.unescape` + strip leading whitespace),
used by `binding.py` and `chart_reconcile.py`. Reusing it here keeps a single
point of truth for "what a label decodes to" rather than adding a second,
possibly-diverging decode step (`html.unescape` alone would have been
sufficient for this call site's needs, but the shared boundary function is
the established pattern and costs nothing extra — it decodes fully then
strips leading whitespace, which is a no-op for mid-string tokenising).

No circular import: `label_canonical.py` imports only `reconcile`, and
`header_repair.py` already imports `reconcile` too.

## Measurements

```
html.unescape('Net income')        -> 'Net income'          tokens ['net','income']
html.unescape('&nbsp;Net income')  -> '\xa0Net income'       tokens ['net','income']   (leading NBSP dropped by \w, harmless)
html.unescape('Net&nbsp;income')   -> 'Net\xa0income'        tokens ['net','income']   (THE fix)
html.unescape('Profit & Loss')     -> 'Profit & Loss'        tokens ['profit','&','loss']
html.unescape('Profit &amp; Loss') -> 'Profit & Loss'        tokens ['profit','&','loss']
html.unescape('&minus;1.5')        -> '− 1.5' (U+2212)  tokens ['1','5']  (minus sign dropped by \w; not \w's job to fold presentation — labels are not this module's numeric path)
html.unescape('&nbsp')  (no ;)     -> '\xa0'                 tokens []          (unresolved, no worse than before)
html.unescape('&amp;amp;')         -> '&amp;'                tokens ['&amp']    (double-encoded, one layer only, as before)
```

## The `&` decision — keep it in the token class

Question was whether `&` is still load-bearing in `[\w&]+` after decoding.
Measured: after `html.unescape`, any `&` remaining in the text is a LITERAL
ampersand ("Profit & Loss"), not an entity — entities are gone by then. Native
PyMuPDF word-splitting on whitespace makes `&` its own word token
(`get_text("words")` splits "Profit & Loss" into `Profit`, `&`, `Loss`), so
the label side must also emit `&` as its own token to match. Removing `&`
from the class would silently break a legitimate "Profit & Loss"-style label.
Verified directly with a synthetic fitz page
(`test_literal_ampersand_in_label_still_binds`): the label binds correctly
with `&` in the class, both before and after this fix (the ampersand case was
never broken by the entity bug — it's an independent, correct behaviour this
fix must not regress).

## Malformed / partial entities — not touched

`&nbsp` (no trailing `;`) and doubly-escaped `&amp;amp;` are not decoded
further by `html.unescape` (it only decodes what it recognises); they remain
corrupted tokens post-fix, same as pre-fix. No evidence these forms occur in
the corpus (the model emits well-formed entities); not invented handling for
an unobserved case.
