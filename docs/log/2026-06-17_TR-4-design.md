## 1. What exists today — the precise data flow for a failing table page

There are TWO independent table paths in socr, and TR-4's whole reason to exist is that they do
NOT share a fail-closed floor. Both are live; which one fires depends on whether the page took the
native bypass or the OCR ladder.

### 1a. The agentic OCR-ladder path (what fired on real CE)

For a born-digital table page that is NOT trusted-native (any page with tables fails
`_is_trusted_native_without_ocr`), the page is routed through `route_page`
(`agentic.py:140`) inside the page-major loop `_phase_agentic` (`orchestrator.py:1401`,
the OCR branch at `orchestrator.py:1792-1816`):

1. Each ladder rung's output is judged by `NativeTableVerifierJudge.assess`
   (`agentic.py:391`), which runs `verify_native_table(fitz_page, output.text)`
   (`native_verifier.py:482`) BEFORE the inner judge. The verifier is two-tier:
   - **Tier 1 hard-fail** (`native_verifier.py:454-464`): a native data row has
     `>= _MIN_HARD_FAIL_LANES` (=2) well-separated numeric lanes but the output row has fewer
     populated cells → `geometry_impossible_collapse` → `AcceptDecision(accept=False)`, inner
     judge NOT called (`agentic.py:414-432`).
   - **Tier 2 warn-and-defer** (`native_verifier.py:466-477`): ambiguous lane gap → record event,
     delegate to inner judge.
2. The ladder is walked to exhaustion (`agentic.py:183-286`); when every rung's output is rejected,
   `route_page` returns `PageDecision(accepted=False, final_output=_best_effort(...))`
   (`agentic.py:285-286`, `_best_effort` at `agentic.py:113`).
3. Back in the loop, because nothing was accepted AND the page has tables,
   `ps.native_table_structure_failed = True` is set (`orchestrator.py:1821-1822`).
4. **The D3 floor PNG is rendered ONLY if `ps.native_table_unverifiable` is also True**
   (`orchestrator.py:1842-1850`).
5. At manifest-freeze, `_winning_page_output` (`manifest.py:259`) selects what ships. The D3 branch
   (`manifest.py:287-310`) fires ONLY when `native_table_structure_failed AND
   native_table_unverifiable AND attempts`. Otherwise it falls to the native-fallback branch
   (`manifest.py:317-328`) and **ships the collapsed/ragged native text flagged WARNING**.

### 1b. The born-digital `_verify_regions` path (where D3 actually wires today)

`native_table_unverifiable` — the second half of the D3 AND-gate — is set in EXACTLY ONE place:
`apply_born_digital` (`state.py:181-182`) copies it from `pa.has_unverifiable_table_region`. That
field is produced by the born-digital detector during `extract_structured`
(`born_digital.py:837-840`, `_verify_regions` at `born_digital.py:898`), which runs
`verify_native_table_region` per region (`born_digital.py:930`, `native_verifier.py:507`) and sets
`self._last_extraction_had_unverifiable`, surfaced as `has_unverifiable_table_region`
(`born_digital.py:590,622`).

### 1c. The gap real CE exposed (the crux of TR-4 Q4)

`native_table_unverifiable` is set **only** from the born-digital `_verify_regions` extraction, and
that extraction only runs on the page if `extract_structured` is invoked and reaches the rowizer.
On real CE the page went through the **agentic ladder** and hard-failed on the
`NativeTableVerifierJudge` (whole-page `verify_native_table`, path 1a). The agentic path sets
`native_table_structure_failed` (`orchestrator.py:1822`) but has **no code that sets
`native_table_unverifiable`**. So the D3 AND-gate at `manifest.py:287-291` was half-open:
`native_table_structure_failed=True`, `native_table_unverifiable=False` → D3 did NOT fire → the
collapsed/ragged native shipped, flagged WARNING. **D3 (TR-3) is real but unreachable from the
agentic verifier path.** Confirmed by reading: there is no assignment to `native_table_unverifiable`
anywhere in `_phase_agentic` (grep: only `state.py:182` writes it).

Confirmation of ticket assumptions vs. reality:
- TRUE: "D3 only fires on the born-digital `_verify_regions` path." Confirmed — the only writer of
  `native_table_unverifiable` is `state.py:182` ← `apply_born_digital`.
- TRUE: "real CE failed on the agentic `NativeTableVerifierJudge` path." The judge wraps the
  whole-page `verify_native_table` (`agentic.py:405`), not the per-region variant.
- NUANCE the ticket understates: the agentic judge uses the **whole-page** `verify_native_table`
  (`agentic.py:405`), NOT `verify_native_table_region`. So on the agentic path the verifier is also
  un-scoped (the TR-2 per-region scoping never reached the judge — confirmed by STATUS.md open
  question: "the agentic-path whole-page ladder verifier remains whole-page"). TR-4 must scope the
  agentic verifier per region too, or the value-guard will compare whole-page lanes against one
  region's grid and false-fail exactly as TR-2 already fixed on the born-digital side.

### 1d. The scanned page (no geometry net)

`verify_native_table` bypasses cleanly on `get_text("words") == []` (`native_verifier.py:500-502`),
and `NativeTableVerifierJudge` only runs on `is_table_page` (`agentic.py:397`), which is
`_page_has_tables` — false for a scan (no native table detection). So a scanned table page never
reaches any geometry verifier and never reaches D3. There is **no native-token net at all** on a
scan. This is the asymmetry TR-4 Q2 must handle separately.

## 2. The escalation trigger + wiring (TR-4 Q1 / Q4)

The deterministic rowizer (TR-1, `reconstruct.py:rowize_from_word_list`) stays the **free first
pass**. The VLM-for-structure re-ask is the **escalation**, fired in exactly two cases:

- **(born-digital)** the rowized grid FAILS its verifier — i.e. the agentic
  `NativeTableVerifierJudge` returns `hard_fail` (the real-CE path), OR the born-digital
  `_verify_regions` returns a hard-fail. This is the measured real-CE trigger.
- **(scanned)** the page is a table page with NO usable geometry
  (`get_text("words")` empty), so the rowizer and the verifier both no-op.

**Where it sits in the ladder, and its relation to D3.** The re-ask is NOT a new ladder rung. It is
a bounded repair step that runs AFTER `route_page` returns `accepted=False` for a table page, i.e.
right where `native_table_structure_failed` is set today (`orchestrator.py:1821`). Sequence:

```
route_page (ladder, deterministic verifier)  → accepted=False on a table page
  → [NEW TR-4]  one VLM-for-structure re-ask, geometry-constrained
       → value-guard PASSES → ship the VLM grid (accepted=True), DONE
       → value-guard FAILS  → set native_table_unverifiable=True → D3 floor (TR-3)
  → (scanned table page, no geometry) → VLM re-ask, NO value-guard
       → ship flagged lower-confidence, never "verified" → record unverifiable-scan event
```

So **the VLM re-ask happens BEFORE D3; D3 is the floor when the re-ask also fails the value-guard.**
This matches the panel synthesis (§6): "A2 re-ask … → D3 fail-closed floor catches whatever
[it] can't."

**The fix that closes the D3 gap (TR-4 Q4) is small and is the load-bearing wiring change:** on the
agentic path, when a table page's structure cannot be verified (re-ask value-guard fails, OR no
re-ask was possible), the code at `orchestrator.py:~1821` must set **`ps.native_table_unverifiable
= True`** (not just `native_table_structure_failed`). That single assignment makes the existing D3
AND-gate (`manifest.py:287-291`) reachable from the agentic path and renders the existing
`_render_d3_floor_png` call (`orchestrator.py:1842-1850`) live. No new manifest logic is needed —
TR-3 already built the floor; TR-4 just connects the agentic path's wire to it.

## 3. The value-guard algorithm (TR-4 Q2 — the crux)

Accept the VLM's row×column grid ONLY if, **per region**, its numeric-token multiset is **lane-aware
EQUAL** to the region's native numeric tokens. "Equal" (the panel's A2 refinement, §6) — NOT
superset, because superset lets the VLM invent a number into a blank cell and still pass.

### 3.1 Extract the native net (born-digital)

Reuse the existing, validated primitives — do not write new geometry:

- Region words: clip `page.get_text("words")` to the region bbox (top-left-in-bbox convention,
  `native_verifier.py:543-544` / `reconstruct.py:_word_in_any_bbox`).
- Native lanes + `lane_of`: `_lane_count_from_words(region_words)` (`native_verifier.py:129`) →
  `(lane_count, lane_of: x0 → lane_idx)`.
- Native rows: `_rows_by_y_from_words(region_words)` (`native_verifier.py:175`) →
  `{y: [(x0, word), ...]}`. Each `word` that matches `_NUM_TOKEN_RE` AND `_NUMERIC_RE`
  (`reconstruct.py:68-70`) is a native numeric token; its lane is `lane_of[x0]`.

Build the **native per-lane token multiset**: `native_by_lane: dict[lane_idx ->
Counter[token_str]]`, accumulated over every native numeric token in the region. This is the ground
truth: "lane L contains exactly these numeric tokens, with these multiplicities."

### 3.2 Extract the VLM net

Parse the VLM markdown grid for this region (header row + data rows). For each data row, map each
non-empty cell to a **column index**; the column→lane correspondence is established once, by
aligning the C VLM data-columns to the C native lanes in left-to-right x-order (both are ordered;
the VLM is told the lane x-positions in the prompt, §4, so the i-th data column IS lane i). For each
data cell whose text is a numeric token (`_NUM_TOKEN_RE` + `_NUMERIC_RE`, the SAME regex as native),
add it to `vlm_by_lane[col_idx]`. A cell whose normalized text is the blank sentinel (`na`, empty,
`-`) contributes NOTHING to any lane (it is an asserted blank, not a token).

### 3.3 Lane-aware equality (the precise accept criterion)

Accept iff **for every lane index L: `vlm_by_lane[L] == native_by_lane[L]`** as `Counter` equality
(multiset equality), AND the set of lanes is identical on both sides. Concretely:

1. **No invented number:** every token in `vlm_by_lane[L]` exists in `native_by_lane[L]` with at
   least the same multiplicity. Catches the VLM hallucinating a value or copying one from the wrong
   row/column.
2. **No dropped number:** every token in `native_by_lane[L]` appears in `vlm_by_lane[L]` with the
   same multiplicity. Catches the VLM silently omitting a cell.
3. **No shifted number (the lane-aware part):** equality is checked **per lane**, not over the flat
   page multiset. A value that the VLM placed under the wrong column lands in the wrong lane's
   Counter → that lane gains a token it shouldn't and the donor lane loses one → BOTH lanes fail
   equality. A flat whole-region multiset would let a left-right swap cancel out and pass; per-lane
   equality is what makes "no shifted number" detectable. This is the difference from the TR-2/TR-3
   verifiers, which count CELLS, not VALUES, per lane.

`na` / blanks: a native blank means the lane has no token at that row's y — it contributes nothing
to `native_by_lane[L]`. The VLM asserting `na` contributes nothing to `vlm_by_lane[L]`. So a true
blank is invisible to the multiset on both sides, which is correct: there is no token to match. The
**hazard the panel flagged** is the VLM padding a blank with an invented number — that adds a token
to `vlm_by_lane[L]` with no native counterpart → criterion (1) fails → reject. The blank is NOT
paddable. (This is why superset was rejected: superset only enforces (2), not (1).)

Edge cases to specify in implementation:
- **Repeated values** (two forecasters both predict `2.1` in the same column): `Counter` carries
  multiplicity, so two native `2.1` in a lane require two VLM `2.1` in that column — preserved.
- **Number-formatting normalization:** native and VLM tokens are compared as the raw matched
  strings. To avoid a false-fail on `1,204` vs `1204` or `2.10` vs `2.1`, define ONE deterministic
  normalizer (strip thousands separators and surrounding brackets, keep sign and decimals) applied
  identically to both sides. Document it as a named, reproducible normalization — NOT a fuzzy match,
  NOT a tolerance (a tolerance on numeric VALUES would be a silent-loss hole). This is a real
  open implementation detail; flag it but it is not an architectural fork.
- **Column↔lane alignment:** if the VLM emits a different column COUNT than the native lane count,
  the alignment is undefined → reject outright (cannot value-guard a grid whose shape contradicts
  geometry). C is given to the VLM in the prompt (§4), so a mismatch is itself a guard failure.

### 3.4 Scanned pages — no net (TR-4 Q2, scanned branch)

A scan has `get_text("words") == []` → `native_by_lane` is empty → the equality check is vacuous and
would trivially "pass" anything. That is NOT acceptance. For a scanned table page the accept
criterion is: **there is no value-guard, so the VLM grid is shipped FLAGGED lower-confidence and is
NEVER stamped `audit_passed=True` / "verified."** Concretely:

- Ship the VLM structure as the page output with `status=WARNING`, `audit_passed=False`, and a new
  audit event `kind="table_structure_unverified_scan"` stating "no native geometry; table structure
  is model-proposed and NOT value-guarded."
- This is strictly better than today (a scanned table page currently has no table handling at all)
  and honest: it never claims a verification it cannot perform. The scanned table is the one place
  the no-silent-loss guarantee degrades to no-silent-CLAIM — surfaced at page/doc/CLI level, never
  silent.

## 4. Prompt construction without magic numbers (TR-4 Q3)

All constraints are DERIVED FROM THE PAGE; no hardcoded thresholds (CLAUDE.md). Feed the VLM the
region crop PNG plus a constraint block computed from geometry:

- **N (data-row count):** the number of native y-rows in the region that carry `>= 1` numeric token
  (`_rows_by_y_from_words`, `native_verifier.py:175`). Derived, not constant.
- **C (column count):** the native lane count for the region (`_lane_count_from_words`,
  `native_verifier.py:129`). Derived.
- **Row labels:** the leftmost (label-column) text per native y-row, recovered by the same
  label-vs-data split the rowizer already does (`_rowize_segment`, words left of
  `data_start_x - snap_margin`, `reconstruct.py:806`). Gives the VLM the forecaster names so it
  binds name↔value rows correctly (the exact thing v1's gap-segmentation got wrong).
- **Lane x-positions:** the C lane centres (so the VLM's column i ≡ native lane i, anchoring the
  §3.3 alignment).
- **Blank instruction:** "emit `na` for any cell with no value; do NOT invent a number for a blank."

Prompt phrasing must avoid magic numbers (no "expect ~28 rows"): N and C are passed as the page's
own measured counts, and the instruction is "this region has exactly N data rows and C numeric
columns at these x-positions." Store the constraint template in `src/socr/prompts/`
(alongside `table_extract.md`, `extract.py:29`), not inline, so it is reviewable.

- **Model:** local `qwen3-vl:30b-a3b-instruct` (`providers.py:65-71`, `PROFILE_QWEN_LOCAL`). NEVER
  `:30b` (thinking, runs away on dense tables) or `:8b`. The crop-render + Ollama call machinery
  already exists (`TableCropExtractor` / `OllamaTableReader`, `extract.py:110-145`); the re-ask
  reuses it with the constrained prompt rather than building a new VLM path.
- **Bound:** exactly ONE re-ask (not a tunable retry count — a count would itself be a magic number,
  per the §6 A2 framing "one constrained re-ask is the principled bound"). Wrap in the existing
  wall-clock deadline (`crop_wall_clock_deadline`, `extract.py:59`) and cascade-halt probe
  (`probe_ollama_idle`, `extract.py:70`) so a wedged GPU halts the doc rather than firing the next
  page. In `--strict-local` the cloud tier is stripped (`orchestrator.py:1482-1485`,
  `providers.py:TIER_LOCAL` filter); the re-ask is local-only there. Non-strict MAY escalate the
  same constrained re-ask to `qwen3.5:cloud` (`providers.py:76-80`) only if the local re-ask fails
  the value-guard — but that is an optional cost knob, NOT required for v2 correctness, since D3 is
  the floor regardless.

## 5. Fail-closed integration + the D3 gap (TR-4 Q4) — concrete

The whole point: an unverifiable table on the AGENTIC path must fall to the image, never ship a
plausible-but-wrong grid. The wiring:

1. **Scope the agentic verifier per region.** Today `NativeTableVerifierJudge` calls whole-page
   `verify_native_table` (`agentic.py:405`). For the value-guard to be meaningful it must run on the
   region's own lanes — reuse `verify_native_table_region` / `_verify_from_words` on clipped words
   (already built for TR-2). Without this, the guard inherits the whole-page false-fail TR-2 fixed.
2. **Run the bounded re-ask** (§4) when a table page exits the ladder unaccepted (or is a scan).
3. **Apply the value-guard** (§3). On PASS, replace the page output with the VLM grid, mark
   `accepted` for that region, and ship.
4. **On FAIL (or no-geometry scan with a flagged ship):** set `ps.native_table_unverifiable = True`
   at `orchestrator.py:~1821` alongside the existing `native_table_structure_failed = True`. THIS is
   the one-line gap-closer: it makes the existing D3 AND-gate (`manifest.py:287-291`) fire from the
   agentic path, triggering the already-built `_render_d3_floor_png` (`orchestrator.py:1842-1850`)
   and the D3 ship branch (`manifest.py:300-310`: failed-table marker + PNG ref, `status=ERROR`,
   `audit_passed=False`). The distinct audit event `table_region_unverifiable` (`audit_log.py:114`,
   emitted at `orchestrator.py:3747`) already exists and will now cover agentic-path failures too.
5. **No-silent-loss propagation** is already plumbed: `native_table_unverifiable` flows to metadata
   (`orchestrator.py:3289`), restore (`orchestrator.py:3478`), doc-level demotion
   (`orchestrator.py:3677-3678`), and the CLI summary (`orchestrator.py:3771`). TR-4 inherits all of
   it for free by setting the existing flag.

Net: TR-4 adds the VLM re-ask + value-guard and **sets one existing flag on the agentic path**; the
entire D3 ship/PNG/audit/demotion machinery is already built (TR-3). The fix is mostly wiring, not
new manifest logic.

## 6. Failure modes of this design

- **Number-formatting false-fail / false-pass.** The §3.3 normalizer is the single point where a
  too-loose rule (false pass: `2.1`≈`2.10000001`) or too-strict rule (false fail: `1,204`≠`1204`)
  bites. Mitigation: exact normalized-string equality, no numeric tolerance; validate the
  normalizer on the TR-4a fixture's known tokens.
- **Column↔lane misalignment when C is ambiguous.** If native lanes mis-cluster (two real columns
  within `_LANE_X_TOL_PT`, or a paired-year "2023 2024" splitting oddly), the i-th VLM column ≠
  i-th lane and a CORRECT VLM grid false-fails → unnecessary D3. Cost is a missed recovery (ship the
  image), never silent loss — acceptable, fail-closed direction. This is the residual risk that
  motivated S3 (VLM confirm/split, deferred TR-5).
- **Scanned ship is unverified by construction.** A scanned VLM grid can be wrong and we cannot
  detect it. Mitigation: ship flagged, never `audit_passed`, distinct event — the only honest
  option absent geometry. Do not let a future change stamp these SUCCESS.
- **Re-ask cost / latency.** One qwen call (~90-125s on dense tables, `agentic.py:39-42`) per
  failing table page. Bounded to one attempt + deadline + cascade-halt. Acceptable.
- **Multi-schema merged region.** If segmentation handed the re-ask an over-merged two-schema
  region (the TR-2 spike's open question), N/C are wrong and the guard fails → D3. Correct
  fail-closed behavior; full fix is TR-5.

## 7. Acceptance-criteria readiness

TR-4's ticket goal ("escalate to VLM for structure, accept only if geometry confirms values, else
fail closed to D3") is implementable as written once the design is chosen, gated on TR-4a providing
the real-CE-geometry failing fixture. Specifics:

- **Implementable as written:** the escalation trigger (§2), the value-guard equality check (§3),
  the prompt constraints (§4), and the D3 gap-closer (§5). All reuse existing primitives
  (`_lane_count_from_words`, `_rows_by_y_from_words`, `verify_native_table_region`,
  `TableCropExtractor`, the TR-3 D3 floor) — minimal net-new surface.
- **Needs tightening before implementation:**
  1. The number-token **normalization rule** (§3.3) must be named and frozen against TR-4a's tokens
     — "EQUALS" is otherwise underspecified for `1,204`/`1204`/`2.10`.
  2. The scanned-page accept criterion should be stated in the ticket as "ship flagged
     `audit_passed=False`, distinct `table_structure_unverified_scan` event, never verified" — it is
     a different contract from the born-digital path and the AC must say so explicitly.
  3. The agentic verifier must be **scoped per region** (point §5.1) — the ticket implies this but
     it is a prerequisite, not an afterthought; without it the value-guard inherits the whole-page
     false-fail.
- **The TR-4a gate** (real-CE-geometry fixture, `xfail(strict=True)` reproducing the row-merge/
  offset) is the falsifiable acceptance test: it must flip green when the value-guarded VLM grid
  passes, and fail-closed (D3 marker + PNG, zero wrong cells) when it does not.

## 8. Is there a genuine `/consilium` fork? — NO. Recommend skipping the panel.

The two architectural questions TR-4 could raise are **already settled by the §6 panel verdict**:

- "May a VLM enter the repair path for table structure?" → **Q2 = A2: yes, one constrained re-ask,
  value-guarded by lane-aware token EQUALITY (not superset)." Settled, with the exact refinement
  this design implements.
- "What ships when the structure cannot be verified?" → **Q1 = D3: ship neither flawed table — fail
  closed to the image (marker + PNG)."** Settled, and the panel explicitly rejected D2
  (ship-flagged-anyway) because a token check does not prove column placement. This design's
  per-lane equality is precisely the stronger guard the panel asked for; it does NOT reopen D2.

Everything else in TR-4 is implementation detail (the normalization rule, per-region scoping of the
agentic verifier, the prompt template, the scanned-ship contract) — engineering choices with a
clear fail-closed default, not architectural forks. The real-CE evidence the panel said would
justify A2/S3 has fired (`real-CE-v1-finding.md`); v2 is the agreed escalation, not a new decision.

**Recommendation: skip `/consilium` for TR-4 and proceed to implementation against the TR-4a
failing gate.** The one thing worth a quick external sanity-check (NOT a blocking panel) is the
numeric normalization rule in §3.3 — but that can be a `/codex` spot-check during implementation,
not a design-gate consilium.

If the orchestrator nonetheless wants ONE crisp question on record, it is the narrow normalization
fork below — but note it is a code detail, not the architectural fork TR-4 was scoped to surface.

### (Optional, non-blocking) normalization question

> In socr's TR-4 value-guard, the VLM-proposed table grid is accepted only if, per native x-lane,
> its numeric-token multiset EQUALS the page's native PyMuPDF tokens (no invented / dropped /
> shifted number). Native and VLM tokens are raw strings (`1,204`, `(0.014)`, `2.10`, `45%`). To
> compare them as "equal" without a value tolerance (a tolerance would be a silent-loss hole), which
> deterministic string-normalization is correct before multiset equality?
>
> - **Option N1 — strict raw-string equality:** compare tokens verbatim; `1,204` ≠ `1204`,
>   `2.10` ≠ `2.1`. Zero false-pass risk, but false-fails (→ unnecessary D3 image fallback) whenever
>   the VLM normalizes formatting the native layer kept, costing real recoveries.
> - **Option N2 — canonical-form equality (recommended):** strip thousands separators and bracket/
>   percent wrappers, normalize sign, compare the resulting decimal STRING (preserving stated
>   precision, NOT casting to float — so `2.10` and `2.1` are distinct, `1,204` and `1204` are
>   equal). Deterministic, no tolerance, fewer false-fails than N1.
> - **Option N3 — numeric-value equality (parse to Decimal/float):** `2.10 == 2.1`, `1,204 == 1204`.
>   Fewest false-fails, but collapses precision the source distinguished and risks float artifacts —
>   a silent-loss flavor the initiative exists to avoid.
