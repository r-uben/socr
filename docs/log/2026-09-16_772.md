`left` is `item.model_token`, RAW by #766's ruling. Entity-encoded (`&minus;1.5`) failed
`is_numeric_token`, so the comparison fell through to a raw string compare that could never

changes (`item.model_token` still raw). `kind == "row_label"` branch is untouched — it has its
own `label_key` normalizer and was out of scope; not shown to need this.

    tokens_agree('-1.5',       '-1.5', kind='cell')  -> True
    tokens_agree('&minus;1.5', '-1.5', kind='cell')  -> False   (same value, wrongly disagreed)
    tokens_agree('&nbsp;62.5', '62.5', kind='cell')  -> False   (same value, wrongly disagreed)
    tokens_agree('-1.5',       '-2.5', kind='cell')  -> False   (correctly different)

After the fix all four read correctly (the two "same value" cases now `True`, the genuinely
different pair stays `False`).

## Site 2 — `row_corroboration.py:_is_genuine_numeric`

`text` is fed from `table_blocks()` model markdown via `numeric_body_rows`, used for the
row-shape reconciliation count. Same raw gate; an entity-encoded genuine value was silently
excluded from the count.

**The `(1)` trap** — `_SPEC_NUMBER_RE` (`^\(\d+\)$`) excludes spec-number footnote decoration
from the count. Decoding first and then applying the same exclusion still excludes it correctly:
`&lpar;1&rpar;` decodes to the plain `(1)` shape, which `_SPEC_NUMBER_RE` matches as before.
Measured: `_is_genuine_numeric('(1)') == (False, '')` and
`_is_genuine_numeric('&lpar;1&rpar;') == (False, '')`, both unaffected by the fix. A third shape,
`(&nbsp;1)` -> `(\xa01)` -> `strip_presentation` -> `'( 1)'`, is excluded too, but for a different
reason: the internal space breaks `_NUM_TOKEN_RE`'s anchored shape so it never reaches
`is_numeric_token` as true at all (not a `_SPEC_NUMBER_RE` match) — checked, not assumed; noted
here so a future reader doesn't mistake it for the same exclusion path.

Fix: route `text` through `_normalize_cell` before the `is_numeric_token` gate, same as
`binding.py`'s four sites.
