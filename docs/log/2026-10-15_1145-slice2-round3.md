# #1145 slice 2 — review round 3, and what the surviving mutant taught

2026-10-15. PR #1168 merged at c4e7c725; these land in the first commit of the slice-3
equation branch, per the orchestrator.

## 1. The ordering gap (Fable P1)

The stub was written BEFORE `_write_metadata`, which swallows every exception on purpose — a
metadata write must never lose OCR output. So a lost write, or a process killed between the
two, left the stub on disk with no `failed` status beside it; `has_installable_text` read a
markdown file with no refusal evidence and INSTALLED it.

Closed twice, because the two writes cannot be atomic and neither file should be
load-bearing alone:

* **Order.** The failure record is written FIRST, so the window does not exist. A second,
  additive metadata write then fills in `output_path`. Asserted by observing the write
  order, not argued from the source.
* **Content.** `has_installable_text` also refuses a file whose whole stripped content
  `fullmatch`es the document-failed grammar. The recogniser is the pipeline's regex,
  imported rather than restated — two copies of a mark shape in two packages is how an
  emitter and a reader come to disagree, which is why #1145 moved the page grammar into
  `core/marks` in the first place.

### The surviving mutant, which is the most useful thing in this round

With the content check added, `shared-gate-ignores-the-status` **SURVIVED**: deleting the
status check left every existing test green, because a stub is caught by either layer. That
is the failure mode of defence in depth — a second line of defence that no test can
distinguish from the first is not depth, it is unexamined code, and it would have rotted
silently.

So each layer now has a case only it can refuse:

| case | only this layer refuses it |
| --- | --- |
| real TEXT with a `failed` record | the status check — and this is a real shape, not a contrivance: a run that produced text and then failed records exactly it |
| a stub with NO record at all | the content check — the lost-metadata window itself |

plus a control (ordinary text, `partial` record) so neither layer can pass by refusing
everything. `shared-gate-ignores-the-status` and `gate-trusts-the-content-alone` are
separate mutants now, each killed by that one test.

## 2. The magic `4096` (Fable P2)

Dropped, not replaced. It was a bare number the repo forbids, and it did harm: a detail
longer than it made the next run fail to recognise its own stub, refuse to rewrite it, and
log that existing text had been kept when there was none.

Measured before deciding: every `unreadable_input` detail on the corpus is **103**
characters (5 of 5), and the longest document `error` string socr has ever recorded is
**2,906** (n=2,014; p99 1,522; median 451). So any cap near the old one sits below real
data. And a bespoke size bound here would defend against something no neighbouring reader
defends against — `_load_json` and the meter's `_read_text` read whole files — so it would
be a threshold with no basis rather than a safeguard. Truncating the detail was the other
option and was rejected: the detail is the only diagnostic a reader of that file gets.

## 3. CLI wording (Fable P2)

"text directory exists without `<stem>.md`" was asserted for every blocked stem. True while
the only way to be blocked was a missing file; false once the gate also refuses a document
whose markdown IS a failure mark — and it sent the reader looking for the wrong problem.
`library.blocked_reason` now names what is actually on disk, one branch per way a stem can
be blocked, and the test has a row for each.

"awaiting approval: socr library --promote <stem>" after a re-run is now conditional on
`staged_stems` actually offering the stem. Before this ticket that message invited a command
that ARCHIVED the real text and installed the mark over it; after round 2 it invited one
that merely fails. Neither is a thing to print.
