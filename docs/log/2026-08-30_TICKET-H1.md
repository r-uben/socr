## The three terminals exercised

1. **`TestRejectedTerminal`** — a real (injected) judge answers FAIL on the shifted
   table; the clean table's judge answers a high-confidence PASS. `page 2` lands
   `TABLE_REJECTED`, `page 1` stays undemoted — proving the demotion is per-page, not a
   document-wide sweep.
2. **`TestPlainUnverifiedTerminal`** — an infra (¬S1, `ok=False`) rung on the **clean**
   table (no mechanical evidence involved at all — the shifted table's candidate
   markdown is the CORRECT one in this scenario, so no contradiction fires); `page 1`
   lands `TABLE_UNVERIFIED` with generic infra wording, `page 2` stays undemoted.
3. **`TestClampedUnverifiedTerminal`** — both tables get a high-confidence real PASS
   (the ladder alone would ACCEPT both), but the shifted table's SHIFTED markdown
   triggers the mechanical binding check (E1); CONSILIUM's clamp caps that table at
   `TABLE_UNVERIFIED` rather than letting the judge's PASS silently erase the mechanical
   evidence. Distinguished from scenario 2 by (a) the rung genuinely answering PASS
   (`S1` held) and (b) its audit-event wording containing "mechanical binding check
   found a contradiction the judge ladder's PASS did not address" — asserted directly
   against `state.events`, not inferred.

Every scenario also asserts the real rung's `prior_findings` argument to prove the
mechanical evidence actually composed with the ladder through the production code path
(`_run_table_judge_gate` → `run_table_ladder`), not a mock standing in for that wiring.

## Design choices / deviations

- **Scripted-by-content rungs, not queued rungs.** `_build_table_judge_rungs()` is
  called ONCE per document (`orchestrator.py:3207`) and its rungs are reused across
  every page/table in the loop. A queue-style fake (`_QueueRung`, the pattern used in
  `test_table_judge_gate.py`/`test_ladder_binding_evidence.py`, both single-witness-
  per-document files) would silently exhaust after the first table and raise on the
  second. `_ScriptedRung` instead keys its canned `RungResult` by the exact candidate
  markdown text handed to it, so one object safely serves both pages' tables.
- **CLI-summary capture via a `_phase_assemble` spy.** `process()` builds its
  `DocumentState` locally and does not expose it, but `_print_summary` (the CLI-summary
  surface) needs it. `_process_and_capture` wraps `_phase_assemble` (the only seam
  holding a state reference) to capture it as a side effect, then calls
  `_print_summary` on the captured state after `process()` returns — exercising the
  real production code path for both, not a re-implementation.
- **Candidate markdown built from the committed ground truth**, not hardcoded strings
  independent of it (`_md()` renders from `ground_truth.json`'s `cells`/`columns`/
  `row_labels`), so a future fixture edit cannot silently desync the test file's
  literals from the artifact.
- **Resume interaction intentionally left to D1b.** `tests/test_ladder_resume.py`
  already exhaustively covers REJECTED-skips / UNVERIFIED-reprocesses at the production
  seam (`_load_terminal_page`), including a fingerprint-invalidation case. Re-driving
  that through a full two-page `process()` run here would exercise the identical seam
  through strictly more machinery for zero new coverage — the ticket's own escape
  hatch ("if it inflates the ticket, note it as covered by D1b's tests and skip") was
  taken.
- One pre-existing gotcha (not a regression): `metadata.json`'s clean-run `status`
  field is `"completed"`, not `"success"` — fixed a wrong assumption in the first draft
  of the flag-off assertion (`meta_off["status"] != "partial"` instead of `== "success"`).
