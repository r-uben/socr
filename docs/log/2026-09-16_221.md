# 2026-09-16 — GH-221: a functional canary for the cascade-halt liveness probe

**Branch:** `fix/221-wedge-canary` (off `origin/main@3e04f1c`)
**Status:** DONE

## The defect

`probe_ollama_idle`/`probe_openai_server_idle` (`src/socr/tables/extract.py`) were a
`GET /api/tags` (Ollama) or `GET /models` (OpenAI-compatible) ping. The issue measured
that ping returning 200 OK in 0.05-0.14s while `qwen3-vl:30b-a3b-instruct` was
mid-generation at 100% GPU — the HTTP layer answers regardless of what the model is
doing, so the PP-2 cascade-halt guard (`_had_timeout and not probe_..._idle()`) never
armed for the exact failure it exists to catch.

## What changed

`src/socr/tables/extract.py`:

- `probe_ollama_idle`/`probe_openai_server_idle` now keep the existing `/api/tags` /
  `/models` request as a cheap precondition (unreachable host still fails fast, without
  paying for a generation call), then run a new functional canary:
  `_ollama_generation_canary`/`_openai_generation_canary`. Both send a minimal
  generation request (`num_predict: 1` / `max_tokens: 1`) against the *same model*.
  Ollama serialises `/api/generate` per model — a request sent while a prior one is
  still running queues behind it rather than returning, so this is the only thing that
  tells "HTTP alive" apart from "GPU available", which is exactly what the docstring on
  the old function already conceded it could not do.
- Both functions gained keyword-only `model: str | None = None` and
  `generation_timeout: float | None = None`. `generation_timeout` defaults to
  `_CROP_DEADLINE_FLOOR_S` (30s) — an existing named constant this file already uses to
  budget a normal crop read — rather than a new invented number (AC4). `model` defaults
  to `PROFILE_QWEN_LOCAL.model` (`socr.core.providers`), the repo's one supported local
  VLM, for callers with no reader instance to read `.model` off of.
- `_probe_reader_idle` (used inside `TableCropExtractor.extract`'s post-timeout branch)
  now passes the reader's own `.model` through, so that call site asks about the actual
  model that timed out rather than the generic default.
- Both probe functions are called ONLY from post-timeout paths — the orchestrator's
  `_probe_backend_idle` (itself only reached after `_had_timeout`) and
  `TableCropExtractor.extract`'s `except _CropTimeoutError` branch — so adding a
  generation call inside them does not touch the per-page happy path (AC3); this was
  verified directly, not assumed (see Verification below).
- **Review round 2:** the workload this canary guards (`TableCropExtractor`) is a
  VISION call, not a text one — every vision call in this codebase sends an
  `images`/`image_url` payload (`judge/ollama_judge.py`, `judge/table_rung_ollama.py`,
  `math/equation_latex.py`, `engines/gemini_api.py`). The first version of this canary
  sent a text-only `prompt`, which exercises a different code path than the one that
  wedges. The justification for the fix is a code-path argument, not a measured claim:
  **a probe must exercise the code path it guards, or it cannot detect a failure
  localised to the part it skips.** A hang confined to image decoding/encoding would
  pass a text-only canary while the vision path — the one `TableCropExtractor` actually
  uses — stayed jammed, reproducing GH-221's own failure class one layer down. (Note:
  a reviewer round cited a 2026-08-17 measurement and an `OLLAMA_NUM_PARALLEL` finding
  for this; neither is in this repo and I could not independently verify either, so
  this justification does not rely on them.) Fixed by adding a fixed, decoded 1x1
  transparent PNG (`_CANARY_IMAGE_B64`, 68 bytes) to both canaries' payloads — `images`
  for Ollama, an `image_url` message part for the OpenAI-compatible sibling. No new
  network dependency: the image is a module-level constant, never read from disk.

## Known, accepted characteristic (not a defect)

A cold model load was reported at ~37.5s in review notes, above the 30s
`_CROP_DEADLINE_FLOOR_S` default `generation_timeout`. If a cold load happens to start
exactly as the canary runs, the canary could read a genuinely-loading (not wedged)
backend as "not idle" and halt conservatively. This is judged low-probability — the
canary only runs after a crop already ran successfully enough to time out mid-response,
at which point the model is normally warm (`OllamaTableReader.timeout` is 120s+, far
longer than a cold load) — and the failure direction is safe: a false-conservative halt
loses no content (pages already flushed are kept, the run stops cleanly), unlike the
defect this ticket fixes, where a false-healthy probe let the pipeline keep firing into
a wedged GPU. Not treated as a threshold to invent a fix for; recorded here so a future
report of "GH-221's canary halted a run that was actually fine" has this as the first
thing to check.

`tests/test_gh222_probe_host.py`: the `recorded_urls` fixture now stubs `httpx.post`
(always-healthy) alongside the existing `httpx.get` stub, so GH-222's host-resolution
tests stay hermetic against the new generation call without changing what they assert.

`tests/test_gh221_generation_canary.py` (13 tests): wedged-vs-healthy detection for
both backends, a same-process pin-a-difference test, the AC3 no-happy-path-call test via
a real `TableCropExtractor.extract` run, AC4 (default timeout equals
`_CROP_DEADLINE_FLOOR_S`, override still honoured), AC5 (connection-refused fails closed
on both backends, and precondition failure short-circuits before the generation call),
one end-to-end test through `UnifiedPipeline.process()` that flips only the canary's
simulated response between two runs in the same process and asserts the cascade-halt
decision differs exactly as intended, and (review round 2) two tests asserting the
actual request payload carries an image (`images` for Ollama, `image_url` for the
OpenAI-compatible sibling) rather than text only.

## Known residual (not this ticket)

`probe_ollama_idle`/`probe_openai_server_idle`'s `model` default assumes the deployment
runs the one model this repo supports on the local rung. A deployment probing a
genuinely different model than the one that timed out (only possible via the
orchestrator's no-`model`-argument call site, since the reader-driven call site always
passes the real model) would canary the wrong model name. Threading the run's actual
configured model through `_probe_backend_idle` into these calls needs an
`orchestrator.py` edit, out of this ticket's `src/socr/tables/extract.py` +
`tests/` write ownership — flagging as a possible follow-up, not filing it unprompted.
