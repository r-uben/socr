# GH-35 Decision Log — Scanned over-count on sparse and full-page-figure pages

Date: 2026-06-15
Ticket: GH-35
Branch: feat/001-issue-plans
Files changed: `src/socr/core/born_digital.py`, `tests/test_born_digital.py`

## Problem summary

`BornDigitalDetector._assess_page()` had two early-exit guards in sequence:

1. `char_count < MIN_CHARS_FOR_TEXT_LAYER (50)` → immediately scanned
2. `word_count < MIN_WORDS_PER_PAGE (15)` → immediately scanned

The word-count gate fired before any text-quality checks ran. A born-digital
figure page with 10 clean words ("Figure 1. Impulse response function. Notes: 90%
confidence intervals shown.") was classified as SCANNED because 10 < 15, even
though the text was produced by proper fonts, had zero garbage characters, and
had normal word lengths. This caused OCR to run unnecessarily on these pages.

## Characterisation findings (pre-fix)

Confirmed via synthetic PDFs:

- Full-page-figure born-digital page (10 words, embedded image, Helvetica font):
  - Current verdict: SCANNED, reason: "too few words (10 < 15)"
  - Expected: born-digital

- Sparse section heading (7 words, 50+ chars, proper fonts):
  - Current verdict: SCANNED, reason: "too few words (7 < 15)"
  - Expected: born-digital

- True image-only scan (draw_rect, 0 chars, 0 fonts):
  - Current verdict: SCANNED, reason: "insufficient text layer (0 chars < 50)"
  - Remains correct

- Garbage OCR ("a b c d..." many single-char words):
  - Current verdict: SCANNED, reason: "avg word length too short (1.0)"
  - Remains correct

## Root cause

The word-count threshold (15) was originally a proxy for "bad OCR layer quality":
garbage baked-in OCR on scans tends to produce many single-character tokens with
low total word counts. That signal is now captured explicitly by the quality checks
(garbage ratio, word-length distribution, CID artifacts, font count). The word-count
gate had become redundant and was doing active harm on sparse born-digital pages.

## Fix design

**Approach**: Make the word-count gate quality-aware. It should only force a SCANNED
verdict when the text layer is also dirty. When the text passes quality checks, low
word count means "sparse born-digital" not "scanned".

**Implementation**:

1. Moved quality-signal computation (`garbage_ratio`, `space_ratio`, `avg_word_len`,
   `has_cid`) to BEFORE the word-count check (was after). No duplication — signals
   are computed once and reused in subsequent quality gates.

2. Added `text_layer_is_clean` predicate:
   - no CID artifacts
   - garbage_ratio <= MAX_GARBAGE_RATIO
   - MIN_AVG_WORD_LENGTH <= avg_word_len <= MAX_AVG_WORD_LENGTH
   - font_count > 0 (page has at least one embedded font)

3. Word-count gate restructured:
   - If `word_count < MIN_WORDS_PER_PAGE` AND (`not text_layer_is_clean` OR
     `word_count < MIN_WORDS_SPARSE`): classify as SCANNED as before
   - Otherwise (clean short text, >= MIN_WORDS_SPARSE words): fall through to
     born-digital path with a "sparse native layer" note for audit visibility

4. Added `MIN_WORDS_SPARSE = 3` class constant — absolute floor for clean text.
   Basis: a figure caption or heading is at minimum a number + noun phrase (e.g.,
   "Figure 1." is 2 tokens — we require 3 to avoid rescuing lone watermarks or
   page-number stubs as meaningful content).

## Threshold rationale

`MIN_WORDS_SPARSE = 3`: The lowest realistic meaningful native text on an academic
page is a section number and a title word or two (e.g. "3. Methodology"). Below 3
words (combined with short char count), the content is almost certainly a stray
artifact, page number, or watermark — not a sparse section heading. This threshold
is conservative; the quality checks do the real discrimination.

`MIN_CHARS_FOR_TEXT_LAYER = 50`: Unchanged. This hard gate catches pages with
trivially short text (<50 chars) regardless of word count. Some chapter headings
(e.g. "Chapter 3\nEmpirical Methodology\n" = 32 chars) fall below this and remain
non-born-digital. This is intentional — such pages contain so little content that
native extraction produces nothing useful. Lowering this threshold would require
corpus validation; deferred.

## Dangerous direction: real scan misclassified as born-digital

The risk is: a scanned page with baked-in short OCR (5-14 words of decent quality)
could now be classified as born-digital, skipping OCR.

**Assessment**: This risk is real but bounded. For a scanned page to slip through,
all of the following must hold simultaneously:
- The baked-in OCR produced >= MIN_WORDS_SPARSE (3) words
- No CID artifacts (high-quality baked-in OCR)
- Low garbage ratio (< 5%)
- Normal average word length (2.5–20 chars)
- At least one font is embedded (true of any baked-in OCR layer)

In this edge case, the baked-in OCR text IS the best available text for the page —
re-running OCR might not produce better output. The practical impact is therefore
limited: we use the baked-in OCR text as the native text, which is typically correct.

The truly dangerous case (scan with zero quality OCR layer) continues to be caught by
the quality checks (CID, garbage ratio, word length) and the char-count gate.

**Residual risk**: A scan with a high-quality short baked-in OCR layer (5-14 clean
words) will now be classified as born-digital. This is the remaining ambiguity
between "sparse born-digital" and "sparse scanned+OCR" that cannot be resolved
without corpus-level evidence. Given the bounded impact (short pages, baked-in OCR
text is used as-is), the tradeoff is acceptable.
