# GH-172 — killable boundary for a wedged provider: panel + measurement

## The fork

`agentic.py:260` states it, and defers it: a soft timeout calls `future.cancel()` +
`ex.shutdown(wait=False)`, but ThreadPoolExecutor workers are non-daemon and cannot be made
daemon after start, so the interpreter joins a wedged worker at exit. The CLI can outlive its
own reported timeout indefinitely. The code names two exits — bound the client timeout (A), or
move to a killable process boundary (B) — "tracked on #172, not done here." A third, a hard
`os._exit` watchdog (C), was added for the panel.

## The measurement that decides it

Option A was the cheap exit, so it was tested before any opinion was taken. A local stub server
sent one byte every 0.3s against an httpx client with `Timeout(1.0)`:

    read timeout = 1.0s; server sends a byte every 0.3s
    -> no ReadTimeout; the call was still alive at 12.2s, ending only when the stub stopped

**httpx's read timeout is an inactivity bound per received chunk, not a total-response deadline,
and httpx exposes no total-request deadline.** A peer that supplies a chunk before each read
interval — including SSE keepalives — runs forever. The precise distinction, which the GPT seat
derived independently before seeing this measurement: a server that sends NOTHING is caught by
`ReadTimeout`; the defeating case is an indefinitely open response that keeps supplying chunks.

So **A cannot meet acceptance criterion 1.** It closes the slow-provider case, which was already
bounded, and leaves the wedged case — the one the soft timeout exists for — untouched.

## Ruling — CONTESTED, pending the third seat

The first seat (GPT) ruled **B**. The second (Kimi) ruled **A+C** and called B disqualified on
cost. The third seat (Gemini) died at spawn on a transport error and was replaced. This section
records the split honestly rather than asserting the first answer received.

### What the dissent got right, verified

My own rejection of C rested on "os._exit can cut a parent mid-write". That does not hold here:

- **Page writes are main-thread.** `_phase_agentic`'s page loop is serial
  (`for page_num, ps in sorted(state.pages.items())`); workers only POST HTTP.
- **Fragment writes are already atomic** — `_flush_page_fragment` writes `.md.tmp` then renames,
  and says so in its docstring.

So `os._exit` from the MAIN thread, after a flush returns, cannot truncate a page. That ordering
is the load-bearing invariant and must be stated in the code if C is taken.

**B also costs more than the first seat implied.** Measured: Python 3.11.14 here, and
`ProcessPoolExecutor.terminate_workers` does not exist (added in 3.14). A pool cannot kill a
wedged worker, so honest B is raw `multiprocessing.Process` + `terminate()` + IPC — a larger diff
than A+C combined.

### The placement point neither the first seat nor I raised

The wedged-worker check must run at process **teardown, unconditionally** — not only on the
cascade-halt path. A document can COMPLETE with an abandoned wedged worker: the timeout escalates,
every page saves, and the process then hangs at interpreter exit with no work left. Criterion 1
fails there under ANY option unless teardown is covered. This is probably the common case, not the
exotic one.

### Not in dispute (both seats, and the measurement)

- **A alone cannot meet criterion 1.** Measured: one byte per 0.3s against `httpx.Timeout(1.0)`
  never raised; the call was alive at 12.2s. httpx's read timeout is an inactivity bound per
  received chunk and httpx has no total-request deadline. A silent socket IS caught; a
  bounded-rate trickle (inter-byte gap < read timeout) is not.
- Criterion 2 does NOT require B — process death terminates the underlying request. B must not
  win on a wording technicality.
- Closing the socket from a watchdog thread does not reliably interrupt a blocked `recv` on POSIX;
  nobody should propose that as a cheaper C.
- Any grace constant must be named and derived (the repo accepts the shape of
  `tables/extract.py`'s documented headroom multiplier), never guessed.

### FINAL RULING (all three seats in, plus measurement)

**B for the deadline. C only as a post-durable-write reaper. A is defence-in-depth and never
the close.**

Seats: GPT ruled B. Grok ruled B first, with C legal only after flush+assemble return. Kimi ruled
A+C, disqualifying B on cost. Two of three for B; all three agree A alone fails criterion 1, which
the measurement settles independently.

Kimi's dissent is not discarded — it is absorbed. Its teardown insight (a COMPLETED document can
hang at exit on a zombie worker) is real and neither other seat raised it. It becomes the reaper's
job, not the deadline's.

**Why B and not A+C, despite B costing more:** C cannot fire the deadline without risking a write.
Both Grok and the cardinal rule land in the same place — `os._exit` is legal only once durable
writes have returned. A deadline mechanism that must wait for durable writes is not a deadline
mechanism. So C reaps; B bounds.

**B is cheaper than the first seat implied, because half of it already exists.** Verified:
`engines/base.py` already runs CLI engines under `subprocess.run(..., timeout=config.timeout)` —
killable, but bounded by the DOCUMENT timeout (`config.timeout = 1800`), not the soft deadline.
The CLI half of B is tightening that kill. Only the httpx-in-thread callers (judge, crop, vllm,
gemini-api) need a new boundary, because there is no child to kill there today.

Scope, per Grok, verified against the tree: `route_page`, `_TimeoutJudge.assess`,
`_escalate_table_page`, `_read_with_deadline`. Wrap ONLY the model call — never the flush or
sidecar write. `spawn`, not fork (fork-after-threads is unsafe on macOS). Pickle call args, not
`UnifiedPipeline`.

**A is not a small tighten, and must not be blanket-applied.** Verified:
`_CROP_WALL_CLOCK_MULTIPLIER = 2.0` sets the crop thread deadline at 2x the httpx reader timeout
DELIBERATELY, so httpx fires first. Bounding client-by-soft would reverse that design and still
miss trickle.

**Existing pin:** `tests/test_gh172_abandoned_worker_exit.py` already exists and stays as the
"threads cannot do this" pin. The new test must be a CHILD-CLI test — the claim is about process
exit and cannot be observed from inside pytest.

**The load-bearing test mode is the trickle**, not the silent socket. A silent-open server is
caught by the read timeout, so a test using only that mode would pass under A and leave #172 open.

### Superseded: open question for the third seat

Whether the teardown guarantee is worth a raw-multiprocessing boundary (B) or whether a
main-thread forced exit after flush (C) buys the same guarantee at a fraction of the diff.

**B, with A as defence in depth. C is rejected.**

`os._exit` can skip buffered output and cut a parent mid-write. This repo flushes completed pages
and per-page sidecars on cascade-halt; a truncated page that looks terminal would corrupt resume.
A grace period that cannot be derived from a real upper bound is also a magic number. C trades the
cardinal rule for convenience.

### Constraints on B (from the panel, not optional)

1. **The child never owns durable writes.** Page-ledger, fragment, manifest and document-status
   writes stay in the parent. The child computes; the parent persists. Only after the child is
   confirmed gone does the parent record the typed timeout and flush synchronously.
2. **Kill the process GROUP, not the worker.** Otherwise provider grandchildren survive.
3. **`ProcessPoolExecutor.shutdown(wait=False)` reproduces the original bug** — it joins too.
   The boundary must be explicitly terminated, bounded-joined, then killed.
4. Pickling: existing closures/stateful clients are not picklable. Define a top-level serialisable
   call spec + result and isolate only the external operation.
5. Killing the local client does NOT cancel server-side generation. It guarantees socr exits —
   that is the whole claim, and the log must not overstate it.

### In-repo precedent

`engines/vllm_manager.py` already does exactly this: `preexec_fn=os.setsid` at spawn, then
`os.killpg(pgid, SIGTERM)` → bounded wait → `os.killpg(pgid, SIGKILL)`. Follow that shape.
**Do not copy its bare `timeout=10` / `timeout=5`** — those are magic numbers and violate this
repo's own rule. Name and derive the grace constants.

## Hermetic CI test (no provider, no GPU, no ollama)

Child `socr` CLI against a loopback stub: page 1 returns normally, page 2 sends headers then
trickles bytes faster than the read timeout, forever. Assert the CLI exits within an outer bound
derived from the configured deadline plus the bounded terminate/kill joins; assert the timeout is
typed and surfaced at CLI, document status and metadata; assert the wedged page is NON-terminal
and page 1's fragment + terminal sidecar are intact and resumable. Add a child/grandchild stub to
prove the kill is process-group-wide.

**Mutation guard:** restore the thread-abandonment path and require the child test to hit its outer
timeout. A test that passes with the fix reverted proves nothing.

## Implementation (this ticket, 2026-09-17)

Delivered a smaller slice than the full four-site boundary, per the ticket's own scope-discipline
clause: **the primitive, plus two of the four named sites.** What each site actually needed
differed once measured, so the shape isn't uniform across all four — see "What's deferred" below
for exactly which are still open and why.

### The primitive: `src/socr/core/killable.py`

`run_killable(CallSpec, timeout=...)` — `multiprocessing.get_context("spawn")`, `os.setsid()` in
the child so it becomes its own process-group leader, `os.killpg(pgid, SIGTERM)` → bounded
`proc.join()` → `os.killpg(pgid, SIGKILL)` on timeout (ruling constraints 2 & 3). `CallSpec` is an
import-path + plain-picklable-args description (constraint 4) — never a closure. The child sends
only `("ok", result)` or `("error", type_name, message)` over a `Pipe`; nothing it computes is
durable until the parent receives and persists it (constraint 1). `KillableTimeoutError` subclasses
the builtin `TimeoutError`, so `socr.judge.judge.is_page_judge_timeout()` — which already
classifies by exception type — picks it up with zero new wiring at any judge call site.

An `atexit.register(_reap_stragglers)` at import time is the panel's absorbed dissent: the case
where a document COMPLETES with a `run_killable` child still alive (a caller drops the process
without waiting, or crashes between start and join) has no cascade-halt latch to clean it up. This
fires only once the interpreter's normal shutdown sequence has begun — i.e. after every caller's
own `main()` body, including `_phase_agentic`'s per-page loop and `_phase_assemble`, has RETURNED —
so it is a reaper (legal per the ruling), never a deadline.

Grace constants: `DEFAULT_TERM_GRACE_SEC = DEFAULT_KILL_GRACE_SEC = 3.0`, derived (not copied from
`vllm_manager.py`'s bare `timeout=10`/`5`) as `_INTERPRETER_TEARDOWN_BUDGET_SEC (1.0) *
_GRACE_MULTIPLIER (3.0)` — enough headroom for CPython's own atexit/socket-close teardown in the
child to finish without racing the SIGKILL escalation.

### Site 1 — `OllamaVisionJudge.judge()` (`src/socr/judge/ollama_judge.py`)

The httpx `POST /api/generate` call — the only externally-blocking part of `judge()` — is now
`run_killable(CallSpec("socr.judge.ollama_judge:_post_generate", (host, model, prompt, image_b64,
timeout)), timeout=self.timeout)`. `_post_generate` is a new top-level function (the extracted
httpx call) so it's a valid `CallSpec` target. No changes needed in `_TimeoutJudge.assess`,
`route_page`'s judge-exception handling, or the `#713` credentialed-stand-in gate — they already
key on `TimeoutError`/`is_page_judge_timeout()`, and `KillableTimeoutError` satisfies that for
free.

### Site 2 (the cheap CLI half of B) — `engines/base.py` + `orchestrator.py`

`BaseEngine.process_pages()` gained `subprocess_timeout: float | None = None`; when given, it
overrides `config.timeout` as the bound on the existing `subprocess.run(cmd, timeout=...)` call
(already a real killable boundary — CLI engines are subprocesses — just bounded by the 1800s
whole-document timeout, not the soft per-provider deadline). `_run_engine_on_pages()` in
`orchestrator.py` threads a new `subprocess_timeout_sec` parameter through to this call;
`_phase_agentic`'s `run_provider` closure now passes `provider_timeout.get(profile.engine)`. This
directly tightens the wedge window for `QwenEngine` (the primary local-model path), which is
CLI-subprocess-based, not httpx-based.

### What's deferred — and why this is not the full ticket

The ticket names FOUR sites for the process boundary: `route_page`, `_TimeoutJudge.assess`,
`_escalate_table_page`, `_read_with_deadline`. Only the httpx call inside the judge path
(`OllamaVisionJudge.judge()`, which `_TimeoutJudge.assess` calls into) is now killable-bounded.
**`route_page`'s own `ThreadPoolExecutor` + `future.cancel()` + `shutdown(wait=False)` pattern is
UNCHANGED** — httpx-based provider engines reached through it (`gemini_api.py`'s
`GeminiAPIEngine`/`OllamaFigureEngine`/`LocalFirstFigureEngine`, `vllm.py`'s `VLLMEngine`) remain
exposed to the original defect this ticket is titled after. `_escalate_table_page` (table
escalation, `orchestrator.py` ~5614) and `_read_with_deadline` (crop reread, `tables/extract.py`
~612) are also unchanged.

Why: each of those three closures captures heavy, non-picklable state — bound methods on
`UnifiedPipeline`/engine instances, PIL `Image` objects, live pipeline config — that would need a
real refactor (isolate the external call into a top-level function, pass only picklable
arguments) to cross the `spawn` boundary, not a small patch. Attempting all four in one pass risked
either a rushed, under-tested change to the four riskiest call sites in the pipeline, or (worse) a
synthetic test that exercises a reimplementation of the closure rather than the real one — I
already caught and deleted one such test for `run_provider`'s CLI-timeout wiring during this pass
(see "Test-coverage gap" below). The ticket's own scope-discipline clause explicitly permits
delivering the smallest working slice with deferrals named, over delivering A (client-timeout
bounding) dressed up as B.

**Follow-up ticket needed:** apply the same `CallSpec`/`run_killable` pattern to `route_page`
(isolate each provider engine's own external call — `GeminiAPIEngine`/`VLLMEngine`/
`OllamaFigureEngine` — behind a top-level, picklable call site the way `_post_generate` isolates
the judge's), then to `_escalate_table_page` and `_read_with_deadline`. `route_page` is the
highest-value remaining site: it is the one directly in the hot path of every OCR page, not just
judge/table escalation.

### Test-coverage gap disclosed

`tests/test_gh172_cli_subprocess_timeout.py` proves `engines/base.py`'s tightened
`subprocess.run(timeout=...)` in isolation (stubbed `subprocess.run`); it does NOT exercise
`_phase_agentic`'s real `run_provider` closure threading `subprocess_timeout_sec` through
`_run_engine_on_pages` end to end. An attempted third test for that wiring reimplemented the
closure's logic rather than driving the real one — a tautological test — and was deleted rather
than kept as a fake pass.

Required-evidence item 1 (a full child `socr` CLI test: real PDF, real CLI entrypoint, loopback
stub, page-1-clean/page-2-trickle, asserting CLI exit + typed timeout at every surface + page-1
resumability + process-group-wide kill of a grandchild) was NOT built. What stands in its place:
`tests/test_gh172_judge_killable.py::test_judge_call_exits_in_a_child_process` gives the same
CHILD-PROCESS-observed-from-outside evidence form the ticket requires, but at the judge call site
directly rather than through the full CLI/pipeline stack, and
`tests/test_gh172_killable_boundary.py::test_kill_is_process_group_wide` proves the
process-group-wide kill generically. Building the true end-to-end CLI test requires either (a) a
real local ladder + VLM judge backend pointed at a loopback stub via CLI args, or (b) `route_page`
itself wired to `run_killable` (deferred above) so a wedged PROVIDER, not just a wedged judge, is
what the CLI test demonstrates recovering from. Both are follow-up work.
