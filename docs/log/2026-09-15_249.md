# 2026-09-15 — GH-249: gate the native table verifier on a grid

**Branch:** `fix/249-verifier-grid-gate-v2` (off `origin/main@8bf34d5`)
**Status:** DONE (see caveat on criterion 1 below)

## What changed

`native_verifier._verify_from_words` went straight from lane detection into `_value_guard`,
without ever checking whether the native "rows" actually establish a table grid —
`orchestrator.py:5443` already gates `table_not_scorable` on
`socr.core.table_grid.rows_establish_grid`, but the verifier never called it. So a chart
page's axis tick labels were graded as a native table: every ladder rung got rejected against
that phantom, and a verbatim tick-dump shipped instead.

Added a gate in `_verify_from_words`, inserted right after `lane_count`/`lane_of` are computed
and the `lane_count == 0` early return, before `_value_guard` is reached:

```python
if lane_count >= 2:
    grid_rows = _header_excluded_native_rows(words, output_text)
    if not _native_rows_establish_any_grid(grid_rows):
        result.reason = (
            f"native_grid_gate: {len(grid_rows)} native row(s) in [{scope_label}] "
            f"(across every contiguous y-block) do not establish a table grid "
            f"(need >= 2 value columns shared by >= 2 rows) — likely chart axis "
            f"ticks or prose, not a native table; abstaining rather than grading "
            f"candidates against it"
        )
        logger.debug("native_verifier [%s] grid gate: %s", scope_label, result.reason)
        return result
```

Supporting helpers (`native_verifier.py`): `_header_excluded_native_rows`,
`_native_row_clusters` (splits native rows into contiguous y-blocks, gap threshold
`_YBAND_ROW_HEIGHT_CAP_PT` = 30.0pt — the same existing constant already used by
`_effective_native_rows_for_output`, not a new one), `_native_rows_establish_any_grid` (True
iff ANY contiguous y-cluster satisfies `rows_establish_grid`), and
`_effective_native_rows_for_output` (pairing-derived y-band scoping, used only inside
`_value_guard`, unchanged by this ticket).

No second predicate was written — `rows_establish_grid` is reused as-is, imported from
`socr.core.table_grid`. No new magic threshold.

### Why `lane_count >= 2` gates the call, not an unconditional call

`rows_establish_grid` requires `modal_width >= 2` (>= 2 value columns) AND `rows_at_modal >= 2`.
A single-numeric-column table (criterion 3) has `lane_count == 1` and can *never* satisfy that
predicate, no matter how many genuine data rows it has — the predicate is mathematically about
column-width agreement, not row count. PR #444 called `rows_establish_grid` unconditionally and
that is exactly what broke single-column tables (its own review finding 2). Gating the call on
`lane_count >= 2` at the call site is the actual fix for that finding: below 2 lanes, the grid
gate never fires and the value guard runs as before.

## The lane_count == 1 nuance (criterion 1 caveat)

A genuine axis with a single stacked column of tick numbers (one numeral per row, all in one
x-lane) is geometrically indistinguishable from a single-numeric-column table — both have
`lane_count == 1`. Under the `lane_count >= 2` gate this case is *not* hard-abstained; it falls
through to `_value_guard` as before. Measured directly: a "correct" (no-table) candidate scores
`AMBIGUOUS` (row-count warn, no hard fail); a "tick dump" candidate scores `EXACT_PASS` — an
asymmetry in confidence, not a clean abstain-with-reason.

This is not a gap introduced by this change; it is the same geometric ambiguity that protects
criterion 3, applied honestly to its symmetric case. Criterion 1 is fully met for lane_count >= 2
axis geometries (a horizontal row of well-separated numeric labels, e.g. year ticks along an
x-axis) — the case the ticket's own wording ("does not reach `_value_guard`") is written for and
the realistic shape of a chart's axis-tick strip. `test_single_lane_axis_column_is_not_hard_failed`
documents the lane_count == 1 behavior explicitly so it stays visible, not silently assumed away.

before this gate, since nothing checked for a grid). Under the gate, `lane_count >= 2` +
1 row no longer establishes a grid, so those tests now abstain instead of exercising
`_value_guard` — silently turning them into vacuous passes rather than failures, which would
have hidden the very criterion-4 regression this ticket exists to prevent. Fixed by adding a
genuine second data row (native + matching output) to each, preserving each test's original
intent:

- `tests/test_agentic.py` —
  `test_rectangular_intact_header_but_multiset_mismatch_rejects_via_tr3`: added a second clean

- `tests/test_gh259_flagged_model_table_wins.py` — 3 tests. The hardest was

## Addendum, same day — REVISE round: `_native_row_clusters` used the wrong quantity as its threshold

**Correction to the numbers reported above:** `tests/test_native_table_verifier.py
tests/test_agentic.py` collects 90 tests, not 128 — result is **89 passed, 1 xfailed**, not
"128 passed, 1 xfailed" as first reported. Re-run and confirmed below.

### The bug (reviewer-found, reproduced independently)

`_native_row_clusters` split native rows into contiguous y-blocks by comparing each consecutive
gap to `_YBAND_ROW_HEIGHT_CAP_PT` (30pt) — a constant defined elsewhere in this file as a
*ceiling on a row-height ESTIMATE derived from matched output/native pairs* (the TR-6 y-band
margin in `_effective_native_rows_for_output`), not an absolute inter-row spacing threshold. A
genuine 2-row table with 60pt row spacing (or any spacing > 30pt) got split into two 1-row
clusters at the grid-gate site; neither cluster can satisfy `rows_establish_grid` (needs >= 2
rows), so the gate abstained on a REAL table and a dropped value shipped unreported — the exact
silent-corruption mode GH-249 exists to close, reopened via a different code path.

Reproduced directly (organic 47.5pt row pitch, not a multiple of 30):
```
OLD clustering -> hard_fail=False, reason="native_grid_gate: ..."   <- false negative
NEW clustering -> hard_fail=True,  reason="...multiset_mismatch..." <- correct
```

### The fix

`_native_row_clusters` now derives its boundary from the row set's OWN geometry rather than a
borrowed constant: the smallest consecutive y-gap among the rows being clustered is the best
available estimate of that block's own row-to-row rhythm (a real table's rows recur at
approximately one spacing); a gap counts as a cluster boundary only once it exceeds that local
minimum by more than a new `_ROW_CLUSTER_GAP_MULTIPLE`. That multiple is itself not a fresh
pick — it is defined as `_YBAND_ROW_HEIGHT_CAP_PT / _YBAND_SINGLE_ROW_HEIGHT_PT` (== 2.0), the
ratio already implicit between this file's two existing row-height constants.

Rows sets with fewer than 2 gaps (<= 2 rows) have no reference spacing to compare against and
are kept as one cluster unconditionally. This directly fixes the reported bug for ANY spacing:
a 2-row table — the minimal real-table shape the gate must protect — can never be fractured by
this function.

**Disclosed trade-off** (same shape as the lane_count == 1 disclosure already in the ticket):
with only one gap available, there is no internal reference to call it an outlier by, so two
widely-separated native rows that happen to share a lane count are pooled and graded as one
table's rows, rather than split apart. `test_widely_separated_two_row_table_narrowing_is_disclosed`
pins this explicitly rather than leaving it an unstated assumption.

### New tests (`TestGH249RowClusterGapIsSelfDerived` in `tests/test_native_table_verifier.py`)

## Round 3 — CI caught a regression the local sweeps missed (2026-09-15)

`bb51894` was pushed as PR #756. **CI failed**; the merge gate refused and nothing
reached `main`.

**Failure:** `tests/test_gh262_d3_marker_over_cached_grid.py::test_a_certain_fail_leaves_no_disposition_behind`
— expected `accept=False`, got `accept=True, reason='inner judge'`.

**Mechanism.** The fixture is ONE native row with THREE lanes, and an output shipping
only the first value — two numbers dropped. `lane_count >= 2`, so the gate ran; a single
row can never satisfy `rows_establish_grid` (it needs >= 2 rows); so the verifier
**abstained**. It returned a reason but no `hard_fail`, and downstream that absence let
the inner judge's `accept=True` stand. A page that dropped two of three numbers shipped
accepted — inverting this repo's cardinal rule that a wrong or dropped number is worse
than a missing one.

This was the SECOND instance of one class. The review finding (round 2) was the gate
abstaining where it should hard-fail at >30pt row pitch; this is the gate abstaining
where it should hard-fail at one row. **In this pipeline abstention is not neutral — it
reads downstream as permission.** The gate fired on *absence of evidence of a grid*, and
absence of evidence was being converted into consent.

**Fix.** The gate now requires `len(grid_rows) >= 2` before it may act, mirroring the
existing `lane_count >= 2` reasoning. One row is not evidence of chart-ness, merely too
little geometry for a native-only predicate to judge; below two rows the value guard's
own multiset/pairing checks remain the sole authority, exactly as before this gate
existed.

**Why local verification missed it.** Both the implementer and the orchestrator ran
`-k "table or native or agentic"`. That filter deselected 82 of the 106 tests in the
failing file, including this one. The failure reproduces locally in 0.12s — it was never
an environment difference, only an unrun test. Full-suite runs, not keyword subsets, are
the gate for this ticket class.

**Cost of this one issue:** 3 implementer passes, 1 adversarial review, 2 orchestrator
verification rounds, 1 CI catch. Each layer caught a distinct class the previous missed;
none was redundant.
