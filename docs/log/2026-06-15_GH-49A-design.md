# GH-49A — Native table verifier before VLM judge on born-digital pages (design)

Date: 2026-06-15
Branch: `feat/49-structured-content-routing`
Status: design note for consilium gate (no production code written)
Author agent: socr-designer (read-only)

## Scope recap

The extract / verify / escalate layering is already settled. GH-49-routing (commit
`46f4b86`) landed the *routing* layer: born-digital pages with `has_tables` now enter the
OCR/VLM ladder instead of being trusted as clean native prose, and a rejected table page is
marked `native_table_structure_failed` so the manifest cannot mask it as a clean pass.

GH-49A is the **verify** layer for born-digital tables only: a *deterministic, no-model*
check that runs on a born-digital table page **before** the expensive VLM judge call, so a
cheaply-detectable structural defect (notably sparse comparison-row lane drift, GH-46-D2)
can fail/escalate without paying for a second model. It must emit a warning/fail signal and
must never silently rewrite cells.

---

## 1. What exists today

### Routing → ladder → judge path

- Born-digital table predicate: `UnifiedPipeline._page_has_tables()` at
  `src/socr/pipeline/orchestrator.py:1025` (reads `ps.has_tables`, set from
  `DocumentAssessment` via the born-digital detector).
- Agentic per-page loop: `_run_agentic()` calls `route_page(...)` at
  `src/socr/pipeline/orchestrator.py:1205`, with the judge built by `_build_page_judge()`
  (`orchestrator.py:1512`).
- The ladder loop is `route_page()` at `src/socr/pipeline/agentic.py:140`. For each rung it
  runs the provider, then calls `judge.assess(output, prof)` at `agentic.py:268`; the first
  `accept=True` wins, otherwise it escalates.
- The **second-model cost** lives entirely in `VLMPageJudge.assess()`
  (`agentic.py:337`): it renders the page to PNG and calls
  `self._judge.judge(image_path, output.text)` — the only model call in the verify path.
  The fallback judge `HeuristicPageJudge.assess()` (`agentic.py:310`) is already
  deterministic but text-only.
- Provenance guard already present: after a full-ladder rejection on a table page,
  `orchestrator.py:1233` sets `ps.native_table_structure_failed = True`.

**Insertion point for GH-49A:** a deterministic table verifier should run *inside the judge
decision*, ahead of the VLM call, only for born-digital table pages — i.e. a wrapper judge
(or a pre-check branch in `_build_page_judge`) that short-circuits to escalate/fail when the
native geometry says the OCR output is structurally wrong, and otherwise delegates to the
existing VLM/heuristic judge. This satisfies AC4 ("before VLM judge escalation") without a
parallel router (Plan step 4).

### Native geometry actually available (confirmed, not assumed)

PyMuPDF is already used this way in-repo, so these signals are real:

- `page.get_text("words")` → tuples `(x0, y0, x1, y1, word, block, line, word_no)`. Used
  today in `src/socr/tables/reconstruct.py:119`.
- **Numeric-lane clustering already implemented**: `has_numeric_columns(page)` at
  `src/socr/tables/reconstruct.py:110` clusters numeric-token x-positions into lanes
  (tolerance `_LANE_X_TOL_PT = 6.0`) and counts rows that co-occupy `>= _MIN_LANES_PER_ROW`
  lanes. This is exactly the header-lane geometry GH-49A needs, and it is *already* the gate
  before the expensive text-strategy table reconstruction.
- `page.find_tables()` (lines) and `page.find_tables(strategy="text")` recover real grids;
  `reconstruct_table_regions()` (`reconstruct.py:71`) already produces a char-exact native
  markdown grid for booktabs tables. `page.get_drawings()` (ruling vectors) is used by
  `src/socr/tables/locate.py:176`.
- Scanned pages: `get_text("words")` is empty / `get_drawings()` is empty on a true scan
  (documented at `src/socr/tables/locate.py:91` and `image_locate.py:3`). So "no native word
  geometry" is a clean, deterministic bypass for AC3 — and `_page_has_tables` is already
  `has_tables`-gated to born-digital pages only.

### Existing audit/heuristic plumbing the verifier should reuse (not reinvent)

- `HeuristicsChecker.check_native_table_structure(text)` at
  `src/socr/audit/heuristics.py:289` and `_native_table_structure_failure_reason(text)` at
  `:327`. **Important — what this actually checks vs. what the ticket assumes:** this
  inspects only the *output markdown text* (collapsed rows, glued numerics, single-cell
  flat streams). It does **not** compare the output against the page's native column
  geometry. GH-49A's novel signal — native header-lane geometry vs. OCR cell placement —
  does not exist yet. The verifier *extends* this metric, it does not duplicate it.
- Result/severity model: `AuditMetric(severity="error"|"warning"|"info")` +
  `HeuristicsResult.add_metric()` (`heuristics.py:27`) already drive accept/fail. The metric
  name constant `NATIVE_TABLE_STRUCTURE_METRIC` (`heuristics.py:41`) is the natural label.
- Audit events: `AuditEvent` / `RunAudit` in `src/socr/core/audit_log.py:43` is where a
  verifier failure should be recorded (AC4) with page number + reason + lane geometry
  context.

### Known failure mode to catch cheaply (GH-46-D2)

Sparse comparison-row lane drift: a lone value (e.g. a standard error `(0.014)` on its own
row, or a single summary-row figure) slides into an adjacent column lane. GH-46-D2 shipped a
*prompt-only* mitigation (`src/socr/prompts/table_extract.md:22`, "Column-lane anchoring")
with manual VLM validation still pending. This is catchable from native geometry: the native
header lanes define the canonical x-positions; if an OCR cell's value maps to a native lane
index different from the column it was emitted under, that is a deterministic drift signal —
no second model needed (AC2).

## 2. Options for the deterministic verifier

All options: deterministic PyMuPDF-only, emit a `warning`/`error` `AuditMetric` (reusing
`check_native_table_structure`'s result shape) + an `AuditEvent`; on `error`, escalate the
ladder rung / set `native_table_structure_failed`; **never rewrite cells**. All run only when
`get_text("words")` is non-empty (scan bypass). Any needed tolerance is named/derived/config,
never a bare literal — reuse `_LANE_X_TOL_PT` and the `reconstruct` lane constants.

### Option A — Header-lane / x-position consistency (lane-count + lane-occupancy)

Cluster native numeric tokens into lanes via the existing `has_numeric_columns` machinery to
get `native_lane_count`. Parse the OCR output grid (markdown columns, already handled by
`_native_table_structure_failure_reason`) to get `output_col_count` and, per data row, the
number of populated cells. **Fail/warn** when:
- `output_col_count` differs from `native_lane_count` beyond a named tolerance, or
- a meaningful share of native multi-lane data rows collapsed to a single output column.

- Cost: ~free (one `get_text("words")` pass already done at detection time; lane clustering
  is O(words)). Determinism/replay: fully deterministic; no model, no network.
- False-positive risk: **moderate.** Native lane count ≠ visual column count when columns
  share an x-band (paired (year/year), spanning headers, stub column with no numbers). Must
  count *lanes* not assume one-lane-per-column, and only fail on large mismatch.
- Scope: directly targets AC2 (catches the sparse case by lane-count shrink). Smallest new
  surface; mostly reuses `reconstruct.has_numeric_columns`.

### Option B — Per-value numeric-cell lane assignment (true drift detection)

Go beyond counting: for each numeric value in the OCR output, find its native token
(by value match) and check that the native token's x falls in the **same lane index** as the
output column it was placed under. A value whose native lane index ≠ its output column index
is *drift*. **Fail** when any value (or > a derived share) is lane-mismatched.

- Cost: still free-ish (token value matching is O(values); same single native pass).
- Determinism/replay: deterministic. Strongest at catching GH-46-D2 lane drift precisely
  (AC2) — it is the only option that localizes *which* value drifted, giving the richest
  audit context (AC4).
- False-positive risk: **higher.** Value-matching is ambiguous when the same number repeats
  across columns (e.g. `1,204` `N` row across all specs), and OCR may legitimately reformat
  values (`0.31` vs `.31`, thousands separators). Mismatches from formatting, not geometry,
  would false-fail a correct table. Needs careful value normalization + "only fail on
  unambiguous, repeated-row drift" guards — more logic, more risk.

### Option C — Row-cell-count vs header-column-count reconciliation (output-shape only)

Derive the header/native column count, then check every output data row has a compatible
cell count (already partially done in `heuristics.py:481` `aligned_rows`). Extend the
*existing* `_native_table_structure_failure_reason` to take an optional
`native_col_count` hint and fail when many rows disagree with the native column count.

- Cost: free; smallest code change (extend an existing function signature).
- Determinism/replay: deterministic.
- False-positive risk: **low**, but **weak coverage**: a drifted value still produces the
  *right cell count* (the value just sits in the wrong lane), so Option C alone does **not**
  catch GH-46-D2 — it catches collapse/merge, which `check_native_table_structure` already
  largely catches. It would barely move AC2.

## 3. Recommendation

**Option A, with the per-value drift localization of Option B added only as the audit-context
enrichment when A has already flagged a row** — i.e. lane-count/occupancy as the *fail
signal* (cheap, lower false-positive), and value-to-lane mapping used *only to describe* the
offending row in the audit event, not as an independent fail trigger. This:

- catches the GH-46-D2 sparse lane-drift case via lane-occupancy shrink (a drifted lone value
  changes which lanes a sparse row occupies),
- reuses `reconstruct.has_numeric_columns` lane machinery and the existing
  `check_native_table_structure` severity/result path (no parallel router),
- keeps the false-positive surface bounded (fail on geometry counts, not on fragile per-value
  matching),
- gives rich audit context for AC4.

**However, there is one genuine fork worth a panel:** whether the verifier should be allowed
to **fail (block) the rung**, or only **warn + still defer the accept/reject to the VLM
judge**. Failing deterministically saves the VLM call (the ticket's cost motivation) but
risks false-failing a correct table whose native lane count legitimately differs from its
visual columns (paired-year headers, spanning cells). Warn-only is safe but pays the VLM call
anyway, partly defeating the cost goal. This trade-off (determinism-vs-false-fail at the
gate) is the architectural decision the orchestrator should panel.

## 4. The consilium question (verbatim, ready to dispatch)

> In socr's born-digital table OCR pipeline, a deterministic PyMuPDF-only verifier (it
> clusters native numeric-token x-positions into column lanes via `page.get_text("words")`,
> with no model call) runs on a born-digital table page *before* the expensive VLM judge, to
> cheaply catch sparse comparison-row "lane drift" (a lone value sliding into an adjacent
> column). Should this verifier be allowed to **deterministically fail/escalate the ladder
> rung and skip the VLM call**, or should it only **emit a warning and still let the VLM
> judge make the accept/reject decision**, given that native lane count can legitimately
> differ from visual column count (paired year columns, spanning headers, a stub label column
> with no numbers)? Options:
>
> - **(A) Hard-fail gate:** the verifier blocks/escalates the rung deterministically when
>   native lane count vs. output column count (or per-row lane occupancy) mismatch beyond a
>   named, data-derived tolerance — saving the VLM call but risking a false-fail on a correct
>   table with paired/spanning columns.
> - **(B) Warn-only, VLM decides:** the verifier records a warning `AuditMetric` + audit event
>   with the drifted-row context, but the VLM judge still renders the page and makes the final
>   accept/reject — safe against false-fails, but pays the second-model cost the verifier was
>   meant to avoid.
> - **(C) Two-tier:** hard-fail only on the unambiguous, false-positive-free shapes (e.g. a
>   multi-lane native data row that collapsed to a single output cell), warn-and-defer-to-VLM
>   on the ambiguous lane-count mismatches.

(Tier C is the designer's lean if the panel wants a synthesis: it preserves the cost saving
on the cases that cannot false-fire while never blocking a correct paired/spanning-column
table.)

## Consilium decision (2026-06-15, run 20260615T170212Z-0362) — ACCEPTED

**Panel:** Codex (gpt-5.5) + Gemini (antigravity). **Verdict: Option C (two-tier), unanimous.**

The native table verifier runs deterministically (PyMuPDF only, no model) on born-digital
table pages at `_build_page_judge`, BEFORE `VLMPageJudge.assess`, and has two tiers:

- **Hard-fail tier (escalate the rung, skip the VLM):** ONLY on geometry-impossible structural
  violations provable from native numeric-token lane bounding boxes — e.g. a row has K distinct,
  well-separated native numeric lanes but the extracted markdown row collapsed them into fewer
  cells, or a numeric token landed in a neighbouring lane with no plausible spanning/paired-column
  explanation. The predicate must be NARROW, NAMED, and false-positive-free ("geometry-impossible
  row collapse / lane drift"), never "native lane count != output column count".
- **Warn-and-defer tier (record AuditMetric/AuditEvent, let the VLM judge decide):** all AMBIGUOUS
  lane-count mismatches — paired-year columns ("2023 2024" as one visual column), spanning headers,
  stub label columns with no numbers, sparse rows where visual and native lanes legitimately diverge.

**Rationale:** risk asymmetry (a false-fail costs a cheap escalation; a shipped shifted number is
catastrophic) PLUS VLM spatial blindness (a VLM judge will rubber-stamp subtle single-token drift,
so the deterministic tier MUST be allowed to escalate on unambiguous violations rather than always
deferring — this is why pure warn-only/B was rejected).

Any tolerance is named/data-derived (no magic literals). Scanned pages bypass cleanly (empty
`get_text("words")`). AC2/AC4 tightened: AC2 = sparse lane drift of the geometry-impossible kind is
caught without a second model call; AC4 = both hard-fail and warn outcomes are recorded in the audit
log with the drifted-row context.
