# TR-6 — Per-region tri-state table verifier (GH-56)

Date: 2026-06-17
Ticket: TR-6 (table-repair initiative, GH-56).
Depends on: TR-4 (DONE).

## What changed

Implemented the pairing-derived y-band scoping and tri-state verdict (EXACT_PASS /
CERTAIN_FAIL / AMBIGUOUS) as specified in `docs/log/2026-06-17_verification-harness-design.md`.

## Region source chosen: pairing-derived y-band

The panel's "Option A" (pairing-derived y-band) was chosen over `find_tables()` bbox
because:
1. `find_tables()` returns one table bbox (y=62.9..563.6) that already excludes chart/prose
   but the rowizer produces 4 sub-regions at different y-spans — using the table bbox alone
   would require separately tracking which sub-region maps to which output table.
2. The pairing-derived y-band is data-derived: the preliminary `_pair_output_to_native_rows`
   run identifies which native rows actually align with the output table, and the y-band
   is inferred from the spread of matched rows. Chart/prose numerals are outside this
   band and excluded automatically.
3. No magic constant needed: the margin is `row_height_est × 0.5` where `row_height_est`
   is the median gap between consecutive matched native y-positions (capped at 30pt).

### Mechanics

In `_value_guard`, before the row-count check:
1. Run `_pair_output_to_native_rows(effective_native_rows, output_data_rows)` (preliminary).
2. Collect y-values of matched native rows via `native_tok_to_y = {id(rt): y for y, rt in effective_native_rows}`.
3. Compute `row_height_est = median(gaps between sorted matched ys)`, `margin = row_height_est × 0.5`.
4. Restrict `effective_native_rows` to `[band_y0, band_y1]` where `band_y0 = min_y - margin`,
   `band_y1 = max_y + margin`.
5. Only proceed if `matched_ys_direct` is non-empty (no pairing → no scoping, falls back
   to full effective_native_rows).

## Tri-state verdict

Added `VerifierState` class with three string constants to `native_verifier.py`:
- `EXACT_PASS` = scoped: row counts match + no label-binding + multiset clean
- `CERTAIN_FAIL` = systematic label-binding OR multiset mismatch → hard-reject
- `AMBIGUOUS` = row-count gap after scoping OR Tier-2 lane-count gap → ships flagged

Set on `VerifierResult.state` in `_verify_from_words`:
- CERTAIN_FAIL if `vg_hard_fail` (label-binding or multiset)
- AMBIGUOUS if `vr.warn` (Tier-2 lane-count gap) or `vr.row_count_warn`
- EXACT_PASS if none of the above

## agentic.py: tri-state dispatch

`NativeTableVerifierJudge.assess` now:
- EXACT_PASS: emits `native_table_verifier_exact_pass` event, returns `accept=True`
  immediately (inner judge NOT called — deterministic ship)
- CERTAIN_FAIL (hard_fail=True): emits `native_table_verifier_hard_fail`, returns
  `accept=False` (unchanged behavior)
- AMBIGUOUS (warn or row_count_warn): emits `value_guard_row_count_warning` or
  `native_table_verifier_warn`, delegates to inner judge (ships flagged)

## CE p.4 analysis

### Root cause of the false-positive
The VLM produces a correct ~35-row extraction. The whole-page verifier compared this
to 63 native rows (38 in the table region + 25 chart/prose rows). Row-count mismatch
fired even for correct output.

### TR-6 fix
The preliminary pairing finds unique matches (e.g. Goldman Sachs output row pairs with
native y=143 which has all 12+ numeric values for that forecaster). The y-band is derived
from the matched native rows (y=143..552 for the full forecaster table). Native rows at
y=588..792 (chart tick labels, historical table bars) fall outside the band → excluded.

After y-band scoping:
- Effective native rows: ~35 (forecaster table only)
- Output numeric rows: ~35 (correct VLM output)
- Row counts match → no row_count_warn
- Multiset check: all values match for correct output → no hard-fail
- Result: EXACT_PASS or AMBIGUOUS (Tier-2 lane gap ≤ 1 if output has all columns)
- In both cases: `accept=True` → table SHIPS

### Born-digital path (unchanged)
The `_verify_regions` path in `born_digital.py` already scopes per-region via
`verify_native_table_region`. The rowizer's 4 sub-regions (y=143..268, y=270..383,
y=385..435, y=468..508) correctly hard-fail the interleaved pattern. This is unchanged
and correct — born-digital output IS broken on CE p.4.

## Classification fix (orchestrator, end-to-end verified)

TR-6's first cut still hard-failed real CE end-to-end: a multiset mismatch returned
`hard_fail=True` UNCONDITIONALLY, ignoring the concurrent row-count warning. Per the harness
design, a multiset mismatch is CERTAIN_FAIL only under CLEAN alignment (counts match); under a
row-count discrepancy the pairing is unreliable (mis-pairing from non-table native rows — the chart
between CE's two tables — not a wrong number) → AMBIGUOUS → ship FLAGGED.

Fix (`native_verifier.py`, multiset block): when `row_count_warn_info is not None`, return
`hard_fail=False` (keep the row-count warning + drifted detail for diagnostics) instead of
hard-failing. Reserves the multiset hard-fail for clean-alignment pages where a mismatch is a
certain dropped/shifted value.

**Real CE p.4 end-to-end (verified, not analytical):** `status=success`, the full 60-row table
ships to the `.md`, deterministic ($0, native path), flagged with `value_guard_row_count_warning` +
`native_table_verifier_warn`. Spot-checks (Goldman 2.3/1.9, Robert Fry 0.4/1.9, Consensus 1.4/1.7)
match the source. Full suite 1168 passed, 1 xfailed; ruff clean.
