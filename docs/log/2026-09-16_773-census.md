### S1. `native_verifier.py:1431` — `_value_guard` multiset — FALSE NEGATIVE (Tier-1)

**This is the worst finding in the census.** Four calls to `_value_guard(words, output_text)` with
identical native words (`alpha=-1.5, beta=2.0, gamma=3.0, delta=4.0`) and four candidate markdowns:

| case | model emits for `alpha` | `hard_fail` | drifted rows | row-count warning |
|---|---|---|---|---|
| A | `-1.5` (correct, plain) | False | 0 | False |
| B | `-9.9` (**wrong**, plain) | **True** | 1 | False |
| C | `&minus;1.5` (correct, entity) | False | 0 | False |
| D | `&minus;9.9` (**wrong**, entity) | **False** | 0 | **False** |

B and D are the same fabrication. Plain, it hard-fails. Entity-encoded, it ships with
`hard_fail=False`, zero drifted rows, and **no warning of any kind** — the page looks exactly like
the correct case A.

The mechanism is worse than a failed comparison: the entity row never even *pairs*. Instrumenting
the two-row version shows `effective_native_rows` collapse from 2 to 1 and the pairing from 2 to 1,
because `_pair_output_to_native_rows` (`native_verifier.py:1497`) scores overlap using
`_numeric_tokens_from_text`, which returns `[]` on the entity row. The row is therefore excluded
from the y-band *and* from the row count, so the row-count soft warning at `:1365` cannot fire
either. Both the hard gate and its backstop are silenced by the same cause.

**Consequence: false negative — fabrication escapes unflagged. This is the #770 shape, in the
Tier-1 hard-fail path.**

### S2. `native_verifier.py:1054` — `_parse_all_data_rows` — FALSE NEGATIVE (Tier-1)

An entity-encoded row is reclassified out of the numeric-row set:

```
plain   numeric_rows=[(0,'alpha',{'-1.5':1}), (1,'beta',{'2.0':1})]   label_only=[]
entity  numeric_rows=[(1,'beta',{'2.0':1})]                           label_only=[(0,'alpha')]
```

Downstream, on the TR-4a interleaved-failure shape (values in unlabeled rows, names in data-less
rows) that `_value_guard`'s label-binding hard-fail exists to catch:

| | `adjacent_pairs` | `clean_labeled` | hard-fail fires |
|---|---|---|---|
| plain | 3 | 0 | **True** |
| entity | 0 | 0 | **False** |

Entity-encoded, the unlabeled numeric rows carry no recognised numeric token, so they join neither
`numeric_rows` nor `label_only_rows`; `adjacent_pairs` drops to 0 and the systematic
name/value mis-binding — under which *every number on the page is mis-attributed* — ships silently.

**Consequence: false negative in a Tier-1 hard-fail path.**

`_MIN_DATA_NUMERIC_CELLS` and is **absorbed into the emitted-header token set**:

```
plain   ['cola', 'colb', 'colc', 'label']
entity  ['&minus;1.5', '&nbsp;2.0', '&nbsp;3.0', 'alpha', 'cola', 'colb', 'colc', 'label']
```

The owed-token set is then compared against a header inflated with body content, so owed tokens can
be spuriously satisfied. **Consequence: false negative — the HARD verdict is talked out of firing
by the defect itself.**

### S7. `witness.py:392` — `_corroboration_contradicted_indices` — FALSE NEGATIVE (swap escapes)

Two table blocks emitted **swapped** relative to their native boxes:

| | output multisets | overlap matrix | contradicted |
|---|---|---|---|
| plain | `[{9.0,8.0}, {1.0,2.0}]` | `[[0,2],[2,0]]` | `[0, 1]` |
| entity | `[{}, {}]` | `[[0,0],[0,0]]` | `[]` |

Entity-encoded, all overlaps are 0, `overlap[i][j] > overlap[i][i]` is `0 > 0`, and the swap is not
detected. The function's docstring (`witness.py:387-389`) declares empty evidence NEUTRAL by
design — that is correct for *unreadable* native words, but here the evidence is readable and is
being discarded by the gate. **Consequence: false negative — a block swap escapes.**

### S8. `native_verifier.py:399` — `_output_header_numeric_tokens` — MISCOUNT

```
plain   _output_header_numeric_tokens("| Var | (1) | (2) |...")               -> ['1', '2']
entity  _output_header_numeric_tokens("| Var | &lpar;1&rpar; | ... |")        -> []
```

Feeds `_header_excluded_native_rows` (`:1132`). With an empty token set, no native row is
header-like, so a leading spec-number header row is counted as a data row and the native row count
is one too high. That shifts the row-count **soft warning** only; no hard verdict reverses on this
path alone. **Consequence: miscount.** Lower severity than S1–S7, but it is on the same input that
triggers them, so it compounds.

### S9. `header_repair.py:148` — `_repair_too_narrow_spanning_header` — **INERT as measured**

The guard at `:147-154` ("a short numeric row is body data, not evidence of a spanning header")
provably diverges in isolation:

```
plain  guard fires (abstain): True
entity guard fires (abstain): False
```

**But I could not make that divergence change the function's return value.** Both encodings return
`None` on every input I constructed, including with site `:209` monkey-patched to a decoding
version. The reason is a second dependency on the same encoding: the widened cell is passed as
`label` to `_native_label_lane` (`:160` → `:441`), which matches `label` against native words — and
the entity-encoded label never matches the native `-1.5`.

**Reported as inert rather than inflated to a bug.** One caveat for whoever fixes this, and it is
a real one: **S9 is inert only because the sites around it are broken the same way.** Fixing `:209`
and `_native_label_lane`'s label path without also fixing `:148` would turn an inert site into a
live one, in the direction of restructuring a body data row as a header. Fix `:148` in the same
change, not later.

### `native_verifier.py:1009` — the shared sink

`_numeric_multiset_from_tokens` calls `is_numeric_token(tok)` on raw tokens. It is not itself
NEEDS-FIX *or* SAFE — it is caller-dependent, and it is the reason S1, S2, S5 and S7 all exist. Its
native-side callers (`:1432`, `header_repair.py:200`, `witness.py:439`) are correct as written;
its model-side callers are not. It is listed NEEDS-FIX in the table because it is the single most
economical place to close the family (§5).

**One structural note on how to fix, not a design ruling.** Ranks 1, 2, 3 and 6 all reach the gate
through `_numeric_multiset_from_tokens` / `_numeric_tokens_from_text`. Decoding inside those two
functions closes four of the eight ranks at once, and it is safe for their native-side callers —
`_normalize_cell` is `html.unescape` plus a trailing-dash strip, and a PyMuPDF token contains no
entity to unescape. It would **not** close ranks 4, 5, 7 or 8, which call the gate directly.
A per-call-site fix and a sink fix are both defensible; this is a note for the implementer, not a
recommendation, since the ticket asked for a census.
