# 2026-09-16 — GH-679: decorated-numeric candidate tokens skipped `html.unescape`

**Branch:** `fix/679-decorated-numeric-tokens` (off `origin/main@751c6ba`)
**Status:** DONE

## The defect

`collect_table_tokens` (`src/socr/tables/source_evidence.py`) ran `is_numeric_token(cell)`
on the RAW cell; `html.unescape(cell)` only happened later, in the label branch, past the
`row_idx == 0 continue`. `&nbsp;62.5` and `62.5--` never entered `raw_numeric` — the
multiset `verify_table_tokens` / `_multiset_supported` actually checks against page
evidence. Fail-open on the citable values: a decorated number shipped unverified while the
table could still pass.

## (a) vs (b): why the evidence side had to change too

The orchestrator's brief asked me to measure candidate-only normalization (a) against a
shared normalizer on both `collect_table_tokens` and `_tokens_from_plain_text` (b), not
assume.

Measured (a): on `origin/main`, `_tokens_from_plain_text("41.3-- appears in the printed
table too.")` returns `Counter()` — the evidence side never recognised the decoration
either, even before any of this ticket's changes. Normalizing the candidate side only would
make `41.3--` visible as `41.3` there while the evidence side stayed keyed on the
unrecognised raw `41.3--` — so a candidate that **genuinely agrees** with a page whose own
raw text (OCR layer, `get_text()`) carries the same VLM-style decoration verbatim would
newly **reject**, where before the fix it silently passed (wrongly, but without an active
false reject). That is a real regression, not a hypothetical: `test_symmetric_decoration_still_passes`
pins it and is, by design, the SOLE guard for the evidence-side half — see its docstring.

Chose (b): one shared `_normalize_cell` (decode + trailing-dash strip), called identically
from both `collect_table_tokens` (candidate) and `_tokens_from_plain_text` (evidence).

## Unicode dash decoration — found during review, not in the original ticket

The reviewer (team-lead, running the same worktree independently) caught that an ASCII-only
`rstrip("-")` half-closes the ticket: `html.unescape("&mdash;")` and `html.unescape("&ndash;")`
produce U+2014 EM DASH / U+2013 EN DASH, not ASCII `-`, so an ASCII-only strip leaves the
decoded glyph trailing and still unmatched by `is_numeric_token`'s anchored `_NUM_TOKEN_RE`.
Measured directly: `62.5—`, `62.5&ndash;`, `&nbsp;62.5&mdash;` all still failed to enter the
numeric multiset with the ASCII-only version.

Fixed by widening `_TRAILING_DASH_CHARS` to a named module constant using explicit
`\N{...}` code-point escapes (auditable, no bare literal glyphs, no magic string):
HYPHEN-MINUS (U+002D), HYPHEN (U+2010), NON-BREAKING HYPHEN (U+2011), FIGURE DASH (U+2012),
EN DASH (U+2013), EM DASH (U+2014), HORIZONTAL BAR (U+2015), MINUS SIGN (U+2212).

**Sign safety check (also reviewer-requested):** the widened class includes U+2212 MINUS
SIGN, the true typeset minus a VLM may emit for negatives, distinct from the presentation
dash glyphs above it. `_normalize_cell` only ever `.rstrip()`s — a LEADING occurrence of any
character in the class (ASCII `-` or U+2212) is never touched, so `−5.2` (leading true
minus) still normalizes to `−5.2` and `is_numeric_token` → `strip_presentation`'s existing
unicode-minus-to-ASCII conversion correctly reads it as `-5.2`, never `5.2`. Measured:
`−5.2` → sign kept; `−5.2—` (true minus + em-dash decoration) → `−5.2`, decoration stripped,
sign kept; `-5.2--` → `-5.2`. Pinned in
`test_leading_true_minus_sign_is_preserved_not_stripped_as_decoration`.

New pins were confirmed to FAIL against the ASCII-only `rstrip("-")` predecessor (verified
in a throwaway `/tmp` copy, discarded after) before the widened class was applied — the
"pins must fail before the fix" check the reviewer asked for.

## Q1 — is a trailing single dash (`41.3-`) always presentation? Recorded as a deliberate choice

`41.3-`, `41.3--`, and `5-` all normalize to their bare magnitude (`41.3`, `41.3`, `5`).
Checked for a genuine collision: does this codebase, anywhere else, treat a TRAILING dash as
a negative-sign convention (so `5-` would mean `-5`, distinct from plain `5`)? Grepped
`reconcile.py` / `native_verifier.py` — no. The only recognised negative conventions in this
pipeline are a LEADING minus (ASCII or Unicode) and parenthesis-wrapping
(`_normalize_numeric_token`'s `(0.014)` → `-0.014`). A trailing dash of any length was
previously **always invisible** (dropped from the multiset, not classified as anything) — so
this fix does not reverse an existing sign reading; it makes a previously-unrecognised token
visible as its bare magnitude. Deliberate choice: **treat any run of trailing dash-class
glyphs as decoration, never as a sign**, consistent with how this codebase already treats
trailing dashes on LABEL tokens (`_content_token`, #659). The one residual ambiguity — a
spaced range boundary like `"41.3- 45.6"` tokenising its first half as a bare `41.3` in the
evidence path — is narrower than the bug closed and was not previously distinguishable
either (the whole token was silently dropped before this fix). Not treated as blocking.

## Q3 — does the shared normalizer change LABEL branch output? Checked and null

The reviewer independently confirmed this and I reproduced it: `_CONTENT_TOKEN_RE`
(`[A-Za-z][A-Za-z0-9\-]{2,}`) only ever admits ASCII `-` internally/at its edges — Unicode
dash glyphs are outside its character class, so they were never part of a label token match
before OR after this fix. `_content_token`'s own `.strip("-")` (ASCII only, #659) already
removes any ASCII trailing/leading run from the matched token. Diffed content-token output
for 9 fixtures (including `Bank--of--England`, `Settlements--`, `Reserves——` with an actual
em-dash, `Item–` with an actual en-dash) between the pre-679 label decode
(`html.unescape` only) and the new `_normalize_cell` (decode + widened dash-class strip):
**identical in every case.** No label behaviour change; nothing out of this ticket's scope.
