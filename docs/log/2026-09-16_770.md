## GH-770 — fabrication escapes detection when entity-encoded

Two `model_unbound`-surfacing sites and one `ambiguous_count` site tested the RAW candidate cell
before `is_numeric_token`, so an invented value that happens to be entity-encoded (`&minus;7.7`
instead of `7.7`) never entered the fabrication signal at all — not misclassified, absent from every
collection.

- **`bind()` ~2085** — unbound candidate rows (a candidate row `_bind_rows` could not anchor to any
  native row): `model_value = cand_row[col].strip()` gated raw. Fixed: normalize via `_normalize_cell`
  before the gate; `UnboundCell.token` still records the RAW `model_value`.
- **`bind()` ~2179** — unmapped columns under the salvage-DP walk (a candidate column
  `_best_lane_column_map` could not place under any native lane): same raw gate on `cand_text`. Same
  fix, same raw-token-recorded decision.
- **`bind()` ~2159** — `ambiguous_count` under the salvage walk, lower severity: a mapped lane whose
  native row has no token for that lane, with a numeric candidate cell, is "known geometry, not
  convictable either way" — was under-counted for entity-encoded cells. Same fix.

All three keep the RAW token/cell in whatever gets recorded downstream (`UnboundCell.token`,
`ambiguous_count` itself carries no token) — consistent with #766's decision that only the numeric
TEST is decoded, never the record.

## GH-768 — an all-entity column vanishes before `bind()` sees it

`_candidate_data_column_indices` (~536) decides which markdown columns count as "data columns" by
testing the RAW cell for numeric shape, upstream of everything #679/#690/#766/#770 fixed.
`_project_candidate_data_columns` then strips any column not in that set — so an entity-encoded
column with no plain-text sibling row anywhere is projected away before `bind()` compares anything.

Two shapes, confirmed both matter (per #766's own decision log, which flagged this site but got the
severity wrong on first pass — corrected here by measuring the mixed shape directly):

- **Single-column shape** (the entity-encoded column is the table's ONLY data column): pre-fix, the
  call site's empty-case fallback (`binding.py:1908-1911`, `if not candidate_data_columns: ... grid =
  candidate_grid`) saved this — verified `data_columns == ()` pre-fix, fallback fires, unprojected
  grid used, no content lost.
- **Mixed shape** (entity column beside a plain-numeric column): the sibling column alone gives
  `data_columns` a non-empty value, so the fallback never fires and `_project_candidate_data_columns`
  drops the entity column for real. Measured pre-fix on the issue's own fixture (`P`, `Q` plain, `Val`
  entity-encoded): `data_columns == (1, 2)`, `Val` excluded, `bind()` reports nothing for it (no match,
  no contradiction, no unbound) — silent content loss, not merely a skipped narrowing.

Fix: route each candidate token through `_normalize_cell` before both the `is_numeric_token` test and
the `_SPEC_NUMBER_RE` exclusion, inside the width-counting loop. After the fix the mixed-shape fixture
gives `data_columns == (1, 2, 3)` and all three columns reach `bind()`'s comparison (verified:
6 `MatchedCell`s, `contradicted_cells == []`, `model_unbound == []`, `native_unbound == []`).

**Precision on the single-column shape** (the line the team lead's original brief got wrong, and the
merged `88ae0c8` still carried — corrected here): post-fix, `_candidate_data_column_indices` now
returns `(1,)` directly — `Val` is correctly recognised as data, so `not candidate_data_columns` is
False and the 1908 fail-safe **no longer fires for this shape**. The path changed. The *outcome* did
not: the fail-safe would have produced `tuple(range(1, physical_n_cand_cols + 1))`, which for this
one-column grid is `(1,)` — identical to what the fixed selector now returns directly — and the
projected rows are unchanged, `(('Yield', '&minus;2.5'), ('Forward', '&minus;4.5'))` either way. The
test (`test_gh768_single_entity_column_shape_unchanged_by_the_fix`) pins the OUTCOME — the returned
`candidate_data_columns` tuple and the projected rows — not the path; asserting the fail-safe branch
executed would be pinning an implementation detail nobody cares about, and would now be FALSE besides.

**Is the fail-safe dead code now?** No — one case still reaches it: a candidate table with NO numeric
column in any row (every column fails `is_numeric_token` even after decoding — pure label/prose
columns). Measured directly against the fixed `_candidate_data_column_indices`:

```
| Item    | Note        |
|---------|-------------|
| Yield   | see below   |
| Forward | flagged     |

_candidate_data_column_indices -> ()   -- unchanged by this fix, "Note" is not numeric under ANY decode
```

Confirmed this still reaches the fail-safe inside a full `bind()` call (not just the isolated helper):
`bind()` on this fixture with no native numeric words runs the `if not candidate_data_columns:` branch,
`candidate_data_columns` becomes `tuple(range(1, physical_n_cand_cols + 1))`, `grid = candidate_grid`,
and returns cleanly (`matched_cells == model_unbound == native_unbound == []`, as expected — there is
no numeric content on either side to bind). The fail-safe is not unreachable; it is reachable for a
genuinely different shape than the one this ticket fixed. Pinned as an eighth test,
`test_gh768_empty_case_fallback_still_reachable_after_the_fix`.

A genuinely non-numeric column (plain prose, decoded or not) stays excluded in both tickets' tests —
the narrowing itself is untouched.

## The fix — four sites, one shared normalizer

All four route the candidate/model cell through `_normalize_cell` (`native_verifier.py`, already
imported by `binding.py`) before the `is_numeric_token` gate:

1. `_candidate_data_column_indices` (~541, GH-768) — `token` -> `normalized` via walrus, feeds both
   `is_numeric_token` and the `_SPEC_NUMBER_RE.match(strip_presentation(...))` exclusion.
2. `bind()`'s unbound-candidate-row walk (~2089-2099, GH-770) — `model_normalized =
   _normalize_cell(model_value)`; `UnboundCell.token` keeps the raw `model_value`.
3. `bind()`'s salvage-walk mapped-lane ambiguity count (~2170-2179, GH-770) — `cand_normalized =
   _normalize_cell(cand_text)` feeds only the `is_numeric_token` branch of the ambiguity condition.
4. `bind()`'s salvage-walk unmapped-column walk (~2197-2210, GH-770) — same pattern,
   `UnboundCell.token` keeps the raw `cand_text`.

at site 1, same call site)

Checked every site not already covered by this ticket or a prior one:

- **`binding.py`** (16 total, 4 fixed here, 5 already fixed by prior tickets — `1601`/`1676`
  `_best_lane_column_map`/`_record_inventions_on_parent_row` #766, `1224` `_candidate_row_multiset`
  #690, `2275` equal-lane-count walk #766): the remaining 7 (`730`, `733`, `792`, `833`, `908`, `964`,
  `991`) all read `word[4]`/`wd[4]` — native PDF words, never entity-encoded (entities come from a
  VLM's markdown, not PyMuPDF's text layer). Confirmed safe by reading each function's signature.
- **`source_evidence.py:288,329`** — already route through `normalized = _normalize_cell(cell)` /
  `_normalize_cell(word)` (the #679 fix). Safe.
- **`native_verifier.py:1009`** (`_numeric_multiset_from_tokens`) — only ever called with a list already
  built from `_normalize_cell`'d strings by both its callers. Safe.
- **`header_cut.py:111`** (`w[4]`), **`reconstruct.py:474`** (`w[4]` from `_destroyed_numeric_tokens`,
  native words by the function's own docstring), **`reconstruct.py:912`** (`_is_data_row`, operating on
  a PyMuPDF `table.extract()` grid — native text-strategy extraction, never HTML-entity-encoded) — all
  native-side. Safe.

Two sites found that ARE genuine unnormalized candidate/model-text reads, **outside this ticket's
`binding.py` scope** — reporting rather than folding in silently:

- **`row_corroboration.py:250` (`_is_genuine_numeric`)**, called from `numeric_body_rows` (`258`, `588`,
  `594`) with rows sourced from `table_blocks(markdown)` — genuine candidate markdown, confirmed via
  `structure_check.py:415` and `manifest.py:1244,1539`. An entity-encoded candidate numeric token is
  silently dropped from a row's token sequence, undercounting "numeric body rows" that feed row-shape
  reconciliation checks.
- **`adjudication.py:182` (`tokens_agree`)**, called from `_disprove_one` with `item.model_token` /
  `item.native_token` — both RAW by #766's own design decision. A fresh independent re-transcription
  (`transcribe(item.cell_bbox)`) is compared against the raw `model_token`; if the model's original
  markdown was entity-encoded, `tokens_agree` can never confirm agreement even when the re-transcription
  is correct, so the `raster_transcription` disproof path silently never fires for entity-decorated
  contradictions.

Both are the same root cause, one subsystem removed from `binding.py`'s comparison core. Candidates
for their own tickets.
