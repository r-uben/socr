# 2026-08-30 — TICKET-A4: ladder state machine + page reducer (GH-353)

## What changed

New `src/socr/judge/table_ladder.py`: pure functions implementing the per-table S1/S2
ladder transition logic and the multi-table page reducer, over injected `RungCallable`s
from `socr.judge.table_verdict` (A1). No I/O, no config reads.

- `TableLadderOutcome` — `ACCEPTED | REJECTED | UNVERIFIED`, shared by both the
  per-table result and the page reducer's result.
- `run_table_ladder(rungs, crop_path, markdown, table_id)` — runs one table through the
  ordered rung sequence:
  - **A, high confidence** (or A reached at the last rung) → `ACCEPTED` immediately,
    no further rungs called.
  - **A, low confidence**, rungs remaining → confirm at the next rung with
    `prior_findings=None` (nothing to complain about).
  - **B (FAIL)**, rungs remaining → tiebreak at the next rung with the FAIL's findings
    attached; exhausting on B → `REJECTED`.
  - **C (¬S1)**, rungs remaining → substitute at the next rung with `prior_findings=None`
    (fresh eyes, never biased by a verdict nobody produced); exhausting on C →
    `UNVERIFIED`.
  - Any later rung's outright PASS (any confidence) ends the ladder `ACCEPTED` — a table
    is never held hostage by an earlier B or C once a later rung actually looked and
    approved.
- `reduce_page_ladder(table_results)` — any `REJECTED` table ⇒ page `REJECTED`; else any
  `UNVERIFIED` ⇒ page `UNVERIFIED`; else `ACCEPTED`. Empty page (no tables) is
  `ACCEPTED`. All per-table results are kept on the returned `PageLadderResult` for the
  sidecar/audit trail, regardless of which table decided the page outcome.

Generalized over an arbitrary rung sequence (not hardcoded to 2), though the current
design (CLI₁ ollama, CLI₂ gemini) only exercises the 2-rung case.

## Open interpretation this ticket had to resolve

The ticket's transition table (A-high, A-low→{A,B,¬S1}, B→{A,B,¬S1}, C→{A,B,¬S1}) covers
2-rung sequences but leaves the "A-low at the last rung, nothing left to confirm" case
implicit. Resolved as: accept (unanimous PASS-so-far, no contradicting evidence)
rather than treat it as an exhaustion failure — consistent with "acceptance needs both"
being about confirmation opportunities existing, not about forcing a second rung to run
when there isn't one. Covered by
`test_a_low_at_last_rung_accepts_unanimous_so_far`.

## Follow-up: review tightening (consilium — codex gpt-5.6-sol + gemini antigravity, unanimous)

The initial "A-low at the last rung, nothing left to confirm → accept unanimous-so-far"
call (above) was TIGHTENED after review. A low-confidence PASS explicitly needs
corroboration; treating a substituted ¬S1 (nobody looked) as sufficient corroboration
silently redefines "needs both" as "one weak witness is enough when the other judge was
unavailable." Fixed rule, now implemented and documented in the module docstring:

- A low-confidence PASS accepts at the last rung **only if the immediately preceding
  rung was itself a real PASS** (any confidence) — two witnesses in agreement.
- A lone low-confidence PASS — whether it is the only rung run, or the preceding rung
  was ¬S1 (substitute) or FAIL (tiebreak) rather than PASS — exhausts to
  `TABLE_UNVERIFIED`, not `TABLE_ACCEPTED`.
- High-confidence PASS at any rung still accepts immediately, unaffected.
- `low-PASS → ¬S1` was already correctly `UNVERIFIED` via the existing ¬S1-exhaustion
  branch; pinned with an explicit symmetric test rather than left implicit.

Implementation: `run_table_ladder` now tracks `prior_was_pass` (True only when the
immediately preceding rung answered with an actual PASS verdict, any confidence; reset
to False on FAIL or ¬S1). The last-rung low-confidence-PASS branch checks this flag
instead of always accepting.

Tests changed: `test_a_low_at_last_rung_accepts_unanimous_so_far` (now-wrong — a lone
low-confidence PASS was being accepted) replaced by
`test_lone_low_confidence_pass_with_no_corroboration_is_unverified`. Added
`test_not_s1_then_low_confidence_pass_at_last_rung_is_unverified` (the case named in the
review) and `test_low_confidence_pass_then_low_confidence_pass_accepts` (confirms the
unchanged two-real-witnesses-agree path still accepts). The symmetric `low-PASS → ¬S1`
pin is `test_a_low_then_not_s1_unverifies` (pre-existing, docstring updated to note it's
the symmetric case).
