# 2026-09-16 — GH-140: audit the known-lossy math-font lane

## What changed

Mirrors the existing PUA-class accounting (`native_math_unrecovered`,
`UNRESOLVED_MATH_KIND`) for the adjacent math-font damage class documented by
`_detect_math_fonts`'s own docstring: "subscripts flatten, Greek letters
drop, reading order breaks around equations." A born-digital page whose
maths is font-detected as lossy, has no PUA damage, and no retained
equation-lane coverage now:

1. emits a durable audit event (`native_math_font_unrecovered`,
   `MATH_FONT_UNRECOVERED_KIND`) that survives into the page sidecar and
   resume replay,
2. demotes the page's reported status SUCCESS -> WARNING via a REPORTING-only
   manifest guard (never re-selects/re-routes),
3. demotes the document status to `AUDIT_FAILED`, prints a CLI line, and
   appends a note to `final_result.error` — the same three surfaces the PUA
   class uses.

New pure accounting: `math_font_unrecovered_detail()` in
`src/socr/math/accounting.py`, reading a new evidence field,
`PageState.equation_region_evidence`, that the P4-R equation-region lane
(`_agentic_equation_region_page`, orchestrator.py) now populates with
`{regions_total, regions_covered}` at every exit (detection failure, zero
regions, and after the attach/reject verdicts), mirroring
`corrupt_region_evidence`'s "assigned unconditionally" contract.

## A correction to the ticket's stated context

The ticket's framing ("recovery exists only behind `--detect-equations` /
`--recover-clean-equations`, both default False, so by default nothing
recovers it") is not accurate on `main@5478b42`. `equation_region_lane`
(config) and `agentic` both default **True** — the P4-R region lane
(`_agentic_equation_region_page`) is already DEFAULT-ON and already emits
per-region outcome events. The real gap was never "nothing is recorded"; it
is that what P4-R already records per region was never wired into the
document-status-demotion / reconciliation / CLI-surfacing machinery the PUA
class gets, so it never became durable, document-level loss. The fix reads
coverage from the lane's own region-outcome evidence rather than gating on
either recovery flag, which also satisfies criterion 2 (outcome-based, not
configuration-based) by construction — there is no flag check anywhere in
`math_font_unrecovered_detail`.

## A design correction found only by running the full suite

The first implementation gated the new event on the umbrella `has_equations`
flag (as literally named in the ticket). Running the FULL suite (not a `-k`
subset) surfaced 4 failures, all pre-existing tests asserting equation-only
pages ship unaffected — most pointedly
`tests/test_s1_structure_class_winner_gh_reachability.py`, whose own
docstring records that #269's BLOCKING 1 review already fixed exactly this
shape of bug once: `has_equations` is a THREE-way union
(`_detect_math_fonts` OR `_detect_equations`'s raw-LaTeX-string fallback OR
`has_corrupt_math`), and the fallback signal extracts as ordinary prose —
not lossy at all. Gating on the union re-flagged pages that were never
damaged.

Fix: added a new, narrower field, `has_math_font_typesetting`
(`PageAssessment` / `PageState`), computed from `_detect_math_fonts(page)`
alone and threaded through `born_digital.py`'s 11 `PageAssessment`
construction sites, `state.py`'s assessment->state copy, and the accounting
function's parameter. The guard and the assemble-phase reconciliation both
read this narrower field, never the union. All 4 previously-failing tests
pass again unchanged; a new regression test
(`test_a_generic_equation_page_with_no_font_signal_is_untouched`) pins the
distinction directly at the guard.

## Criterion 4 — joins the status-demoting set (argued)

**Decision: yes**, the new kind joins the `pages_ok` chain (document status
demotes to `AUDIT_FAILED`), gets its own retire-then-readd reconciliation
block on reruns/resume, its own CLI print, and its own `final_result.error`
note — the identical shape as `UNRESOLVED_MATH_KIND`.

Argument: this repo's rule is that loss surfaces at every level — page
status, document status, metadata, CLI — not just one (CLAUDE.md, "No
silent content loss"). The ticket exists specifically because a math-font
page ships SUCCESS with zero surface today; landing only a page-level note
while leaving `DocumentStatus.SUCCESS` intact would still let a document
with real, known math loss report clean at the level most consumers
actually read (the CLI summary, the document-level `.error`). The PUA class
already made this call for the structurally identical situation
(unrecoverable native math, same failure mode, same consumer-facing
surfaces) — treating a stricter twin damage class more leniently than its
sibling would be an unprincipled asymmetry, not a considered choice.
Counter-consideration (rejected): "this is a metadata/plausible-prose signal,
noisier than PUA's, so under-report it as a WARNING-only note." Rejected
because a noisier signal is an argument for *tightening the detector*
(future work — see `MIN_MATH_CORRUPTION_GLYPHS`'s analogue is deliberately
absent here per criterion 5), not for hiding a known-lossy page from the
document-level bucket that exists precisely to make this kind of loss
discoverable without reading every page's own notes.

## Criterion 3 — no double-reporting

Guaranteed by construction: `math_font_unrecovered_detail` returns `None`
whenever `has_corrupt_math` or `has_unmapped_math_glyphs` is true, so it can
never fire alongside `UNRESOLVED_MATH_KIND` (PUA) or the corrupt-math-region
lane's own AUDIT_FAILED bucket. Covered by
`test_a_pua_page_never_also_raises_the_math_font_event` (end to end) and the
two pure unit tests preceding it.

## Criterion 5 — no new magic threshold

None introduced. Coverage is a direct region-count comparison
(`regions_covered == regions_total`), no ratio, no score cutoff.
