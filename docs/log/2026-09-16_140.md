# 2026-09-16 — GH-140: audit the known-lossy math-font lane

## What changed

Mirrors the existing PUA-class accounting (`native_math_unrecovered`,
`UNRESOLVED_MATH_KIND`) for the adjacent math-font damage class documented by
`_detect_math_fonts`'s own docstring: "subscripts flatten, Greek letters
drop, reading order breaks around equations." A born-digital page whose
maths is font-detected as lossy, has no PUA damage, and no retained
equation-lane coverage now:

1. emits a durable audit event (`native_math_font_unrecovered`,
   `MATH_FONT_UNRECOVERED_KIND`) that survives into the page sidecar and
   resume replay,
2. demotes the page's reported status SUCCESS -> WARNING via a REPORTING-only
   manifest guard (never re-selects/re-routes),
3. demotes the document status to `AUDIT_FAILED`, prints a CLI line, and
   appends a note to `final_result.error` — the same three surfaces the PUA
   class uses.

New pure accounting: `math_font_unrecovered_detail()` in
`src/socr/math/accounting.py`, reading a new evidence field,
`PageState.equation_region_evidence`, that the P4-R equation-region lane
(`_agentic_equation_region_page`, orchestrator.py) now populates with
`{regions_total, regions_covered}` at every exit (detection failure, zero
regions, and after the attach/reject verdicts), mirroring
`corrupt_region_evidence`'s "assigned unconditionally" contract.

## A correction to the ticket's stated context

The ticket's framing ("recovery exists only behind `--detect-equations` /
`--recover-clean-equations`, both default False, so by default nothing
recovers it") is not accurate on `main@5478b42`. `equation_region_lane`
(config) and `agentic` both default **True** — the P4-R region lane
(`_agentic_equation_region_page`) is already DEFAULT-ON and already emits
per-region outcome events. The real gap was never "nothing is recorded"; it
is that what P4-R already records per region was never wired into the
document-status-demotion / reconciliation / CLI-surfacing machinery the PUA
class gets, so it never became durable, document-level loss. The fix reads
coverage from the lane's own region-outcome evidence rather than gating on
either recovery flag, which also satisfies criterion 2 (outcome-based, not
configuration-based) by construction — there is no flag check anywhere in
`math_font_unrecovered_detail`.

## A design correction found only by running the full suite

The first implementation gated the new event on the umbrella `has_equations`
flag (as literally named in the ticket). Running the FULL suite (not a `-k`
subset) surfaced 4 failures, all pre-existing tests asserting equation-only
pages ship unaffected — most pointedly
`tests/test_s1_structure_class_winner_gh_reachability.py`, whose own
docstring records that #269's BLOCKING 1 review already fixed exactly this
shape of bug once: `has_equations` is a THREE-way union
(`_detect_math_fonts` OR `_detect_equations`'s raw-LaTeX-string fallback OR
`has_corrupt_math`), and the fallback signal extracts as ordinary prose —
not lossy at all. Gating on the union re-flagged pages that were never
damaged.

Fix: added a new, narrower field, `has_math_font_typesetting`
(`PageAssessment` / `PageState`), computed from `_detect_math_fonts(page)`
alone and threaded through `born_digital.py`'s 11 `PageAssessment`
construction sites, `state.py`'s assessment->state copy, and the accounting
function's parameter. The guard and the assemble-phase reconciliation both
read this narrower field, never the union. All 4 previously-failing tests
pass again unchanged; a new regression test
(`test_a_generic_equation_page_with_no_font_signal_is_untouched`) pins the
distinction directly at the guard.

## Criterion 4 — REVISED: reported, not status-demoting

**First decision (below, kept for the record): yes, join the status-demoting
set, mirroring the PUA precedent.** That decision was reviewed and
**reversed** — but the first version of this reversal argued from the wrong
premise. Recorded here is the corrected version (a design-panel review, via
Astra, caught the error), not the original.

**Wrong premise (do not repeat this argument):** "36.1% is ~15x the PUA
precedent's 2.4%, therefore the demotion is unaffordable." This treats the
trigger-rate measurement (`docs/log/2026-09-02_p4m-trigger-rates.md`,
23,190 pages) as if it were a false-positive rate. It is not — it is
*prevalence*: how often `has_math_font_typesetting` fires, not how often
that firing corresponds to an actually garbled reading. Prevalence alone
cannot justify suppressing a failure signal; a common defect is still a
defect. Worse, the same log's own "Ruling — 2026-09-02" section explicitly
**accepts** the 36% figure for routing — citing it as grounds to *reject* a
different, downstream use of the same signal without reconciling that
acceptance would have been a misreading of the document being cited.

**The argument that actually holds — why the acceptance does not transfer.**
The ruling's stated reason for accepting 36%:

> Owner chose the signal as detected … accepting that 36% of the free lane
> pays a local model call. Reasons: … the panel's Q2 ruling makes
> **over-routing a cost, not a correctness risk** (the model reading is
> region-scoped and never replaces native prose)

36% was accepted *because, in that context, it has no correctness
consequence* — routing on a false positive spends one local model call and
changes nothing else; native prose ships either way. Status demotion is not
that kind of decision. It changes what every downstream consumer sees
(`state.status`, the CLI summary) and, per GH-177's contract, it flips the
process exit code. The number (36.1%) is identical between the two uses;
the *consequence* is not, and it is the consequence — not the prevalence —
that the ruling's acceptance was conditioned on. So citing the same
percentage to reject demotion is not inconsistent with the ruling; it is
applying the ruling's own stated condition to a case where that condition
is absent.

The 8.0% slice (≤10 math-font chars, "inline symbols in prose, not
equations") sharpens this further on its own terms, independent of the
prevalence question: it has no display equation for the P4-R region locator
to ever find, so under the *original* (demoting) design it would be a
**permanent** `AUDIT_FAILED` with no path out — not a transient state
waiting on a recovery lane to catch up, but a fixed floor on how clean any
document containing such a page could ever report. The trigger-rates log
also forecloses inventing a char-count cutoff to carve that slice out: "The
math-font character count has no natural break … Any cut is an invented
threshold" — which would also violate criterion 5.

**Decision now: report, don't demote — and treat this as unresolved, not
settled.** Nobody has measured how often math-font presence corresponds to
an actually garbled reading (the false-positive rate the wrong-premise
argument above assumed without evidence either way). Until that is
measured, this ships as an interim observability patch: the event, its
sidecar persistence, the page-level audit note, and the CLI/document-note
surfacing all ship — a downgrade from "fails the document" to "reported and
visible," not a downgrade to silence — but the demotion itself stays out
because the one precedent for accepting this exact prevalence figure was
explicit that it applies only where the consequence is a cost, not a
correctness/exit-code change. Only the `pages_ok`/`AUDIT_FAILED`
document-status line and its accompanying retire-then-readd status
side-effects were removed; the retire-then-readd *event* reconciliation
(keeping `state.events` in sync with the current per-page reduction across
reruns/resume) stays, since that is what makes the event itself durable and
correct, independent of document status. The document-level note itself
lives in `final_result.audit_notes`, not `final_result.error` — see the
"Second REVISE" section below for why.

This reverses the PUA-precedent argument below, which is left in place
because it was a fair reading of the ticket's stated criterion in isolation
— it did not check whether the class it mirrors was validated at the scale
being copied, and neither, on the first attempt, did this reversal's own
reasoning. **Named follow-up (deferred, separate ticket, both panel models
converged on it independently):** demote only when
`equation_region_evidence` shows a display-equation region was FOUND
(`regions_total > 0`) and recovery FAILED to cover it
(`regions_covered < regions_total`) — a structural gate, not a
character-count cutoff, so it needs no invented threshold, and the 8.0%
no-region slice correctly falls into "never confirmed" rather than
"permanently stuck" under it. A future ticket should also measure the
false-positive rate this argument turns on before deciding whether even
that narrower gate should demote.

### Original argument (superseded by the above)

**Decision: yes**, the new kind joins the `pages_ok` chain (document status
demotes to `AUDIT_FAILED`), gets its own retire-then-readd reconciliation
block on reruns/resume, its own CLI print, and its own `final_result.error`
note — the identical shape as `UNRESOLVED_MATH_KIND`.

Argument: this repo's rule is that loss surfaces at every level — page
status, document status, metadata, CLI — not just one (CLAUDE.md, "No
silent content loss"). The ticket exists specifically because a math-font
page ships SUCCESS with zero surface today; landing only a page-level note
while leaving `DocumentStatus.SUCCESS` intact would still let a document
with real, known math loss report clean at the level most consumers
actually read (the CLI summary, the document-level `.error`). The PUA class
already made this call for the structurally identical situation
(unrecoverable native math, same failure mode, same consumer-facing
surfaces) — treating a stricter twin damage class more leniently than its
sibling would be an unprincipled asymmetry, not a considered choice.
Counter-consideration (rejected): "this is a metadata/plausible-prose signal,
noisier than PUA's, so under-report it as a WARNING-only note." Rejected
because a noisier signal is an argument for *tightening the detector*
(future work — see `MIN_MATH_CORRUPTION_GLYPHS`'s analogue is deliberately
absent here per criterion 5), not for hiding a known-lossy page from the
document-level bucket that exists precisely to make this kind of loss
discoverable without reading every page's own notes.

**What the review found wrong with this argument:** it never checked the
PUA precedent's trigger rate before mirroring its treatment. The two damage
classes share a failure mode but not a scale, and the scale is exactly what
determines whether "surface everywhere" or "surface everywhere except the
one bucket with no exit" is the correct application of the no-silent-loss
rule.

## Criterion 3 — no double-reporting

Guaranteed by construction: `math_font_unrecovered_detail` returns `None`
whenever `has_corrupt_math` or `has_unmapped_math_glyphs` is true, so it can
never fire alongside `UNRESOLVED_MATH_KIND` (PUA) or the corrupt-math-region
lane's own AUDIT_FAILED bucket. Covered by
`test_a_pua_page_never_also_raises_the_math_font_event` (end to end) and the
two pure unit tests preceding it.

## Criterion 5 — no new magic threshold

None introduced. Coverage is a direct region-count comparison
(`regions_covered == regions_total`), no ratio, no score cutoff.

## Second REVISE — the note's home, and status this as interim (design panel)

A design panel run on the fork found a real defect in the first REVISE:
the math-font note was appended to `final_result.error`. That field is
load-bearing — `cli.py:843` greps it for `LOST_CONTENT_NOTE`, and GH-177's
contract (`result.py:593-611`) documents it as "already `AUDIT_FAILED`".
A `success=True` document with a populated `error` is a state with no
name: a downstream reader that checks `error` before `status` — a
reasonable thing to write — gets exactly the full failure blast radius the
criterion-4 revision above chose not to impose, through a back door that
bypasses `status` entirely. Fixed: the note now goes into
`final_result.audit_notes` (an existing, currently-unused-at-document-level
list field on `EngineResult`) instead — additive, never mistaken for a
failure signal. Pinned by a new assertion in
`test_no_provider_leaves_the_math_uncovered_and_reported` that the note is
NOT in `.error` and IS in `.audit_notes`; demonstrated to fail without the
fix by reverting just that one hunk (1 of 19 tests fails, the exact one
asserting the placement) and restoring.

**#140 is NOT fully resolved by this ticket — this ships as an interim
observability patch.** The panel's shared objection, independent of the
split verdict on other points: the math-font signal is a *suspicion*, not
a confirmed loss. Every other note bucket in this reconciliation block
demotes (or, now, notes) because a checker actually saw something go wrong
on that page — a rejected reading, a fabricated URL, a truncated table. Font
presence alone is not evidence that anything was garbled; nobody has
measured this detector's false-positive rate. The trigger-rates log
(`docs/log/2026-09-02_p4m-trigger-rates.md`) establishes *prevalence*
(36.1% of the free lane) — it says nothing about how often that prevalence
corresponds to an actual reading defect. So this ticket makes a previously
silent loss visible; it does not establish that the loss is real often
enough, or precisely enough located, to justify failing anything on it.

**Named follow-up (not implemented here, both panel models converged on
it independently):** demote only when a display-equation region was FOUND
and the recovery attempt FAILED to clear the math-font run — i.e. gate on
`equation_region_evidence` showing `regions_total > 0` and
`regions_covered < regions_total`, not on raw `has_math_font_typesetting`
character presence. This is a structural gate, not a character-count
cutoff, so it needs no invented threshold (satisfying criterion 5 the same
way this ticket's coverage check does) — and the 8.0% no-region slice from
the trigger-rates log correctly falls into "never confirmed" rather than
"permanently stuck", because it never reaches the gate at all. A future
ticket should also measure the false-positive rate implied above before
deciding whether even that narrower gate should demote.

## Closes

Criteria 1, 2, 3, 5 hold as originally argued. Criterion 4 holds in its
twice-revised form (report via `audit_notes`, never `error`, never demote
— see above). This ticket is an interim observability patch: it makes a
previously-silent suspicion visible everywhere the PUA class is visible,
without asserting the suspicion is a confirmed defect. The demotion
question — for the general signal, and for the narrower found-but-
unrecovered-region gate the panel proposed — is deferred, not closed,
pending the `trigger_rates.py` extension named above (separate ticket).
