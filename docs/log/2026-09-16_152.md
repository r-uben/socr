## Part 1 — `rowize_from_word_list` column-gutter split

### Detector

`_detect_column_gutter(words)`: reuses `ALIGNED_RUN_GAP_MAX_WORD_SPACES`
(`born_digital.py`, existing measured constant) as a multiplier on the
page's own median word-gap width (`_median_word_gap`). Merges all word
x-intervals; a gap between merged intervals at or above that yardstick is a
gutter candidate. Requires **exactly one** such gap — zero means no split,
two-or-more falls back to the unsplit whole-page rowizer (fails closed
rather than guessing a 3+-column layout).

### False-positive guard

A gutter is only acted on if splitting at it produces two non-empty sides
AND both independently pass `_has_row_labels` (majority of rows carry a
non-numeric token) AND both independently produce non-empty output from
`_rowize_word_group`. Defeats:
- a single wide table's own label→value gap (right side has no label
  column of its own)
- a gap between two groups of value columns within one table (same reason)

Deliberately does NOT reuse `has_numeric_columns` / `_MIN_LANES_PER_ROW` as
the per-band gate, per the GH-152 plan's wave-3 ruling (that gate needs
three numeric lanes co-occupied per row; a genuine two-table page can be a
1- or 2-lane schema on either side). Confirmed by inspection: `_has_row_labels`
does not call either.

### Single-column byte-identity

Difference-pinned (not an absolute string pin): the same input run once
with `_detect_column_gutter` monkeypatched to always return `None` and once
unpatched, asserted identical. Done on a synthetic 4-lane single-table
fixture and on the real `tests/fixtures/table_repair/ce_like_p4.pdf`.

### Mutation testing

Reverted the fix in an isolated copy (source-canary-checked: `_detect_column_gutter`
absent post-revert). 6/9 tests fail without the fix; 3/9 (the false-positive
guards + one byte-identity check) correctly continue to pass — invariants,
not fix-dependent.

## Part 2 — the same detector at the `reconstruct_table_regions` rung

### The gap Part 1 alone left open

Built a real synthetic PDF (booktabs style, no ruling lines, two tables side
by side) and ran it through `BornDigitalDetector().extract_structured()`.
Still merged, despite Part 1 being in place: `reconstruct_table_regions()`
calls PyMuPDF's own **unclipped** `page.find_tables(strategy="text")` before
`rowize_from_word_list` is ever reached. That call sees both tables at once
and, when it builds a clean grid (no destroyed token — the check that would
otherwise reject it and fall back to Part 1's fixed rowizer), the merged
grid ships directly without ever consulting words or the rowizer.

This matches `docs/plans/gh152-side-by-side-tables/TICKETS.md`'s TICKET-A1
2026-08-13 retarget ruling verbatim: "wiring only the rowizer rung is a
measured end-to-end no-op." That plan predates this dispatch and was found
independently, from the code, before it was read.

### Fix

Refactored `reconstruct_table_regions` into a thin outer function plus
`_reconstruct_table_regions_for_words(page, words, *, clip=None, rejections=None)`
(the original body, now parameterised). The outer function runs the same
`_detect_column_gutter` / `_has_row_labels` guard used in Part 1 and, only
when it holds, calls the helper twice — once per band, each with
`find_tables(clip=_clip_rect_for_words(band_words), ...)` so a band's own
call cannot read text across the gutter — and returns the concatenation
only if BOTH bands produced at least one region. Any doubt falls through to
today's single unclipped call, unchanged. The destroyed-token fallback
inside the helper also now operates on band-scoped `words`, so it cannot
leak a word from the other band into its own numeric-scope check either.

Same binding constraint honoured: the band-accept gate is `_has_row_labels`
only, not `has_numeric_columns` / `_MIN_LANES_PER_ROW`.

Out of scope, as instructed: `born_digital.py`. Two regions are returned
left-then-right; `born_digital.py:1201`x re-sorts everything it collects by
`y0` alone, so cross-band left-to-right order is not delivered here — a
known remainder, same class as instructed, not attempted.

## Findings reported, not fixed here

### Duplicate content when a text block spans both bands — introduced by this change, and silent

This is a regression this change causes and is accepting, not a pre-existing
condition being merely documented. Measured directly: when a real PDF's own
block/line segmentation groups a row's left- and right-table words into ONE
`get_text("dict")` text block (observed on both a single-`insert_text`-per-row
fixture and a two-`insert_text`-per-row fixture — MuPDF's block segmentation
is geometric, not aware of two separate tabular environments),
`born_digital.py`'s overlap-suppress check measures each of the two narrower
band regions' coverage of that block INDEPENDENTLY (by design, to stop a
line being dropped because its words appear in an unrelated table elsewhere
on the page). Neither narrow band rect alone reaches the 50%
(`_REGION_COVERAGE_DROP`) threshold that a single wide pre-152 region used
to clear, so the block's lines survive as duplicate plain-text rows beneath
the two correctly-split markdown tables. Confirmed this did NOT happen
pre-fix on the identical fixture (one wide region covered the block fully) —
this is new, caused by A2's narrower per-band regions, not inherited.

**Nothing surfaces it.** Checked `born_digital.py`'s suppression path
directly (`~line 3708` onward): when no region clears
`_REGION_COVERAGE_DROP`, the block's lines are appended untouched — no
status flag, no note, no count is emitted anywhere to say suppression was
skipped. There is no page status, metadata field, or log line that would
let a downstream consumer notice this happened. That makes it
**silent-but-correct, not legible-by-construction** — "legible" was my
framing when I proposed this as a known remainder, and the measurement does
not support it as stated: nothing makes it visible, only the fact that
every value stays individually correct and correctly labelled makes it
*harmless* rather than *legible*.

Not fixed: fixing it needs either a change to `born_digital.py`'s coverage
check (explicitly denied for this ticket — "I am not granting it") or
returning fewer, wider-rect regions from `reconstruct_table_regions` in a
way that would require pairing left/right segments 1:1, which risks
mis-pairing when segment counts differ and reintroducing exactly the
rect-does-not-match-content misattribution class of bug this ticket exists
to close — team-lead confirmed this refusal is correct: duplication is a
strictly better failure than misattribution under this repo's cardinal
rule (a wrong number is worse than a redundant one), so the trade stands,
but the regression itself and its silence are recorded here rather than
downplayed. Team-lead is filing this as its own tracked issue.

### GH-418 (pre-existing, separately tracked) is a residual exposure

`_rowize_segment`'s per-row cell-assignment loop silently drops any word
that is neither in the label zone nor within snap radius of any lane — no
cell, no label, no note column, word vanishes. This is already open as
GH-418, found during #342, and #342 explicitly records two rejected fix
attempts (both regressed prose-page handling: pulling every off-lane word
into the nearest cell, or every word "between lanes", both wrongly grid a
prose page).

When `_detect_column_gutter` correctly finds the gutter, both A1 and A2's
band split give each side its OWN label zone and lane set before
`_rowize_segment` ever runs, so a band's own label words are never far
enough from its own boundary to trip the drop — measured: the headline
Part 1 and Part 2 tests both show every RightLab/LeftLab token present with
correct row attribution.

If `_detect_column_gutter` fails to find the gutter on a genuine two-table
page (for example: unusual PDF-generator line/block grouping, which this
session's own synthetic-fixture attempts hit twice before landing on a
courier single-insert-per-row shape that grouped correctly), the OLD,
unfixed drop still applies: a right-table label sitting far from every
left-table lane and outside the merged label zone can be silently dropped
while its value is glued into the nearest lane on the wrong row — which
matches the "RightLab entirely gone, value reattributed to the left label"
shape team-lead reproduced independently.

Not attempted here: it is a distinct root cause from GH-152's "unclipped
call merges two x-bands" (this is a snap-radius drop inside an ALREADY
correctly-scoped single table/band), it touches the core rowizer used by
every single-table page in the corpus (much larger blast radius), and #342
already tried and rejected two fixes for exactly this function. Reported to
team-lead as a STOP-and-report fork rather than guessed past. Recommendation
given: either file GH-152 as depends-on GH-418 for full closure of the
motivating page, or ship GH-152 now with this documented as a known,
separately-tracked residual (GH-418 already open, already has failed-attempt
history that any new fix must reckon with) — team-lead's call.

**Decision (team-lead, 2026-09-16): ship GH-152 now, option (b).** GH-418
stays separately tracked; blocking a working, measured fix on a known-hard
problem with two prior rejected attempts is the wrong trade. Stated
precisely, for anyone reading this later: **GH-152 closes the merge
whenever `_detect_column_gutter` fires. When it does not fire — measured
to happen, not hypothetical, hit twice while building this ticket's own
fixtures — the GH-418 drop still applies and the page can still
misattribute.** "GH-152 fixed" must not be read as "side-by-side tables
are safe" in general; it is safe specifically when the gutter is detected.
`docs/plans/gh152-side-by-side-tables/TICKETS.md` carries an explicit
`related: GH-418` cross-link, and GH-418's own issue should carry one back
to GH-152, so the dependency is discoverable from either end.
