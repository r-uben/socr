## What changed

`markdown_rows` (`src/socr/benchmark/table_exactness.py`) filtered empty cells
out of a row before building its `LabeledRow.values` tuple
(`values = [c for c in raw_values if _is_value(c)]`). Two rows with the same
value multiset but different gap positions — `['-1.0','1.0','28.1','']` and
`['2.5','0.5','','13.8']` — both compacted to three values and both matched a
three-value ground truth. A value shifted into an adjacent empty cell scored
as correct.

Fix: keep the row's raw column shape when building `LabeledRow.values` —
`positional_values = [c if _is_value(c) else "" for c in raw_values]` — instead
of compacting it. The compact `values` list is still used for the existing
control flow (`labelled_but_empty`, `orphan_rows` — "does this row carry any
real value at all") since those checks are about presence, not position.

`score_rows` was not touched. It already compares column-by-column,
`got.values[column] if column < len(got.values) else ""`, against
`want.values` from the ground truth. Ground truth (`native_rows_from_page`)
has no per-value x-position field yet — that lands in B3 — so it is still a
flat, compacted list of the values found. "Compare positionally against the
preserved markdown shape" (the ticket's wording) means exactly this: only the
*predicted* side keeps its gaps; the ground truth's flat order is read against
those gaps column-by-column rather than against a second compacted list. A
genuinely sparse ground-truth row (e.g. one value in a two-column row) still
matches a correctly-placed sparse prediction — the fixture's uncorrupted
"Other adjustments" row (`("0.5",)` GT, one value at markdown column 0) still
scores 100%, because `strip_presentation`'s empty-cell handling now leaves the
predicted row as `("0.5", "")`, and column 0 matches. The shifted corruption
(`("", "0.5")`) now fails at column 0, because the value moved to a position
the ground truth's flat order does not expect there.

This is deliberately the cheap fix the ticket calls for — no lane clustering,
no ground-truth position field. It is bounded by what B3 is scoped to add.

## `cells` semantics — did they change?

No. `ExactnessReport.cells` is computed in `score_rows` as
`report.cells += len(want.values)` for each ground-truth row — it counts
*ground-truth* values, never touches `predicted`/`LabeledRow` from
`markdown_rows`. `markdown_rows` only changed what `LabeledRow.values` holds
for the *predicted* side. So `cells` — the denominator `escalation_decision`
reports (`of {incumbent.cells} cells`) and the `candidate.exact > incumbent.exact`
comparison's scale — is unaffected.

What *does* change is `exact`: a shift-into-empty-cell case that used to score
as a match on the predicted side now correctly scores as a miss. That is the
intended effect — the metric now reports fewer false positives, on the
denominator it already had. `decide_escalation`'s accept rule
(`candidate.exact > incumbent.exact`) becomes more conservative in exactly the
direction the ticket describes: a candidate whose numbers are simply shifted
into a gap can no longer out-score an incumbent it doesn't actually improve on.
