# 2026-08-30 — TICKET-D1a: table judge ladder sidecar persistence + restore (GH-353)

## What changed

`src/socr/pipeline/orchestrator.py`:

- `_flush_page_sidecar`: added `"table_ladder_disposition"` to the payload
  dict — the bare `FailureMode` value string (`ps.table_ladder_disposition
  .value`) or `None` when the page never reached a ladder terminal (flag
  off, ladder ACCEPTED, or no tables on the page). Placed beside the other
  `PageState` decision flags already persisted there
  (`needs_ocr_enhancement`, `judge_rejected`, etc.). The per-table ladder
  audit events themselves needed no new plumbing: `page_events` already
  filters `state.events` by `page_num` and serialises `kind`/`engine`/
  `detail`/`data` (including `data={"table_id": ...}`) for every event on
  the page, ladder events included — B1 emits them through the same
  `AuditEvent` path every other distrust kind uses.
- `_restore_terminal_page_state`: after the existing flag restores, parses
  `meta["table_ladder_disposition"]` back into a `FailureMode` (or `None`)
  and sets `ps.table_ladder_disposition`, then replays every sidecar
  `audit_events` entry whose `kind` is in `TABLE_LADDER_EVENT_KINDS`
  (`table_ladder_accepted` / `_rejected` / `_unverified`) back into
  `state.events` as reconstructed `AuditEvent`s. Scoped to the ladder's own
  three kinds deliberately — restoring every persisted event verbatim would
  duplicate categories other tickets already re-derive fresh each run from
  `PageState` flags at assemble time (native fallback, corrupt-math-hybrid,
  etc.), not from the historical event log. All of this lives inside the
  same try/except that already wraps flag restoration ("best-effort: a
  flag-restore failure is non-fatal, the body text is already correct"), so
  a corrupt/unknown disposition string degrades to `None` rather than
  breaking the resumed run.

No changes to `_load_terminal_page` (D1b's job — REJECTED/UNVERIFIED pages
currently ship `status=WARNING` via C3's `_apply_ladder_disposition_guard`,
so the existing `status == SUCCESS` gate already refuses to skip them; D1b
adds the deliberate REJECTED-skips-anyway exception). D1a only makes the
restore path correct for whenever D1b (or a future direct caller) invokes
it.

## Why events are restored but not re-derived

`tables_trust.json` (`core/tables_trust.py:build_tables_trust`) and the
assemble-time metadata note (`_tables_trust_note`) are both derived from
`state.events`, unlike every other GH-353-adjacent bucket in
`_phase_assemble` (which reads `PageState` flags directly). Without
replaying the ladder's own events, a resumed page would keep its
disposition (via `ps.table_ladder_disposition`, which drives `pages_ok` /
`_table_judge_ladder_note`) but silently vanish from `tables_trust.json`
and lose its per-table reasons/details — the exact "trust entry" loss named
in the ticket's problem statement.

## Tests

New: `tests/test_ladder_sidecar.py` — 9 tests, fully hermetic (`_flush_page
_sidecar` / `_restore_terminal_page_state` called directly, no rung/witness
machinery reachable; `prepare_table_witnesses` / `run_table_ladder` /
`_build_table_judge_rungs` are patched to raise in the restore tests as a
sentinel that restore never re-judges).

- `TestSidecarPersist` (3): disposition serialises as the bare value;
  no-disposition case persists `null` with an empty `audit_events` list;
  two consecutive flushes of an unchanged state are byte-identical.
- `TestSidecarRestore` (6): disposition + both ladder events round-trip;
  `build_tables_trust`/`trust_note` on the restored state reproduce the
  original exactly; `_table_judge_ladder_note` reproduces exactly; a
  no-ladder-record sidecar restores `None`/no events (today's behaviour,
  unchanged); restore never touches witness/rung machinery even with a
  REJECTED disposition on the sidecar; a hand-corrupted disposition string

## Deviations / follow-ups

- No design deviations. The sidecar's existing `audit_events` serialisation
  already covered the per-table event payload; this ticket only added the
  missing page-level disposition field and the restore-side replay, rather
  than inventing a separate `table_ladder` sub-record as the ticket
  description sketched — the existing fields already satisfy "per-table
  results + page disposition" without duplicating data.
- D1b (wave 6, resume skip policy) is now unblocked: it can rely on a
  restored `ps.table_ladder_disposition` and replayed events being correct
  the moment its positive REJECTED-early-return starts letting
  `_load_terminal_page` skip those pages.
