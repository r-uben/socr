## What was built

### 1. `src/socr/math/detect_equations.py` (new)

Deterministic display-equation region detector using PyMuPDF geometry only — no model call,
no whole-page OCR.

Detection pipeline (conservative; a missed equation is preferable to a false-positive crop):

1. **Math-font page scan** (`page.get_fonts()`): collect font names matching `_MATH_FONT_RE`
   (CMMI/CMSY/STIX/…) from `born_digital.py`. Fast exit if no math fonts found on the page.
2. **Math-font span ratio** per line: a line whose spans (by character count) are ≥ 50 % from
   a recognised math font qualifies as a math-font line.
3. **Centering check**: a line's horizontal midpoint is compared to `page_width / 2`. Lines
   within `DISPLAY_CENTER_TOLERANCE_PT = 20.0` pt are display-equation candidates. Using
   page-width half (not text-column union midpoint) avoids the bias that prose blocks of
   varying width would introduce when computing a column midpoint dynamically.
4. **Equation-number confirmer**: a line matching `DISPLAY_EQ_NUM_RE` (`(3.4)`, `(A.1)`, etc.)
   is promoted regardless of centering — a reliable display-equation signal.
5. **Vertical merge**: adjacent candidate lines within `DISPLAY_MERGE_GAP_PT = 6.0` pt merge
   (same constant as `_REGION_MERGE_GAP_PT` in `recover.py`).
6. **Height filter**: merged regions shorter than `DISPLAY_MIN_HEIGHT_PT = 8.0` pt are dropped
   (rejects single-pixel artefacts).
7. **Padding**: `DISPLAY_PAD_PT = 4.0` pt added around each region before crop rendering
   (same semantics as `_REGION_PAD_PT` in `recover.py`), clipped to page bounds.

Named constants (all documented in module docstring with basis):
- `DISPLAY_MIN_MATH_SPAN_RATIO = 0.50`
- `DISPLAY_CENTER_TOLERANCE_PT = 20.0`
- `DISPLAY_MIN_HEIGHT_PT = 8.0`
- `DISPLAY_MERGE_GAP_PT = 6.0`
- `DISPLAY_PAD_PT = 4.0`
- `DISPLAY_EQ_NUM_RE` (equation-number pattern)

Crop-PNG naming: `equation_{n}_page{N}.png` under `equations/` in the doc output dir,
beside the `figures/` directory — mirrors `FigureExtractor._save`.

`EquationDetectionResult.detection_time_s` is the wall-clock time of the geometry pass only
(model-free), enabling the throughput harness required by GH-36a AC5.

## Splice_math validation gap — deferred to GH-36b

`splice_math` (`recover.py:207+`) performs ZERO LaTeX validation.  This is acceptable for the
corrupt-font case (native text is garbage; any non-empty LaTeX is an improvement; crop fallback
prevents mojibake reaching corpus).  For the clean-equation case (GH-36b), the native
linearised text is faithful, so an unvalidated/hallucinated LaTeX block would silently replace
correct content.  GH-36b must add the pylatexenc 1A structural gate before any splice.
The gap is now documented in the code comment on `splice_math` and in this log.

## Residual risk / notes for GH-36b

- **False-positive rate**: the centering check (page_width/2 ± 20 pt) may admit wide inline
  equations (e.g., a long denominator spanning most of the line) that happen to be centred.
  Mitigation: min_math_span_ratio=0.50 requires the majority of the line to be math-font, which
  excludes most inline prose; equation-number check is a confirmer, not a gate.
- **False-negative rate**: narrow display equations whose typeset line is narrow-centred but the
  bbox extends asymmetrically (e.g., due to a flush-right equation number) may fall outside the
  20 pt tolerance.  The equation-number confirmer addresses the numbered case; unnumbered narrow
  equations may be missed.  Per AC: a missed equation is acceptable at this phase (detection is
  conservative by design).
- **Corpus calibration**: DISPLAY_CENTER_TOLERANCE_PT and DISPLAY_MIN_MATH_SPAN_RATIO should be
  validated on a sample of real math-heavy papers before GH-36b enables default-on detection.
  The throughput harness (`detection_time_s`) provides the per-page timing data the AC requires.
- **GH-36b dependency**: the 1A structural validation gate (pylatexenc) must be in place before
  any splice into clean pages.  Without it, the splice_math function (which has no validation)
  cannot safely be called on clean-equation regions.
