# 2026-08-30 — TICKET-B2: table-scoped trust events (GH-353)

## What
`src/socr/core/tables_trust.py` learns the two ladder terminals and fixes the
bug the ticket names: `build_tables_trust` used to resolve *by page number
only*, so one table's PASS could erase another table's FAIL/¬S1 on the same
page (`core/tables_trust.py:216`, pre-fix).

- `TABLE_DISTRUST_KINDS` gains `"table_ladder_rejected"` /
  `"table_ladder_unverified"` (content problem / infra problem, per the
  design doc's own terminal split).
- `RESOLVING_KINDS` gains `"table_ladder_accepted"`.
- `build_tables_trust` now resolves **table-scoped** when the resolving event
  carries `data["table_id"]`: it clears only distrust events on that
  `(page_num, table_id)` pair, not the whole page. A resolving event with no
  `table_id` clears the whole page ONLY when its kind is in
  `WHOLE_PAGE_RESOLVING_KINDS` (currently just `table_escalation_accepted`);
  every other resolving kind without a `table_id` (including
  `table_ladder_accepted`) is a **no-op** — see the review-fix section below.
- `LADDER_TERMINAL_NOTES` — a fallback detail sentence for each terminal
  ("...not retryable" / "...retryable on resume", straight from the design
  doc's REJECTED/UNVERIFIED distinction) used only when the emitting event's
  own `detail` is empty, so a consumer never sees a bare kind token.

## Review fix (2026-08-30, same day): no-table_id ladder-accept must not clear the page
First cut treated every `RESOLVING_KINDS` member the same in the no-`table_id`
branch: any resolving kind with no `table_id` cleared the whole page. The
reviewer reproduced the defect this reintroduces — the exact bug class the
ticket exists to fix, just moved one level up:

```python
events = [
    AuditEvent(page_num=5, kind="table_ladder_rejected", data={"table_id": "1"}),
    AuditEvent(page_num=5, kind="table_ladder_accepted"),  # no table_id
]
# before the fix: untrusted_pages == [] — the REJECTED silently vanished
```

Safety rested entirely on B1 (unwritten at the time) always attaching
`table_id` to every ladder event — a discipline no contract or test enforced.
Fixed by replacing the blanket `else: resolved_pages.add(page_num)` with an
explicit allowlist, `WHOLE_PAGE_RESOLVING_KINDS = frozenset({"table_escalation_accepted"})`:
only a resolving kind IN that allowlist clears the whole page when
`table_id` is absent; every other resolving kind (including
`table_ladder_accepted`) resolves nothing without a `table_id`. Fails closed
(distrust survives an ambiguous accept) instead of failing open (distrust
silently erased). A genuine page-wide-ladder-accept shape, if ever wanted,
needs its own distinct kind with its own contract and test — not a piggyback
on optional `table_id` on the existing accept kind.

Added `test_a_page_wide_ladder_accept_with_no_table_id_is_a_no_op` (the
reviewer's repro, now green) and
`test_table_escalation_accepted_keeps_its_legacy_whole_page_clear`
(regression guard: the allowlist must not also silence the one kind that IS
supposed to keep whole-page semantics). The drift-guard test now also
asserts `TABLE_LADDER_ACCEPTED_KIND not in WHOLE_PAGE_RESOLVING_KINDS`.

## Design choice not spelled out in the ticket: import direction
The ticket flagged a layering question: A1 already owns the three kind
constants in `src/socr/judge/table_verdict.py`. I did **not** import them
into `core/tables_trust.py`. Two reasons:

1. `#175` (`docs/plans/orchestrator-decomposition/TICKETS.md:315`,
   `tests/test_package_layering.py`) already fought a `core -> tables`
   inversion once and left a standing rule ("tables/core must not import
   benchmark") plus a precedent against `core/` growing new upward edges.
   `judge/` already imports from `tables/` (`table_rung_ollama.py` imports
   `tables.extract`), so a `core -> judge` import would be one hop from a
   cycle the day `judge/` (or anything it imports) needs anything from
   `core/`.
2. Every existing entry in `TABLE_DISTRUST_KINDS`/`RESOLVING_KINDS` is
   already a bare string literal, not an imported constant — that's the
   file's own established convention, and it needed no invention.

I duplicated the three literal strings instead, with a comment pointing at
`judge/table_verdict.py` as the source of truth, and added
`test_ladder_kinds_match_judge_table_verdict` (in
`tests/test_gh95_tables_trust.py`) as a drift guard: it imports A1's real
constants and asserts they equal the literals used here, and that they land
in the right set. A typo in either file now fails a test instead of silently
diverging.

## Design choice: table-scoping applies to the whole `RESOLVING_KINDS` set,
not just the new kind (whole-page clearing does NOT)
`data["table_id"]` presence gates table-scoped resolution for *any* resolving
event — that part still generalizes, no per-kind branch needed. Whole-page
clearing, by contrast, is now an explicit per-kind opt-in
(`WHOLE_PAGE_RESOLVING_KINDS`, see the review fix above) rather than "every
resolving kind, whenever `table_id` happens to be absent". `table_escalation_accepted`
never carries a `table_id` today, so its behavior is byte-for-byte unchanged
(verified by the pre-existing GH-96 tests, all still green, plus a new
regression test pinning it explicitly).
