# 2026-08-30 — TICKET-C2: document aggregation + CLI surfacing (GH-353)

## What changed

`src/socr/pipeline/orchestrator.py` (`_phase_assemble` + the note-helper
section, no `cli.py` change needed — see "Why no cli.py change" below):

- `table_rejected_pages` / `table_unverified_pages` — two new buckets in
  `_phase_assemble`, computed from `p.best_output.failure_mode ==
  FailureMode.TABLE_REJECTED` / `TABLE_UNVERIFIED`. Keyed off
  `failure_mode`, deliberately **not** `.status` — C3's reviewer flagged
  that a page can legitimately arrive as `status=SUCCESS,
  audit_passed=False` (GH-161, `orchestrator.py:4347`), and C3's manifest
  guard only backfills `failure_mode` in that state without rewriting
  `.status`. A predicate reading `.status` would let a REJECTED/UNVERIFIED
  page slip through aggregation silently — the exact failure this ticket
  exists to close. Folded into `pages_ok` (`pages_ok = pages_ok and not
  table_rejected_pages and not table_unverified_pages`) alongside every
  other bucket in that function, so `DocumentStatus` demotes to
  `AUDIT_FAILED` (never a silent SUCCESS) whenever either fires.
- Both buckets added to the existing `if (failed_pages or ... ):` audit
  gate (no-op for them today — B1 owns emitting the ladder's own audit
  events at the gate; this ticket's console/CLI block is the
  document-assemble-time echo, matching the pattern every other bucket in
  that function already follows) plus two new `console.print` lines under
  the existing `if not self.config.quiet:` block, one per terminal (red for
  REJECTED — "not retryable", yellow for UNVERIFIED — "retryable on
  resume").
- `_table_judge_ladder_note(state)` — new static method, mirrors
  `_chart_detection_failed_note`/`_fabricated_url_note`: returns `None` on
  a clean run, else a one-liner naming affected pages per terminal and
  embedding the literal `FailureMode` value (`table_rejected` /
  `table_unverified`) so a `metadata.json`/CLI consumer can grep the exact
  terminal name, not a paraphrase. Wired into `final_result.error`
  (appended, never overwriting) the same way every other document-level
  note in that function is.

## Why no `cli.py` change

The ticket's file list names `src/socr/cli.py`, but tracing the existing
surfacing plumbing showed no code change was needed there:

- `metadata.json`'s `Status` already goes `PARTIAL` generically whenever
  `result.status != DocumentStatus.SUCCESS` and `has_text` is true
  (`_write_metadata`, unconditional on which bucket caused the demotion) —
  contract `Status` stays COMPLETED/PARTIAL/FAILED exactly as the ticket's
  scope note requires, and the note text rides in `meta.error` via
  `final_result.error`, which the new `_table_judge_ladder_note` already
  populates.
- `_print_summary` (called from `UnifiedPipeline.process()`,
  `orchestrator.py:549`) prints `result.error` verbatim, so the ladder note
  reaches the CLI summary line for free.
- `cli.py:481`'s existing `DocumentStatus.AUDIT_FAILED` branch ("Completed
  with warnings... output written; see audit_log.json", exit 0) already
  covers both ladder terminals generically — they are exactly the
  "content shipped, something needs review" shape that branch was written
  for, not the `LOST_CONTENT_NOTE` hard-failure shape.

Adding a `cli.py`-specific ladder branch would have duplicated logic that
already generalizes correctly; verified by driving `_phase_assemble` +
`_print_summary` directly in tests rather than assuming the plumbing works.

## Review fix (2026-08-30, post-3673a07): read the disposition, not `best_output`

**Ruling:** the reviewer flagged that the original predicate
(`p.best_output.failure_mode == FailureMode.TABLE_REJECTED/TABLE_UNVERIFIED`)
reads a seam production will never write to. C3's own decision log
(`docs/log/2026-08-30_ticket-c3.md:93-95`, "Why inert today") contracts B1 to
set `PageState.table_ladder_disposition` and rely on
`_apply_ladder_disposition_guard` (`core/manifest.py`) to enforce it — and
that guard demotes only the finalized COPY it returns from
`_winning_page_output`/`finalized_page_outputs`, **never** `best_output`
itself (the #252 round-1 rule: mutating a shipped attempt's
`audit_passed`/`failure_mode` in place would make assemble discard the
page's text — the same discipline C3's own decision log states explicitly).
So a page whose disposition is REJECTED/UNVERIFIED but whose `best_output`
was never independently stamped (the expected steady-state once B1 lands)
would sail through `_phase_assemble` as a clean SUCCESS — precisely the
silent-loss failure GH-353/this ticket exists to prevent. This is settled by
C3's own artifacts, not a fresh design question, so no `/consilium` panel was
needed — it is a direct read of the contract C3 already wrote and committed.

**Fix applied**, `src/socr/pipeline/orchestrator.py`:
- New module-level `_table_ladder_terminal(p) -> FailureMode | None`
  (defined just above `class UnifiedPipeline`, alongside the module-level
  `_LADDER_TERMINAL_MODES` constant): reads `getattr(p,
  "table_ladder_disposition", None)` FIRST — the durable, pre-guard
  `PageState` signal, matching how every other bucket in `_phase_assemble`
  already reads `PageState` flags rather than a finalized copy — and falls
  back to `p.best_output.failure_mode` only when no disposition is set.
  When both are present and disagree, the disposition wins, so a page lands
  in exactly one bucket.
- `table_rejected_pages` / `table_unverified_pages` and
  `_table_judge_ladder_note` both now call this one shared predicate instead
  of duplicating the `best_output.failure_mode` read, so the bucket
  computation and the note can never disagree about which pages are
  affected.
- Kept `best_output.failure_mode` as the documented fallback (belt-and-
  braces under no-silent-loss) rather than deleting it: it still catches a
  page where some future caller stamps the terminal directly onto the kept
  attempt without going through the disposition attribute at all.

**Tests reworked** (`tests/test_ladder_status_surfacing.py`, now 11 tests):
added `_inject_disposition`/`_inject_clean_output` helpers that set
`PageState.table_ladder_disposition` while leaving `best_output` an ordinary
passing attempt (`status=SUCCESS`, `audit_passed=True`,
`failure_mode=NONE`) — the exact production shape the manifest guard leaves
it in. This is now the PRIMARY injection path for every
document-status/metadata/CLI test. Kept one `_inject_failure_mode_only` test
for the documented fallback path (including the GH-161 shape), and added
`TestDispositionPrecedence::test_disposition_wins_over_conflicting_failure_mode`
proving precedence and single-bucket membership when both are set and
disagree.
