# GH-773 fix: HTML-entity decode gap in table-verification numeric-token gates

Branch `fix/773-decode-gap-sites`, off `origin/main@6a151b2`. Implements the ranked
fix order from `docs/log/2026-09-16_773-census.md`.

## Decision: sink fix via a shared helper, unescape-only (not `_normalize_cell`)

Three options were on the table: (a) fix the shared sink
(`_numeric_multiset_from_tokens`) directly, (b) fix each call site individually,
(c) split unescape-only at the sink from the dash-strip at candidate sites.

Chosen: **(a), but at a slightly lower level than the sink itself.** The census's
own §4 structural note undercounted which sites actually reach the sink — tracing
the real source found `header_cut.py:238` (`_emitted_header_tokens`, rank 4) also
routes through `_numeric_multiset_from_tokens`, and `witness.py:392`
(`_corroboration_contradicted_indices`, rank 3) routes through it via
`_numeric_tokens_from_text`. But two functions reimplement the raw
`_NUM_TOKEN_RE`/`_NUMERIC_RE` check inline rather than calling
`is_numeric_token`/the sink (`_numeric_tokens_from_text` used by row-pairing and
witness.py; `_output_header_numeric_tokens`, rank 8), and `header_repair.py` had
two more inline reimplementations (`detect_header_column_collapse`,
`_first_data_row_idx`, rank 5/6) plus the rank-7 guard.

Rather than duplicate a decode step at each of these, a single helper
`_decoded_numeric_candidate(tok) = strip_presentation(html.unescape(tok))` was
added to `native_verifier.py`, and every one of `is_numeric_token`,
`_normalize_numeric_token`, `_numeric_tokens_from_text`,
`_output_header_numeric_tokens` was refactored to route through it (or, in
`header_repair.py`, refactored to call `is_numeric_token` directly instead of
reimplementing the regex check). This makes `is_numeric_token` — already the
module's public predicate — the single point of truth, and every ranked site is
either fixed by calling it or fixed transitively by calling
`_numeric_multiset_from_tokens`, which calls it internally.

`html.unescape` alone is not sufficient: `html.unescape('&minus;9.9')` decodes to
`'−9.9'` (U+2212 MINUS SIGN), which the ASCII-anchored `_NUM_TOKEN_RE` does not
match. `strip_presentation`'s Unicode-minus-to-ASCII fold has to run AFTER the
unescape, not before (an entity has nothing to fold before it's decoded). Hence
`_decoded_numeric_candidate` composes both steps in that order.

**Not `_normalize_cell`** (`html.unescape(raw).rstrip(_TRAILING_DASH_CHARS)`,
already used by the #679/#690/#766/#768/#770/#772 ALREADY-FIXED sites). Measured
below: the trailing-dash strip is not inert on native tokens, so composing it
into every numeric-token predicate — including the ones read from native
PyMuPDF words — would silently change native-side comparisons this ticket has no
mandate to touch.

## The `1990-` measurement (native-side inertness of the chosen fix)

Team-lead flagged that `_normalize_cell`'s dash-strip half is NOT inert on native
tokens: `'1990-'` → `'1990'` changes `is_numeric_token`'s verdict. Measured
directly, before choosing the approach:

```
is_numeric_token('1990-')                        == False   (pre-ticket baseline)
is_numeric_token(html.unescape('1990-'))          == False   (unchanged)
is_numeric_token(_decoded_numeric_candidate('1990-')) == False   (unchanged, this ticket's fix)
is_numeric_token('1990')                          == True    (unaffected control)
```

`1990-` has no HTML entity to decode, so `html.unescape` is a no-op on it either
way, and the anchored `_NUM_TOKEN_RE` rejects a trailing `-` regardless (the
regex has no trailing-dash allowance). This ticket's fix (`html.unescape` +
`strip_presentation`, no `rstrip(_TRAILING_DASH_CHARS)`) does not introduce the
regression the team-lead warned about — pinned as a **difference of none**, not
an absolute value, per `tests/test_gh773_decode_gap.py::test_negative_control_native_trailing_dash_token_is_pinned`.
CI has no provider dependency in this codepath either way (pure string logic,
no VLM call), so this holds identically in CI and locally.

### Rank 7 in detail — resolving census §5 item 2

The census could not settle whether `header_repair.py:148`'s severity is real,
because fixing it alone doesn't change `_repair_too_narrow_spanning_header`'s
outward return value — confirmed here directly. With the fixture below and the
guard's real, unmocked neighbour `_native_label_lane` (an UNRANKED, un-fixed
function that matches a label against native words without decoding):

```
grid = [
    ['', 'Group', '', ''],
    ['', v1, '', v2],
    ['', '(1)', '(2)', '(3)', '(4)'],
    ['row', '10.0', '11.0', '12.0', '13.0'],
]
plain  (v1='1.5', v2='2.0')    -> _repair_too_narrow_spanning_header(...) == None
entity (v1='&#49;.5', v2='&#50;.0') -> == None   (both before AND after this fix)
```

Reverting ONLY the `:148` guard (back to the raw regex check, `is_numeric_token`
elsewhere intact) leaves this fixture's result at `None` for both plain and
entity — **a full-function test does not distinguish pre/post-fix behaviour for
this rank**, because `_native_label_lane` independently returns `None` one step
later regardless of the guard's state (out of scope; not in the census's ranked
list).

To pin the ONE behaviour this ticket's diff actually changes — whether the
guard itself recognizes an entity-encoded numeric secondary band as body data —
`_native_label_lane` is monkeypatched to a fixed lane index that clears the
later arithmetic checks, isolating the guard. With that stub:

```
plain  -> None   (guard fires: numeric secondary band correctly refused)
entity, guard fixed   -> None   (guard fires, symmetric with plain)
entity, guard reverted -> a repaired grid (NOT None) -- the body-data row gets
                           restructured as a spanning header
```

This confirms the census's structural note (team-lead's instruction: "`:148` is
inert only because its neighbours are broken the same way") is correct at the
current, real-`_native_label_lane` state of the code — a bare full-function test
would be unguarded for this rank, as flagged in advance — but the diff is real
and observably dangerous (restructures a body data row as a header) once the
unrelated `_native_label_lane` gap is factored out, so it ships with rank 6 as
instructed. `_native_label_lane`'s own decode gap remains open and out of scope
for this ticket.
