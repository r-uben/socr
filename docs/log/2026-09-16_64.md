# 2026-09-16 — GH-64: flag a tabular-looking page that fell silently to native

## What changed

PP-6 (GH-54) narrowed table routing to the lane-cooccupancy gate
(`has_numeric_columns`, `_MIN_LANES_PER_ROW >= 3`). That gate structurally
cannot reach a 2-column, whitespace-aligned, borderless label|value table —
there is only one numeric lane per row, never three. Such a page now falls to
native prose with its row × column grid unreconstructed, and nothing recorded
it: `PageAssessment.notes` alone reaches nothing the pipeline reads
(`orchestrator.py:9605-9609`'s own comment says so).

Fix, mirroring the #136 / #217 / #140 shape exactly:

1. `_detect_columnar_numbers` — the pre-PP-6 single-token-line-ratio
   heuristic, byte-identical to the version PP-6 (`dfbd317`) deleted — is
   restored in `born_digital.py` as a **private, audit-only** static method.
   It is never called from `_detect_tables` (the sole routing gate); it is
   called only inside `_assess_page_signals`, guarded on `not has_tables`, to
   compute `PageAssessment.possible_table_structure_not_reconstructed`.
2. `state.py::apply_born_digital` copies the flag onto
   `PageState.possible_table_structure_not_reconstructed` with the same
   `getattr(pa, ..., False)` form as its `has_encoding_hygiene_suspect` /
   `has_unrecovered_symbol_glyphs` neighbours.
3. `orchestrator.py::_agentic_native_page` appends a third `AuditEvent`
   (`kind="possible_table_structure_not_reconstructed"`) to `state.events`,
   in the identical shape as the #136 and #217 blocks already in that
   function — the seam that turns a PageState flag into something the page
   sidecar carries.

## Criterion 1 — the defect reproduced and flagged

Synthetic fixture: single-word labels at x=72, numeric values at x=450, 20
rows, no ruled lines. PyMuPDF's own line grouping splits each row across the
gap into two single-token lines (verified empirically: `page.get_text("text")`
on the fixture yields `"Alpha\n0.143\nBeta\n0.571\n..."`), so 40 single-token
lines out of 41 non-empty lines — well past the heuristic's `>=15` count and
`>50%` ratio floors. `has_tables` is `False` (one numeric lane per row, gate
needs three); `possible_table_structure_not_reconstructed` is `True`; a note
is appended to `PageAssessment.notes`; the flag survives
`apply_born_digital` into `PageState`; a call to the real
`_agentic_native_page` appends exactly one `AuditEvent` of the new kind to
`state.events`, and the page still ships `PageStatus.SUCCESS` (report-only,
never demoting — see criterion 4/scope-limit 2 below).

## Criterion 2 — negative case tested as hard as criterion 1

Two negative fixtures: ordinary justified prose (`insert_textbox`, multi-word
wrapped lines) and the detector's own standard academic-paper fixture shape
(8 hand-typeset multi-word lines × pages). Neither flags.

**One documented exception, not a criterion-2 failure but worth stating
plainly — WIDENED after review.** The ticket requires reusing
`_detect_columnar_numbers` **verbatim** ("do not write a new ratio,
row-count cut, or lane threshold"). That heuristic is *itself* PP-6's own
subject: its docstring and `TestLaneCooccupancyRoutingGate` in
`test_born_digital.py` document that it false-fires on chart-axis tick
columns (single x-lane, many single-token lines). Reusing it byte-identical
therefore inherits that exact false-positive class by construction — I did
not narrow it with a new threshold, because the ticket forbids exactly that.

Review (2026-09-16) found the inherited class is **broader than chart axes
alone**: two independently-built synthetic probes (the reviewer's and the
team lead's) both found that book-index pages (term|page-number pairs — also
the shape named in backlog item #213, "book indexes are routed to table
reconstruction") and bare numbered-list markers (`"1."`, `"2."`, ...) trip
the same flag. The actual shared property is **single-token-line-heavy page
furniture**, not "chart axes" specifically — anything whose lines are mostly
one token (tick labels, index terms, index page numbers, list markers)
matches the `>=15` / `>50%` profile regardless of whether it is chart-axis
content. `TestKnownFalsePositiveClassInherited` now pins three instances of
this class (chart-axis, book-index, numbered-list) rather than one, and its
docstring states the class in those broader terms.

**No trigger rate is claimed.** The two review probes disagreed with each
other on other fixtures (a TOC fixture flagged on one run and returned
`False` on the other; a multi-token label|value control that was expected to
flag did not on at least one run) — neither probe's synthetic fixtures were
established as faithful to real corpus pages, so no rate estimate from
either is trustworthy. This ticket documents that the false-positive class
exists and is broader than first stated; it does not measure how often it
fires on the real corpus.

**Named follow-up (deferred, not implemented here):** measure the corpus
trigger rate of `possible_table_structure_not_reconstructed`, the same way
`docs/log/2026-09-02_p4m-trigger-rates.md` measured the equation-lane
signal. That measurement — not a synthetic-fixture guess — is what would
justify either narrowing the predicate (a change this ticket's own scope
forbids) or promoting the flag beyond report-only. GH-140 shipped the same
night with its demotion removed for exactly this reason: an unmeasured rate
cannot justify a stronger signal.

## Criterion 3 — no double-reporting

Guaranteed by construction: the detection call is `not has_tables and
self._detect_columnar_numbers(page)`, so a page that already routed to table
handling can never also carry this flag. Pinned with the same dense
5-column × 6-row forecast-table fixture PP-6's own suite uses for its
`has_tables=True` regression guard.

## Criterion 4 — no new magic threshold

None introduced. `_detect_columnar_numbers` is the exact pre-PP-6 body
(`>= 15` single-token lines, `> 0.50` ratio) — an AST diff of the method as
restored against `dfbd317^` shows the only difference is the docstring; the
executable heuristic is unchanged.

**2026-09-16 correction to this claim's testing (tests-only, no source
change).** The original test,
`test_detect_columnar_numbers_is_byte_identical_to_pre_pp6`, was
mislabelled and under-proved: the source is not byte-identical (the
docstring was rewritten), and it only recomputed the formula against ONE
fixture that flags overwhelmingly far from either boundary — mutating
`>= 15` to `>= 10` or `> 0.50` to `> 0.30` left it passing. It has been
renamed to `test_detect_columnar_numbers_matches_the_pre_pp6_thresholds`
with a docstring that states the narrower, true guarantee, and a new class,
`TestPredicateThresholdsPinned`, was added with four boundary fixtures built
with an exact, controllable single-token/multi-token line count
(`_create_boundary_pdf`): 14 vs 15 single-token lines at a fixed high ratio
(pins the count floor), and 15 single-token lines with 15 vs 14 padding
lines giving a ratio of exactly 0.50 vs ~0.517 (pins the ratio floor, since
the check is strictly `>`). Each fixture's expected result was verified
empirically against the live detector before the assertion was written.
Mutating `>= 15` to `>= 10` flips the count-floor boundary fixture from
`False` to `True`; mutating `> 0.50` to `> 0.30` flips the ratio-floor
boundary fixture from `False` to `True` — both confirmed by direct
before/after runs against the mutated source, restored afterward
(byte-identical, no diff). The pin is now load-bearing, not fictional.

**No status demotion**, per the ticket's second hard scope limit. GH-140
shipped the same night with its demotion removed after review measured a
36.1%-vs-2.4% trigger-rate gap against its precedent; nobody has measured
this signal's rate either. Report via `AuditEvent` + `PageState` field only;
`PageStatus` stays `SUCCESS`, `DocumentStatus` is untouched. If a future
ticket wants to demote, it needs its own trigger-rate measurement first —
not argued here, not implemented here.

## Criterion 5 — routing byte-identical

`_detect_tables` (the sole routing gate) is unmodified — `_detect_columnar_
numbers` is a new sibling method, never called from it. Demonstrated two
ways: (a) monkeypatching `_detect_columnar_numbers` to unconditionally
return `False`, then `True`, and asserting `has_tables` is identical to the
unpatched baseline in both cases (`TestRoutingByteIdentical`); (b)
re-running the exact two PP-6 fixtures (`chart_axis`, `dense_forecast`)
through the detector and asserting the same `has_tables` values PP-6's own
suite pins.
