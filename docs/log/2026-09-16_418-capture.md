# GH-418 step 2/2 — capture the orphan word into the trailing column

Branch `fix/418-orphan-capture`, off `origin/main@daa7a6f`. Continues step 1
(`docs/log/2026-09-16_418-event.md`, PR #788) and implements the panel ruling
in `docs/log/2026-09-16_418-design.md` (Option 3: surface then repair).

## What changed

`_rowize_segment` (`src/socr/tables/reconstruct.py`) now computes, per row,
`is_data_row = len(row_numeric_lanes) >= 2` — the same predicate
`_looks_tabular` (`reconstruct.py:978`) already uses to call a row a "data
row", applied one step earlier and over the same snap rule the lane-cell
branch already uses. An orphan word (further than the snap radius from every
lane) on a row that clears this gate is appended to `orphan_marginals` (the
trailing column) instead of being deleted. A row below the gate (sparse, or a
header) still deletes the word and, when `orphan_drops` is wired, still
records it — this residual is the panel ruling's explicit requirement, not a
gap left by the fix.

No new threshold was introduced; the `>= 2` gate is reused verbatim from
`_looks_tabular`, per the ruling's instruction that the gate is measured and
not open for re-litigation this ticket.

## Decision: reuse `orphan_marginals`, not a new column

Reused GH-461's existing trailing column rather than adding a second one.
Evidence:

1. The design note's "What you are building" section names `orphan_marginals`
   as the target column directly — this reads as the directive, not merely a
   suggestion.
2. Both a GH-461 margin note and a GH-418 captured qualifier are the same
   *kind* of thing from a downstream consumer's perspective: an annotation
   riding along a row, not a value. Splitting them into two trailing columns
   would ask every consumer (the markdown renderer, `_clean_grid`,
   `_prepend_header_band`'s own note column) to distinguish two annotation
   columns with no behavioural difference between them.
3. A second column would require threading a second sideband through
   `_clean_grid`'s "drop iff every row's trailing cell is empty" rule and
   through `_prepend_header_band`'s own band-note column, which already
   aligns structurally with the single trailing column. That's strictly more
   surface for the same outcome, with no measured defect motivating it.
4. No defect was measured that a shared column would cause (e.g. no fixture
   in the design note or in this ticket's own new tests ever needed to tell
   a GH-461 note and a GH-418 capture apart in the same cell) — this is
   because a capture inserted alongside a folded marginal note requires two
   independent sources on the SAME row, which none of the measured corpus
   or the constructed worst-case fixtures exhibit.

If a real corpus case later needs to distinguish a folded margin note from a
captured orphan qualifier in the same row's trailing cell, that's new
evidence for a follow-up ticket — not a reason to split the column now.

## The row-loss regression: mechanism, fix, and why it stays in scope

**Mechanism.** `_clean_grid` (shared, NOT modified by this ticket — it is
also called on an unrelated native-`find_tables` grid shape at
`reconstruct.py:278`) peels a leading row via
`while g and _is_runhead(g[0]): g = g[1:]`, where `_is_runhead` matches the
row's whole joined text (all cells, including the trailing column) against
`_RUNHEAD_RE` (`jou[rm]nal|econom|review|quarterly|econometrica|\([\d/]{3,5}\)`)
to strip a page running-head swept into the grid. A captured orphan word can
supply exactly this vocabulary: capturing "Journal" (from a reference
citation's journal name) into a leading data row's trailing cell makes that
row's joined text match `jou[rm]nal`, so `_clean_grid` silently deletes the
**entire row** — not just the word, the row's real numeric values too. That
is strictly worse than the pre-ticket behaviour (word-only drop) and the
same prose-page regression class #342's two prior attempts were rejected
for. Confirmed this is real, not cosmetic: the row that "Fama, 1992, 427,
12" disappeared with it.

**Fix.** `_clean_grid`/`_is_runhead` were not touched — they are shared with
the unrelated native-table caller, and rewriting their semantics was outside
this ticket's write ownership regardless. Instead, the capture site in
`_rowize_segment` now checks, before appending a word to `orphan_marginals`,
whether doing so would make the row's joined text (label + lane cells +
the trailing column with this word added) match `_RUNHEAD_RE` via
`_is_runhead` — reusing the existing regex/function, no new heuristic. If it
would, the word is refused capture and falls through to the pre-existing
drop+`orphan_drops` branch instead, exactly as if the `>= 2` gate had not
been cleared. The row survives; only the one colliding word stays a visible,
recorded drop rather than a capture.

Verified on the exact repro (5-row reference-citation fixture, words
identical to the one sent to team-lead): with the guard, all 5 rows survive
with real values intact; "Journal" and "Econometrica" (the two words that
would trigger `_RUNHEAD_RE`) are refused and recorded in `orphan_drops`;
"Finance" and "Vol" (same rows, non-colliding words) are still captured
normally.

**Why this is in scope, not a design-panel question.** The fix is entirely
inside `_rowize_segment`'s own capture decision (the file/function already
under this ticket's write ownership) and does not touch `_clean_grid`,
the snap radius, or the prose guard — the three things explicitly
off-limits. It doesn't change the disposition question the panel already
settled (capture vs. drop as a category); it adds one more reason a specific
capture is refused, on top of the `>= 2` gate, using a mechanism the ticket
was already permitted to use (`orphan_drops`).

Team-lead's suggested mechanism ("the capture widens the grid, which
plausibly changes what `_is_runhead` sees for row 0") was correct in
substance; the actual trigger is more specific — the row need not be row 0
of the whole page, only row 0 of whatever `_clean_grid` sees after
`_prepend_header_band`, and it's about the row's *content* matching
`_RUNHEAD_RE`, not merely the grid's width changing.

## Mutation testing

Isolated copy at `/tmp/socr-418-mutation` (`src` + `tests` + `pyproject.toml`
copied out of the worktree, per repo convention). Provenance confirmed
before trusting any result — and this is where the earlier "confirmed on
daa7a6f" claim broke:

```
cd /tmp/socr-418-mutation && ~/venvs/socr/bin/python3 -c \
  "import sys; sys.path.insert(0, 'src'); import socr; \
   assert socr.__file__.startswith('/private/tmp/socr-418-mutation/'); \
   print(socr.__file__)"
```

**Trap found:** `pyproject.toml`'s `[tool.pytest.ini_options] pythonpath =
["src"]` makes pytest insert `<rootdir>/src` at the FRONT of `sys.path`
based on rootdir discovery (nearest `pyproject.toml` to the invoked cwd) —
this wins over a `PYTHONPATH` env var set from outside. Running `pytest`
with `PYTHONPATH=/tmp/socr-418-mutation/src` while `cd`'d into the worktree
silently tests the WORKTREE's own source, not the mutation copy — which is
exactly how the earlier wrong "confirmed on daa7a6f" claim happened. Fix:
copy `pyproject.toml` into the isolated copy too, and run pytest with cwd
INSIDE the isolated copy, so its own `pythonpath = ["src"]` resolves to the
copy's `src`, not the worktree's.

**Corollary on the provenance canary itself**: the `socr.__file__` check above
only closes this hole when it runs INSIDE the pytest process (e.g. a test
that asserts `socr.__file__`), not as a separate `python -c` invocation run
beforehand. A standalone `python -c` has its own `sys.path` resolution and
will happily report the mutated copy's path while the pytest process, run
moments later with a different cwd/rootdir, silently imports the worktree
instead — which is exactly what made the earlier ad hoc `python -c`
provenance checks look clean while the actual mutation runs were wrong. A
canary that runs outside the process under test decorates the report; only
one that runs inside it guards.

## Residual-loss contract (explicit, not implied)

A word further than the snap radius from every lane is captured into the
trailing column IF AND ONLY IF its own row already has `>= 2` numeric lanes
populated. Two cases still delete the word and still record it via
`orphan_drops`/`orphan_word_dropped`:

- **Single-lane (sparse) rows** — a row with 0 or 1 populated numeric lanes.
  The word is deleted from the grid; `orphan_drops` still names it
  (`{"word", "x", "y"}`), and step 1's audit/event surfacing is unaffected.
- **Header rows** (inside the same y-segment, not `_prepend_header_band`'s
  separate multi-line-header path) — 0 numeric lanes by definition, same
  outcome as above.
- **A word that would make its row match `_clean_grid`'s running-head
  pattern** (`_RUNHEAD_RE`) if captured — regardless of the `>= 2` gate.
  This is the row-loss regression above: refusing capture here is what
  keeps the row itself alive. The word is deleted and recorded via
  `orphan_drops`, same as the other two residual cases.

This is the panel ruling's explicit design, not a limitation of this patch:
the `>= 2` signal is what separates a genuine table row from prose, and rows
that don't clear it get no benefit of the doubt. The running-head refusal is
this ticket's own addition to that residual, added because the alternative
(capturing unconditionally) traded a smaller, visible loss for a larger,
silent one — exactly the class of regression this ticket exists to prevent.
