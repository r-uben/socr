# 2026-09-16 — GH-783: positional clause for `_has_row_labels`

## What changed

`src/socr/tables/reconstruct.py::_has_row_labels` (GH-152's false-positive guard for the
side-by-side table split) previously asked only "does any non-numeric token appear in this
row". A token that fails `_NUM_TOKEN_RE` for any reason — not just being a genuine label —
counted, including a value carrying a significance marker (`0.253***`) or an `n.a.` cell.
Verified on `main@1fb15a3`: a value-only band whose cells carry `***` markers read as `True`
(has its own label column), defeating the guard on a corpus-realistic case.

Added the plan's positional clause (TICKET-A1): a non-numeric token only counts as a label if
it sits strictly left of the band's own leftmost numeric **lane**, and requires that lane to
recur across at least `_MIN_TABLE_ROWS` rows before it counts as a lane at all — plus an
absolute `_MIN_TABLE_ROWS` floor on the labeled-row count (previously only a
`_MIN_DATA_ROW_FRAC` fraction).

## "Leftmost numeric lane" resolved to

A CLUSTER, not a single token's x0. Numeric token x0s are clustered with `_adjacent_lane_of`
(the same greedy-adjacency clustering `has_numeric_columns` already uses elsewhere in this
file — reusing the clustering *primitive*, not the forbidden `has_numeric_columns` /
`_MIN_LANES_PER_ROW` per-band *gate*). A lane only counts as "numeric" if it recurs across at
least `_MIN_TABLE_ROWS` distinct rows (reusing the existing `_MIN_TABLE_ROWS` constant for
"must recur this many rows", the same semantic GH-248's column-like-lane logic already uses).
The leftmost such qualifying lane's minimum x0 is the boundary.

Why not the simpler "global minimum numeric x0"? That collapses to the same value as the
leftmost lane's min in the common case, but breaks under an accidental one-off numeric token
sitting IN the label column (e.g. a stray row-ID number): that single token would found its
own one-off "lane" at the label column's own x, dragging the boundary left and making every
OTHER row's genuine text label read as sitting at-or-right-of the boundary — invisible to the
positional check. Requiring lane RECURRENCE excludes a one-off token from founding a lane.
Confirmed load-bearing by mutation (see below): a naive global-min implementation fails
`test_one_off_numeric_label_does_not_blind_the_positional_check`.

No new tolerance constant: the boundary comparison is a plain `<` against the lane's own
minimum x0 (not `<=` with a margin) — a label with a slightly larger x0 than an in-lane value
would need to justify its own constant, and no such case appeared in-corpus, so none was
invented.

## `_MIN_TABLE_ROWS` row-count floor

Added `labeled >= _MIN_TABLE_ROWS` alongside the pre-existing `_MIN_DATA_ROW_FRAC` fraction
check (kept, not replaced — the fraction test already exercised the "majority" semantic
documented on this function before this ticket). The plan's text ("in at least
`_MIN_TABLE_ROWS` rows") reads as an absolute floor distinct from the fraction; a small band
could clear the 0.5 fraction with only 1-2 labeled rows, below the 3-row structural minimum
this file uses everywhere else for "this is a real recurring row pattern". Confirmed
load-bearing by mutation: reverting only the floor (keeping the fraction) fails
`test_below_min_table_rows_labeled_is_not_recognised`, whose fixture is built so the fraction
alone (0.5) would pass without the floor.

## Tests — `tests/test_gh783_row_label_position.py`

Both directions per the ticket brief:

- `TestStarredValueColumnDoesNotFakeALabelColumn` — the bug: a unit reproduction of
  `_has_row_labels` on a starred value-only band, and an end-to-end reproduction through
  `rowize_from_word_list` (a single table whose SD-group has two clean numeric columns plus a
  third, starred column must stay ONE region, not split into two).
- `TestGenuineSideBySideTablesStillSplit` — **a CONTROL, not a guard**: it passes both with
  and without this fix (mutation 1 above leaves it green), because `_has_row_labels` already
  returned `True` for both bands on the pre-fix code. It exists to prove tightening the
  positional clause did not defeat GH-152's own split, not to catch a GH-783-shaped
  regression — a reader wanting a test that FAILS on this ticket's bug should look at
  `TestStarredValueColumnDoesNotFakeALabelColumn` instead.
- `TestIncidentalNumericTokenInARealLabelColumn` — a real label column with one row's
  incidental numeric label token (`"3"`) is still recognised as having row labels.
- `TestMinTableRowsFloorIsEnforced` — the row-count part of the clause, isolated from the
  positional part, with a fixture sized so the pre-existing fraction check alone would pass.

## Mutation results

Three isolated mutations, run against copies outside the repo (never a committed
`socr.__file__` assertion — only in these throwaway scripts):

1. **Revert the whole positional clause** (restore the pre-fix `_has_row_labels` body):
   `test_unit_starred_value_only_band_has_no_row_labels` and
   `test_wide_single_table_with_starred_value_group_is_not_split` FAIL (2 == 1 assertion
   trips, reproducing the exact bug). The other 4 tests still pass — unaffected by this
   clause, as expected (2 genuine-tables/incidental-label tests don't depend on it changing
   outcome; see below for why).
2. **Revert only the `_MIN_TABLE_ROWS` floor** (keep the fraction check alone):
   `test_below_min_table_rows_labeled_is_not_recognised` FAILS. All other 5 pass.
3. **Revert only the lane-recurrence requirement** (leftmost lane = global min numeric x0,
   no clustering/recurrence): `test_one_off_numeric_label_does_not_blind_the_positional_check`
   FAILS. All other 5 pass.

Each targeted test failed under its corresponding mutation and only that one; the guard is
shown to guard something, not just pass trivially.
