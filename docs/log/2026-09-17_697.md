# 2026-09-17 — GH-697: surface recovered scanned prose at the document level and the CLI

## What changed

Provenance-only fix, following the `_no_witness_backend_note` (#658) / `_label_unverified_note`
(#659) / `_ditto_unresolved_note` (#625) pattern in `src/socr/pipeline/orchestrator.py`:

- `UnifiedPipeline._scanned_prose_recovered_pages(records)` / `_scanned_prose_recovered_note
  (records)` — new staticmethods reading `rec.output.scanned_prose_recovered` off the FINAL
  winning `FinalizedPageRecord`, same precedence principle as the siblings (a page whose earlier
  attempt was a recovery but whose later, fully-verified candidate won instead reports nothing,
  so the note retires on its own).
- Hoisted `scanned_prose_recovered_pages = self._scanned_prose_recovered_pages(pre_records)` in
  `_phase_assemble`, next to `label_unverified_pages` / `ditto_unresolved_pages`.
- Added `or scanned_prose_recovered_pages` to the shared defect-bucket `if (...)` gate that wraps
  the whole event-emission / CLI-print block — this is the reachability fix. Without it, a
  recovered-prose page (real prose ships, not the bare marker, so `is_page_failed_marker` is
  False and `failed_pages` never catches it; `failure_mode` is `NO_WITNESS_BACKEND` or
  `HALLUCINATION`, neither of which is in the gate's OR-chain either) never turned the gate true
  on a document whose only signal was the recovery, so the CLI line was unreachable — the exact
  #659 shape.
- Added the CLI print line (red, styled like the no-witness ending since the page is still an
  ERROR status, not yellow like label/ditto which ship without a failure).
- Added the metadata-note append (unconditional site, outside the gate, same append-only rule:
  never overwrites an existing failure reason).

## What I measured before assuming the issue's framing

The ticket said "I looked: at the METADATA site (:13979) the notes appear to sit at top level...
so the bucket condition may bite at the CLI run-report site instead, or may already be fixed."
Confirmed by construction: built a document whose ONLY signal was a `scanned_prose_recovered`
page (`status=ERROR`, `audit_passed=False`, real prose text) and drove it through the real
`_phase_assemble` before touching any code.

- **Document status was already correctly non-SUCCESS** (`AUDIT_FAILED`) before this change —
  NOT because any defect-bucket caught it, but because `PageState.needs_repair` reads
  `best_output.audit_passed`, which this recovery ending always sets `False`, so
  `pages_needing_repair` is non-empty and `pages_ok` is forced False regardless of any bucket
  membership. This is a real, load-bearing mechanism, not a test artifact — verified by also
  setting `ps.best_output` (the confound I checked and ruled out: without it, `needs_repair` is
  `True` for an unrelated reason and the measurement is meaningless).
- **The metadata note (`final_result.error`) was `None`** before this change. Confirmed.
- **The CLI line was absent** before this change — confirmed by capturing console output; the
  gate's `if (...)` never turned true on this sole-signal document, so the entire print block
  (which contains all the yellow/red per-defect lines, `label_unverified`/`ditto` included) never
  ran. This IS the issue's named trap, and it does bite at the CLI site, not the metadata site
  (the metadata site is unconditional, outside the gate).

So the issue's framing was correct on both counts: document status already fine, and the trap
bites at the CLI reachability line, not the metadata append. No correction needed to the ticket.

## Scope note

Did not add `scanned_prose_recovered_pages` to the `pages_ok` chain — document status is already
correctly demoted through the `needs_repair`/`audit_passed=False` mechanism described above, and
the ticket's stated gap was CLI + metadata only. Did not add an `AuditEvent` emission loop for
this bucket (the siblings that have one — `label_unverified`, `ditto` — feed `tables_trust.json`
consumers this recovery ending has no equivalent of); the page's own `audit_notes` already carries
`SCANNED_PROSE_RECOVERED_NOTE` per #649.
